# 亲缘数据模型：两种合规写法（2026-11-18）

> 用户口径（2026-11-18）：
> 「亲属边本体也能写，但是装了拓展时候 拓展会直接覆盖掉（其实是不合规的）。
> 合规写法：1. 不装拓展 自己维护亲缘关系；2. 装拓展 写生父生母交给拓展计算亲缘关系。」
>
> 本文定的是**数据模型与合规判据**。族谱/宗族怎么显示见 `extensions/family/doc/CLAN-DESIGN.md`，
> 扩展与宿主的边界见 `docs/EXTENSIONS.md`。

---

## 1. 两种模式，互斥

| | **模式一：不装拓展** | **模式二：装拓展** |
|---|---|---|
| 模板怎么写亲缘 | 自己写 `father` / `mother` / `wife` / `son` … 边 | **只写 `fatherId` / `motherId` 指针** |
| 亲缘由谁维护 | 模板作者 | 扩展（建图、推导） |
| 亲属称谓 | **不推导**（引擎不产 `kinshipTerm`） | 扩展推导，投影下发 |
| 族谱 / 宗族视图 | 不出现 | 出现 |
| 典型用途 | 只需要"某人是某人的父亲"来跑条件/事件 | 要称谓、族谱、宗族、继承 |

**同一个模板不许两者都用。** 这就是 `kinship_conflict` 的判据。

---

## 2. 判据：装拓展又写亲属边 ⇒ 加载期拒载

```
world.yaml 声明了 extensions.family
  且 任一 characters.yaml 边 / 事件效果建的边，kind ∈ KinshipKind
⇒ 该版本不可载，封闭码 kinship_conflict
  reason 点名：哪个角色、哪条边（from → to, kind）
```

与 `unknown_extension` 同类：**按版本标不可载、带 reasonCode、不崩进程**。

### 为什么是拒载，而不是"扩展覆盖掉"

当前实现的实际行为不是"覆盖"，是**并存 + 被静默压掉**：

- 模板写了 `father` 边 ⇒ 投影里有一条事实行；
- 扩展又从指针推出一条"爸爸"⇒ `extendRows` 因为 `factCounterpartIds` 里已有这个对手而**丢弃**它；
- 结果：玩家看到的是模板那条，扩展那条无声消失，**没有任何报错**。

覆盖至少是"新赢旧输"，而静默压制是"谁先到谁赢，且没人知道打过架"。
模板作者以为自己在用扩展，实际扩展被架空——这比崩掉更难查。

所以：**冲突必须在加载期炸**，让人当场改。运行期择一是下策。

## 3. 数据结构

### 3.1 模式二：指针在 NPC 上

```ts
interface V2Npc / CharacterSchema {
  /** **大众认知的生父**。缺省 = 不详（不编）。**一切亲缘推导按这个算**。 */
  fatherId?: string;
  /** **大众认知的生母**。 */
  motherId?: string;
  /**
   * **血缘上的生父**（CK3 式，私生子系统专用）：`realFatherId ≠ fatherId` 时，
   * 众人以为的生父与真正的生父不是同一个人。
   *
   * 与 `fatherId` 的区别是**认知 vs 事实**，不是"名分 vs 血统"
   * —— 那是另一回事，别混。
   *
   * `未决`：私生子系统落地时再启用。**本轮即使写了也不参与任何推导**，
   * 亲缘一律按 `fatherId`。
   */
  realFatherId?: string;
}
```

- **指针是唯一真源**。兄弟姐妹、祖孙、叔伯、堂表全部**派生**，不写第二份。
- `fatherId` / `motherId` 指向角色 id，**必须存在**（加载期校验，缺失=`unknown_reference`）。
- 性别不校验（父=男性是常识，但不必强制；模板写错由称谓推导暴露）。
- 玩家也适用（玩家有 `fatherId`，不是特例）。

### 3.2 婚配：归扩展

```ts
// state.extensions.family
interface FamilyState {
  spouses: Array<{ a: string; b: string; since?: number; until?: number }>;
  /** 收养（第三层推导用）：`parent` 是养父母，`child` 是被收养者。 */
  adoptions: Array<{ child: string; parent: string; since?: number; until?: number }>;
  clans: ClanFact[];      // 见 extensions/family/doc/CLAN-DESIGN.md
  members: ClanMember[];
}
```

- 婚配放扩展而**不留在 core 的边里**：多妻、继室、和离这些语义只有家族关心，
  core 今天没有任何消费者；留在 core 等于 core 又得认识"配偶"。
- `a`/`b` 无向，按 `(min,max)` 归一去重；`until` 表达和离/丧偶（历史要留，不删条目）。
- **多妻顺序 = 数组顺序**，不再需要 `spouseOrdinal`（那个字段已删，理由见 `CLAN-DESIGN §1.5`）。

### 3.3 core 的 `KinshipKind` **保留不动**

模式一需要它。它退出的是**家族扩展的数据源**，不是 core 的类型系统。
`isKinshipKind()` 仍然有用——`kinship_conflict` 的检测就靠它。

## 4. 建图与增量

| 时机 | 做什么 |
|---|---|
| **世界初始化** | 从 `characters.yaml` + `opening.yaml` 的指针建一次亲属图（父边 + 婚配边），挂到家族扩展的运行时 |
| **NPC 出生 / 生成** | 追加该节点的父指针与婚配边（`generatedCharacters`、spawn 效果、刷新规则都走同一入口） |
| **NPC 死亡** | **不改图**。死者仍是亲属（ADR-0020 先例：逝去的祖父依旧是祖父），只是称谓/族谱上标已故 |
| **认领 / 过继**（未决） | 改 `fatherId` 并留一条事记；不要悄悄改，否则族谱会"重写历史" |

- **建边策略复用现有上限**：称谓推导仍用 `FamilyConfig.maxHops`（默认 3）；族谱渲染用 `maxGenerations`（默认 4）。
- 图**建一次 + 增量维护**，不要每次投影重建——`valmont` 12 人已经跑过 2s 级耗时，人多会爆。

## 4.5 推导顺序：血亲 → 拟制 → 收养

族谱不是一次算出来的，是**三层叠加**，顺序不能换：

| 层 | 输入 | 产出 | 会不会被上层改写 |
|---|---|---|---|
| **1 血亲** | `fatherId` / `motherId` 指针 | 父母、子女、同胞 / **半同胞**、祖孙、叔伯姑舅姨、堂表 | **不会被改写**，是地基 |
| **2 拟制（婚配）** | 婚配表 + 已算出的血亲 | 继父母、继子女、继兄弟姐妹；姻亲（岳 / 婿 / 嫂 / 姐夫…） | 只在**血亲不存在**处补位 |
| **3 收养** | 收养表 | 养父母、养子女、养兄弟姐妹 | 只在**血亲与拟制都不存在**处补位 |

三条硬规则：

1. **顺序不能换**。先有血亲才谈得上"继"（继母 = 父之妻 **且非** 生母），先有家才谈得上"养"。
2. **下层不许改写上层**。某个位次已经被血亲占住，拟制与收养不得覆盖。
   一个人同时是「母亲」和「继母」只可能是**两条不同的边**（生母 / 父之再娶），
   不能因为"她是父之妻"就把生母降级。**这正是今天修掉的那个 bug**：
   旧实现把「父之妻」一律折成「母」（`relationship.js` 的假定），
   于是伊尔玛被算成奥德里克的母亲，而他亲妈是希尔达。
3. **半血亲在第一层就出来**：同父异母 / 同母异父 / 同胞，靠"共同亲代数"区分，
   不用等第二层，也不该被当成"继"。

**族谱的呈现**：血缘边实线、婚配边虚线（跨行弧）、**收养边虚线弧 + 「养」标记**。
世代仍**只按血缘**算；无血亲父母的孤儿用养父母提供定位（否则上不了树），
并在节点上标 `generationBasis: "adoptive"`，让它与真血亲的层级区分开。

## 5. 长幼：按出生时间算，不再靠边 kind

模式二的边只有父/母，没有 `elder-brother` 这种 kind，所以：

- 兄弟谁大 ⇒ 比 `birthTime`；
- 伯父还是叔父 ⇒ 父亲的兄弟与父亲比 `birthTime`；
- **`birthTime` 缺失（生成角色常见）⇒ 不要编**，退中性词（兄弟 / 父辈），并在这条读法上标 `unknown`。

这比"库凭空给大/小"和"边里编码长幼"都干净：**信息在就在，不在就不猜**。
（`Npc.birthTime` 已有，年龄是由它 + 世界时间现算的。）

## 6. 与 `birthStatus`（名分）的关系

另一条在办的改动给 `V2Snapshot.npcs[]` 加了 `birthStatus: legitimate | out-of-wedlock | unacknowledged`，
语义是"父母都在册且有配偶边 / 都可见但无配偶边 / 缺可见父或母之一"。

**它和本模型是同一条线上的两层**，需要对齐：

| 层 | 字段 | 含义 |
|---|---|---|
| 名分 | `fatherId` | 谁认这个孩子（社会/法律上的父） |
| 血统 | `realFatherId`（未决） | 谁生物学上是父 |
| 名分状态 | `birthStatus` | 由前两者 + 婚配表推出 |

- 只有 `fatherId` 时，`birthStatus` 由「`fatherId` 与 `motherId` 之间有没有婚配」推出 —— 这正是现有实现的算法，**兼容**。
- 加了 `realFatherId` 之后，`birthStatus` 要改成「名分父 vs 血统父是否同一人 + 婚配表」，否则同一个词在两套模型下含义不同。

**这两个改动应该一起落**，否则会出现"名分从配偶边推、血统从指针读"的半套。

## 9. 未决

- `realFatherId`（血统 vs 名分）的完整语义：认领流程、`birthStatus` 重算、族谱上怎么画两条父线。
- 婚配的"仪式/法律"区分（CK3 有 concubine）：本轮只有一条 `spouses`，不分等级。
- 模式一是否需要"只写部分亲缘"的宽容（例如只写父边、不写母边）——现在是允许的（缺省=不详），但会让称谓推导出现断层，需在模板规范里写清代价。
- 冲突判据的**粒度**：是"任一亲属边都不许"还是"允许边 + 指针并存但以指针为准"。本稿选前者（全禁），因为并存就是双真相。

- **主称谓的「父系优先」是硬编码惯例，不读模板的 `descent`。**
  例：`休→巴尔多` 同时是「爷爷」（父系：父亲奥德里克之父）与「外公」（母系：母亲玛蒂尔达之父），
  主称谓取「爷爷」，外公进 `kinshipTerms` 附加读法。依据是**中文惯例 + 直系优先**，不是路径更短（两者同跳）。
  `valmont` 声明 `descent: patrilineal`，恰好一致所以没暴露差异；若某模板要 `bilateral` 或母系，
  引擎仍会给「爷爷」——那就是引擎用自己的惯例替模板做主。
  要接 `descent` **得先有第二个非父系模板验证**，否则只是把一处硬编码换成另一处未经证实的抽象。

- **`birthStatus`（出生名分）本轮不做，属私生子系统。** 用户口径：「后面设计私生子的时候再看吧，
  这轮私生子按 `fatherId` 算亲缘就行」。
  落地时有两条硬约束：
  1. **位置**：必须在**扩展契约**（`extensions/family/src/contract.ts`）里，**不许**挂在
     `V2Snapshot.npcs[]` —— 那是 core 拥有的快照类型，加进去等于宿主认识「婚生 / 私生」，
     直接违反 §1 的"宿主零知识"。
  2. **算据**：由 `fatherId` / `realFatherId` / 婚配表推出，**不要**从"父母之间有没有配偶边"反推
     —— 后者是边模型的临时等价物，指针模型落地后就是错的。

### 7.1 迁移前必须先解决的两处（否则会静默降级）

1. **行级称谓在指针模式会消失**。NPC 卡上的「关系」行来自 `state.relations`；指针模式下那里没有亲属边
   ⇒ 没有行可装饰。
   **解法（用户 2026-11-18）：「计算的时候把边加回去」** —— 投影期把指针合成的边**并入边集合**，
   之后的行装配、称谓装饰（`relationDerivation`）、族谱全部照旧走原来的路。
   接缝只需加一个"扩展可以贡献关系边"的钩子；**`RelationCardContext` 不用加字段**，
   行级逻辑也不用搬进扩展。合成边**只活在投影里**，绝不写回 `state.relations`。
2. **切片重建会抹掉婚配表**。`FamilyStateSchema` 目前是 strict 的 `{ clans, members }`，而
   `writeClanState` 会**重建整个切片**。现在往里写 `spouses` / `adoptions`，任何 clan effect
   （`joinClan` 等）一跑就整块覆盖 ⇒ 亲属图当场塌。
   解法：先扩 schema 加 `spouses` / `adoptions`，并让所有写点保留这两个字段。**这条必须早于模板迁移。**

> 顺序：`3a 切片 schema + 写点保留` → `3b 接缝补 actors/extensionState + 合成亲属行` → `3c 模板迁移 + 闸门接入`。
> 3a 是纯增量零行为变化；3b 会改变"关系行长什么样"，应当在有人盯着的时候做。

**3b 的形状**（据上一条解法）：接缝加

```ts
/** 扩展可向投影**贡献**关系边（通常是「从指针合成」）。返回的边只活在投影里，不写回 state。 */
readonly contributeRelationEdges?: (ctx: RelationEdgeSourceContext) => readonly RelationEdge[];
```

核心在 `projection.ts` 里把它返回的边并入 `observableRelations`（**并集后去重**，按 `(from,to,kind)`），
再把合并后的集合同时喂给行装配与 `relationDerivation` —— **一个集合，两个消费者**，
不允许两条路径各拿一份（那就会重新长出双真相）。
合成边的 `source` 用一个明确值（不能伪装成 `template`），前端据此可以区分"声明的关系"与"推出来的关系"。
