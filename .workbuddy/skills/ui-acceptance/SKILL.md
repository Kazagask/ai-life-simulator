# 对抗式视觉验收（UI Acceptance）

## 为什么存在

作者自己看自己做的特效，会**自动补全意图**：心里知道「这里应该是一道刃」，看图时就把那团糊掉的红光认成刃。
用户没有这个补全，所以他看到的是「一坨」。这个技能的作用是**在给用户看之前，先让一个没有上下文的人挑刺** —— 挑不出来，才算过关。

## 什么时候用

- 改过 `packages/rpg-ui`（战斗界面、特效、战斗结算）之后；
- 用户对上一版说过「丑」「不如以前」「别再让我看到」之后；
- 任何要发给用户看的界面截图之前。

## 流程

### 1. 截图（必须三帧 × 两档宽度）

一帧说明不了问题，位置错、不淡出、残留，都只在中间帧或结尾帧才露出来。

| 帧 | 时机 | 看什么 |
|---|---|---|
| `cast` | 施法开始后 0.5×castMs | 起手是否在角色身上、是否像「起手」 |
| `fly` | 施法中后段 | 轨迹是否连在起手与目标之间、跨度和弧度 |
| `hit` | 命中后 80–150ms | 受击是否落在轨迹终点、是否够醒目 |

宽度：**430**（手机竖屏）+ **1280**（桌面，卡会拉成 900px 长条，百分比锚点全在这里露馅）。
每套图用独立文件名（`.tmp-ui-<tag>-<frame>.png`），避免看图工具缓存旧图。

### 2. 交给人格化的挑剔者（必须新 context）

用子代理跑评审，**不要自己在主线程里看**：主线程已经知道「我改了什么」，看不出丑。

评审提示词要素：

- 身份：挑剔的视觉总监，不认识这个项目，不关心实现代价；
- 只给图 + 一行说明（「这是技能 A 的施法/飞行/命中三帧」），**不给改动理由**；
- 硬性清单（见下）逐条判 PASS/FAIL；
- 输出：`VERDICT: PASS|FAIL` + 3 条最丑的地方 + 每条一句具体改法；
- 明确要求：**宁可错杀**，含糊就判 FAIL。

### 3. 不过就改，改完重拍重评

同一个挑剔者**重新开一个**（不要接着上一个，它会为了自洽而放宽标准）。

### 4. 全 PASS 才发用户

发的时候只描述「现在是什么样」，不要解释「我改了几版」——用户要的是结果。

## 硬性清单（任一 FAIL 即整体 FAIL）

| # | 检查 | 为什么 |
|---|---|---|
| 1 | **三点成链**：施法在角色上 → 轨迹从施法处出发 → 受击在轨迹终点 | 断开就是「打偏了」 |
| 2 | **轨迹有跨度**：明显长于卡片高度的一半，且有弧度 | 短直线像 UI 进度条，不像攻击 |
| 3 | **受击落在目标卡上**，不在卡片之间的空隙、不在屏幕边缘、不压住伤害数字 | 落在空处最像 bug |
| 4 | **不留残影**：命中后 1 秒，屏上不该还有球、环、线停在原地 | 「球放这了」是用户第一个会骂的 |
| 5 | **主次分明**：一眼能说出主体是什么（球 / 刃 / 法阵），陪衬不超过两种 | 12 根一样粗的线 = 蒲公英 |
| 6 | **有渐变**：发光体不能是纯色块（白核 → 本色 → 暗边） | 纯色 = 贴纸 |
| 7 | **两档宽度都不崩**：430 与 1280 下位置与大小都成立 | 百分比锚点只在一种宽度上凑巧对 |
| 8 | **不遮关键信息**：生命/资源数值、技能名在演出期间仍可读 | 好看不能以读不出数为代价 |

## 反面教材（这个项目真实踩过的）

- 施法画在卡面中间、轨迹从右下角冒出来 → 断开；
- 为了「连上」把轨迹起点挪到卡面中心 → 跨度塌成一小截，更丑；
- 受击用卡面中心、轨迹终点用宽度 30% → 刃插在 A、爆点在 B；
- 光球只画不收 → 演完还挂在血条上；
- 起手和受击都是八向星芒 → 看起来在两个地方各炸一次。
