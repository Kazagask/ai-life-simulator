### 0.3 句式（EARS）

每条需求用下列五种之一，便于直接转成测试：

| 类型 | 句式 |
|---|---|
| 普遍 | 系统应当…… |
| 事件驱动 | 当……时，系统应当…… |
| 状态驱动 | 当处于……状态（如「已终止」「已归档」）时，系统应当…… |
| 非期望行为 | 如果……，系统应当…… |

## 2. 功能需求

### A. Lifecycle 生命周期骨架（`S1 §2 / §6`）— ⛔ 整节 `RETIRED`（R2.2 退役）

> **用户 2026-11-11 决定：不引入生命周期概念。** 「模拟终止」确实需要新建，但六阶段状态机（`CREATED → OPENING → RUNNING → ENDING → EVALUATING → ARCHIVED`）、`LifecycleState`、`PhaseTransitionLog` 与 `lifecycle.ts` 属过度设计。真正需要保留的是三条不变量：开局完成前不推进轮次、终止后拒绝行动、归档只读 —— 分别由 `R-TM-01..03`、`R-OP-07`、`R-EV-06`、`R-AR-02` 承担。理由与成本对比见 `design.md` §3。
>
> 以下 6 条**编号与原文保留，状态为 `RETIRED`**：不实现、不测试、不派任务、不计入 DoD；日后恢复只需把状态改回 `ACTIVE`，编号不重排。

**R-LC-01（事件驱动｜S1 §2.1）**：当一局游戏被创建时，系统应当进入 `CREATED` 阶段，绑定世界观模板与开局模板，并按 `CREATED → OPENING → RUNNING → ENDING → EVALUATING → ARCHIVED` 推进。
验收：
- Given 选定世界与开局模板；When 创建实例；Then `phase === "CREATED"` 且记录两个模板 ID。
- Given 任一阶段；When 正常完成条件满足；Then 只迁移到状态机定义的下一阶段。

**R-LC-02（非期望行为｜S1 §6.1.7）**：如果发生非法阶段迁移（如 `OPENING → ARCHIVED`、重复进入 `ENDING`），系统应当拒绝并给出可诊断错误，且保持原阶段与状态不变。
验收：Given `OPENING`；When 请求跳到 `ARCHIVED`；Then 抛带阶段名的错误，状态快照与调用前逐字段相等。

**R-LC-03（普遍｜S1 §2.1、§2.2）**：系统应当把 Lifecycle 限定为阶段编排与模块调用：它不直接执行事件、不做时间换算、不计算人生分数、不写角色属性。
验收：静态检查 `lifecycle` 模块不得 import 事件结算 / 历法换算 / 评分实现；其导出仅为阶段查询与迁移函数。

**R-LC-04（状态驱动｜S1 §6.1.1）**：当处于 `CREATED` 或 `OPENING` 阶段时，系统应当拒绝普通轮次推进请求。
验收：Given `OPENING`；When 调用轮次推进；Then 返回 `PHASE_NOT_RUNNING`，世界时间与事件历史不变。

**R-LC-05（状态驱动｜S1 §6.1.3）**：当处于 `ENDING` 及之后阶段时，系统应当停止接收普通模拟行动；必要的**当前**事件结算完成后再固化最终状态。
验收：Given 终止条件在事件结算中命中；When 结算完成；Then 该事件效果完整落库，之后任何玩家行动被拒，且不产生「半更新」状态。

**R-LC-06（普遍｜S1 §2.1、§6.1.7）**：每次阶段切换，系统应当产生一条含 `from / to / 触发原因 / 世界时间 / 轮次` 的日志。
验收：Given 完整跑一局；When 读取阶段日志；Then 日志条数 = 合法迁移次数，且 `from/to` 首尾相接、可复原完整阶段序列。

### A2. Termination 模拟终止（`R2.2 新增｜用户 2026-11-11 决策`，取代 `R-LC-*`）

**R-TM-01（事件驱动｜用户决策 ①）**：当终止条件在模拟边界命中时，系统应当固化一条 `TerminationRecord`（`reason / worldTime / turnIndex / endingId? / source`），停止接收普通轮次与模拟行动，并在当前事件完整结算后才落定最终状态；重复终止请求应幂等且不得产生「半更新」。
验收：
- Given 终止条件在事件结算中命中；When 结算完成；Then `termination !== null`、该事件效果完整落库，之后任何玩家行动被拒且状态逐字段不变。
- Given 已终止；When 再次调用终止；Then 返回同一 `TerminationRecord`，不追加记录、不改写世界状态。

**R-TM-02（状态驱动｜用户决策 ①）**：在 `openingCompleted === false` 时，系统应当拒绝普通轮次推进；开局 `handoff` 完成后置为 `true`，之后首轮可正常消费 chains 与 schedule 中的事件。
验收：Given 开局未完成；When 调用轮次推进；Then 返回 `NOT_ACTIVE`，世界时间与事件历史不变；Given `openingCompleted === true`；Then 首轮推进成功。

**R-TM-03（非期望行为｜用户决策 ①）**：系统应当以「运行 / 已终止」二态加归档只读标记表达模拟结束，**不得新增六阶段状态机、`Phase` 枚举、`PhaseTransitionLog` 或独立 `lifecycle.ts` 模块**；阶段序列不得成为可复现性或回放断言的一部分。
验收：Given 静态扫描 `game-core/src/v2/`；Then 无 `lifecycle.ts`、无 `PhaseTransitionLog`、无 `transition(state, to: Phase)` 形式导出；Given 同 seed 两次回放；Then 归档逐字段相等且不依赖任何阶段序列。

### B. Opening 开局（`S1 §3`）

**R-OP-01（可选特性｜S1 §3.1）**：在模板提供了多个 `OpeningTemplate` 时，系统应当允许按 `openingId` 选择开局，并支持不同年代、身份、地点、人生阶段或剧情切入点。
验收：Given 同一世界两个开局模板；When 分别创建；Then 主角、起始时间、地点、初始关系至少一项按模板不同。

**R-OP-02（普遍｜S1 §3.2、§3.4）**：系统应当支持模板声明开局步骤及顺序，且模板可增删必经/可选/分支步骤；通用能力覆盖：选世界与开局模板、角色创建或选择、开局参数（起始时间/地点/随机种子/初始规则）、初始化世界状态、初始化关系、组织初始目标、抽取并执行开局事件、交接模拟引擎。
验收：Given 模板删去「玩家选择」步骤；When 跑开局；Then 流程按剩余步骤完成且 `OpeningRun` 记录实际执行步骤序列。

**R-OP-03（普遍｜S1 §3.1、§3.2 末段）**：系统应当以「固定必要步骤 + 事件池随机抽取 + 关键节点玩家选择」组织开局，且不要求模板预先编排完整剧本。
验收：Given 固定步骤模板 + 随机池；When 同 seed 跑两次；Then 固定步骤一致、随机事件一致；换 seed 后随机事件可变而固定步骤不变。

**R-OP-04（可选特性｜S1 §3.3）**：在模板声明开局事件池时，系统应当支持 `tags`（按身份/地点/背景筛选）、`weight`、`conditions`、`required`、`countRange`、`exclusiveGroup`、`sequence`、`seed`、`effects`、`nextEvents`，并支持「固定主事件 + 若干随机遭遇/关系事件」组合。
验收：
- Given 两个事件同 `exclusiveGroup`；When 抽取；Then 至多命中一个。
- Given `required: true` 且条件满足的事件；When 抽取；Then 必定出现。
- Given `countRange: [1,3]`；When 多次同 seed 抽取；Then 数量落在区间且结果可复现。

**R-OP-05（普遍｜S1 §3.2 步骤 4/5/6）**：当初始化世界状态时，系统应当创建主角、初始 NPC、组织、地点、物品/装备、属性与信息权限，并创建带来源的初始关系；**不得默认所有 NPC 都认识主角**。
验收：Given 模板未声明某 NPC 与主角的关系；When 初始化；Then 该关系不存在或为 `unknown`，且信息可见性按模板分级。

**R-OP-06（普遍｜S1 §3.5；受 A4/A5 约束）**：开局事件应当复用统一事件系统的定义、条件判定、效果结算与事件记录；当前连续处理的事件进入现有事件链状态机，带未来时间或条件的事件进入现有 schedule 事件；**不得新建独立「事件栈」调度器，不得新增事件类型枚举**。
验收：
- Given 开局产出一条事件；When 检查其结构；Then 与普通事件共用同一定义/结算路径，仅实例级元数据 `origin` 标为 `opening` + `openingId`。
- Given 静态检查；Then 无新增栈式调度模块，`source` 枚举值数量不变。

**R-OP-07（事件驱动｜S1 §3.2 步骤 8、§3.4 `completionConditions` / `handoff`；R2.2 去阶段化）**：当开局完成条件满足时，系统应当按 `handoff` 交接给模拟引擎、标记开局完成（置 `openingCompleted = true`），不设置阶段枚举。
验收：Given 有未完成即时事件与一条未来事件；When 交接；Then 两者分别进入现有待处理链与 schedule，`openingCompleted === true`，且首轮推进能正常消费它们（R-TM-02）。

### C. Ending 结局（`S1 §4`）

**R-EN-01（可选特性｜S1 §4.1）**：在模板定义终止条件时，系统应当支持时间条件、角色状态、目标条件、世界状态、事件条件、玩家主动结束，以及多个条件的 AND / OR 组合。
验收：Given `(到达年龄 X) AND (主目标完成)`；When 只满足其一；Then 不触发结束；两者都满足时触发。

**R-EN-02（普遍｜S1 §4.1 末段）**：系统应当只在明确的模拟边界（事件结算后、时间推进后、玩家主动结束时）检查终止条件，不在每个内部计算步骤重复检查。
验收：Given 一次结算内状态临时满足条件、结算后不满足；When 跑完该结算；Then 不产生误触发。

**R-EN-03（可选特性｜S1 §4.1；R2.2 去阶段化）**：在模板配置了立即终止（如战败触发的死亡结局）时，系统应当立即停止模拟；未配置时应当默认采用「事件结算后终止」。终止一律走 `R-TM-01` 的 `TerminationRecord`，**不得由 HP 数值直接触发**。
验收：Given 立即终止条件命中；When 事件结算中途；Then 按模板语义停止且不留下半更新状态（与 R-TM-01 一致）。

**R-EN-04（事件驱动｜S1 §4.2）**：当任一终止条件满足时，系统应当收集世界状态、主角状态、关键关系、已发生事件与重要选择，筛选满足条件的结局模板，按 `priority`、专属条件与 `exclusiveGroup` 决胜；若无专属命中则使用 `fallback` 结局，最后固化 `EndingRecord` 并交给 Evaluation。
验收：Given 三个结局同时满足；When 判定；Then 命中 `priority` 最高且不与更高优先级互斥组冲突者；同输入重复执行结果一致；无专属命中时命中 `fallback`。

**R-EN-05（可选特性｜S1 §4.3）**：在模板定义结局时，系统应当支持 `endingId / name / description / triggerConditions / priority / endingType / narrativeConfig / visibility / exclusiveGroup / fallback`，含隐藏结局、互斥结局与默认结局；结局模板只负责选择与描述，不计算人生评价。
验收：Given 隐藏结局未满足解锁条件；When 筛选；Then 不进入候选集；Given 静态检查；Then 结局模板结构中无评分字段。

**R-EN-06（非期望行为｜S1 §4.4）**：如果 LLM 生成的结局叙事包含未发生的关键事实、修改了游戏状态或补写不存在的选择，或输出未通过结构校验，系统应当拒绝该输出并回退到模板文本/变量填充，且不污染最终状态。
验收：Given 注入一条含虚构事件的 LLM 输出；When 生成结局叙事；Then 回退模板文本，最终状态与调用前逐字段相等。

**R-EN-07（普遍｜用户决策 ④）**：系统应当保证模拟过程中玩家 HP **不低于 1**（战斗镜像与回写世界状态均 clamp 到 `[1, maxHp]`），且**不得把 HP ≤ 0 / HP 归零作为终止条件或死亡结局的触发条件**；死亡是叙事/事件层结论，不是资源层数值结论。
验收：
- Given 战斗把玩家 HP 打到 1 以下；When `checkBattleEnd` / `finishBattle` 回写；Then `state.player.hp >= 1` 且模拟继续（除非另有终止条件命中）。
- Given 模板扫描；Then 不存在以 `hp <= 0` /「HP 归零」为条件触发结局的声明；静态检查 `ending.ts` 不读取 HP 作为死亡判据。

**R-EN-08（事件驱动｜用户决策 ④）**：当战斗以 `defeat` 结束且模板的死亡判定条件满足时，系统应当按模板声明的 `deathMode` 走两条路径之一：（a）`event` —— 生成模板声明的死亡事件，经既有事件链结算后由该事件触发结局；（b）`direct` —— 直接触发结局。两条路径都不改写 HP、不绕过 `R-TM-01` 的终止标记；战败但条件不满足时模拟继续。
验收：
- Given `deathMode: event` 且条件满足；When 战败结算；Then 死亡事件出现在事件历史且随后产生 `EndingRecord` 与 `TerminationRecord`。
- Given `deathMode: direct` 且条件满足；When 战败结算；Then 直接产生结局与终止标记，无死亡事件实例。
- Given 条件不满足；When 战败结算；Then `termination === null`、`hp >= 1`，模拟可继续。

### D. Evaluation 人生评价（`S1 §5`）

**R-EV-01（普遍｜S1 §5.1）**：系统应当把结局与人生评价作为两个独立结果：结局类型不得直接决定评价高低，死亡/失败结局不得自动得到低评价。
验收：Given 两个过程记录不同但结局类型相同的局；When 评价；Then 至少一项维度得分不同；Given 结局类型不同但过程相近的两局；Then 评价可相近。

**R-EV-02（可选特性｜S1 §5.2）**：在模板未覆写时，系统应当提供成就、人际、幸福、影响、道德、遗憾六个通用维度；模板可增删、改名、调整权重，并可增加世界观专属维度（守护/探索/知识/名望/自由等）。
验收：Given 模板增加「名望」并删除「道德」；When 评价；Then 输出维度集合与模板一致。

**R-EV-03（普遍｜S1 §5.3）**：系统应当基于**整个过程**计算评价，输入包含最终角色与世界状态、关键事件与重大选择及其后果、目标完成情况、关系变化与最终状态、成长轨迹、对世界/组织/他人的长期影响；结局类型仅作背景信息。
验收：Given 两局最终属性面板相同但事件历史不同；When 评价；Then 结果不同，且差异可归因到历史事件。

**R-EV-04（普遍｜S1 §5.4）**：系统应当输出各维度得分/等级及解释、关键成就与重要关系总结、主要贡献与遗憾、人生总结文案，以及**评价依据**（关联事件 ID、选择记录或状态变化）；总体等级可选且不得取代分项。
验收：Given 任一维度得分；When 读取 `EvaluationRecord`；Then 能定位到至少一条证据 ID，且该 ID 存在于本局事件历史/选择记录中。

**R-EV-05（普遍｜S1 §5.5）**：分数/等级应当由确定性规则或可解释评分器计算；维度权重、评分区间、解释规则由模板配置；LLM 只把评价依据组织成自然语言总结，不得决定分数或改写事实。
验收：Given 同一 `EvaluationRecord` 两次调用 LLM 总结；When 对比；Then 分数、维度、证据 ID 完全一致；Given 注入篡改分数的 LLM 输出；Then 被结构校验拒绝并回退。

**R-EV-06（状态驱动｜S1 §5.5；R2.2 去阶段化）**：当本局已按 `R-TM-01` 终止并归档后，系统应当使本局不再接受普通模拟状态修改，且评价结果不得反向改变结局或模拟结果；不得依赖任何 `EVALUATING` / `ARCHIVED` 阶段枚举。
验收：Given 已终止且归档；When 尝试写状态/改结局；Then 拒绝且记录只读错误。

### E. Archive 归档（`S1 §1、§6`）

**R-AR-01（事件驱动｜S1 §1.5；R2.2 去阶段化）**：当本局终止并完成评价后，系统应当保存最终状态快照、事件历史、结局记录、评价记录与 **`TerminationRecord`**（取代原「阶段日志」），形成可回顾的本局记录。
验收：Given 完整一局；When 读归档；Then 五类数据齐全且事件 ID 可被评价证据引用。

**R-AR-02（普遍｜S1 §2.1；R2.2 去阶段化）**：归档后的本局记录应当只读（由 `archived` 只读标记判定，不依赖阶段枚举）。
验收：Given 归档；When 任何写操作；Then 拒绝且不产生副作用。

**R-AR-03（普遍｜S1 §2.1 末段）**：首版应当沿用现有存档机制处理存档恢复与异常中断，不扩展阶段状态机。
验收：Given 服务重启后按现有机制恢复；Then 行为与恢复前一致；本轮不新增独立存档子系统。

### F. 时间穿越 Time Travel（`S2 A3；ADR-0002 §后果`）— ⛔ 整节 `DEFERRED`（延期至 R3）

> **本节 7 条需求 `R-TT-01`～`R-TT-07` 状态一律为 `DEFERRED`**：原文保留作为 R3 输入，本轮不实现、不测试、不派任务、不写 ADR-0005、不计入完成门槛（依据见 §0.2）。本轮只需守住 `design.md` §8 末列出的三个接口预留点，避免未来接入时需要重构。

**R-TT-01（普遍｜S2 A3、S1 §6 数据边界）**：系统应当把「模板原始事件定义 `EventDefinition`」「本局事件实例 `EventInstance`」「已发生事件记录」三层分离存储；原始定义在穿越后必须保留。
验收：Given 时间回拨；When 检查模板定义集合；Then 与回拨前逐条相等。

**R-TT-02（事件驱动｜增量说明 §2.3）**：当时间回拨（穿越）发生时，系统应当保留已发生的事件记录，并记录其**实际发生日期**。
验收：Given 事件 E 在 T2 发生；When 回到 T1；Then E 的记录仍在且带 T2 时间戳，未被删除或改写为 T1。

**R-TT-03（事件驱动｜增量说明 §2.3）**：当时间回拨时，系统应当检查当前时间之后的未来事件实例，删除或撤销其**执行状态**，但不得删除模板中的原始事件定义。
验收：Given 未来实例 F 已排程但未执行；When 回拨；Then F 的执行状态被撤销、定义仍在；已结算实例不受影响。

**R-TT-04（事件驱动｜增量说明 §2.3）**：当时间回拨时，系统应当把主角、亲友及重要 NPC 的未来事件转为隐秘状态，且该状态不得进入玩家端投影。
验收：Given 隐秘化的未来事件；When 生成玩家可见投影；Then 该事件不可见；服务端内部记录仍可查询。

**R-TT-05（事件驱动｜增量说明 §2.3）**：当回拨完成后，系统应当按新的世界状态重新触发相关事件，而非简单重放旧时间线。
验收：Given 回拨后某条件不再满足；When 推进到原触发点；Then 该事件不触发或按新条件分支触发。

**R-TT-06（普遍｜S4 可复现约束）**：时间穿越后的世界线应当可复现：同初始状态 + 同指令序列 + 同 seed（含穿越指令）产生相同的事件实例集合、隐秘状态与最终归档。
验收：两次相同输入的完整回放，归档逐字段相等。

**R-TT-07（可选特性｜S1 §7 末段、增量说明 §九）**：在提供 Steins;Gate 测试模板时，系统应当能验证时间穿越后的未来事件重置、世界线结局差异与人生评价差异。
验收：剧本测试通过，且不需要修改核心引擎即可表达该世界观规则。

### G. 装备系统（`S2 A10；S3 #9；ADR-0001`）

**R-EQ-01（可选特性｜增量说明 §七、S3 #9）**：在模板配置装备栏时，系统应当支持模板定义槽位、可装备类别、品质档位与初始装备；不同世界观可有不同的栏位结构。
验收：Given 两个世界模板栏位不同；When 加载；Then 校验通过且 UI 数据源来自模板，不改引擎代码。

**R-EQ-02（普遍｜S1 §6 数据边界）**：系统应当把「模板中的装备定义」与「本局装备实例」分离，实例携带所属角色、槽位、当前耐久/层数等本局状态（若模板启用）。
验收：Given 重新加载模板或恢复存档；When 检查装备定义集合；Then 不受本局实例变化影响。

**R-EQ-03（普遍｜ADR-0001、增量说明 §七）**：装备效果应当通过现有声明式效果 DSL / 补正系统表达，不新增通用基础属性语义（HP/ATK/DEF/CRIT…）、不引入自由表达式公式、不新增控制语义白名单之外的原语。
验收：Given 模板定义一件带属性修正的装备；When 结算；Then 走 `effectiveAttributes` 管线与 preset 白名单，静态检查无自由表达式求值器。

**R-EQ-04（普遍｜用户决策 ③；取代 S3 #9 待决项）**：装备词条**统一采用动态补正**：修正值在每次结算时按当前世界/战斗状态、条件与层数由 preset 白名单求值，**不得把结果固化进基础属性或写回装备实例**；无条件的固定值只是动态补正的退化形式，仍走同一求值管线。模板不再提供「静态词条 / 动态补正」二选一，引擎不保留另一套静态词条结算路径。
验收：
- Given 同一件装备、两份不同状态（如层数/心情/条件不同）；When 结算；Then 补正值不同且符合模板声明的 preset 语义。
- Given 穿脱前后；When 读 `state.player.attributes`；Then 基础属性逐字段不变；补正只体现在 `effectiveAttributes()` 输出。
- Given 模板使用自由表达式或 `attributeModifiers.perStack`（S3 #18）；When 协议校验；Then 报可诊断错误而非静默忽略。
- Given 同 seed 回放；Then 动态补正序列逐次相等。

**R-EQ-05（普遍｜S4）**：装备的穿戴/卸下/替换应当参与既有属性生效管线（每次重新求值动态补正），且在同 seed 下可复现；非法操作（槽位不匹配、重复占槽）应被 Zod/模板校验拒绝。
验收：Given 槽位冲突；When 尝试装备；Then 抛可诊断错误且状态不变；Given 卸下装备；Then 下一次 `effectiveAttributes()` 不再包含该件补正。

**R-EQ-06（普遍｜ADR-0001 §6 判定白名单）**：装备不得绕过 preset 判定白名单直接改写战斗判定或伤害结果。
验收：Given 装备携带判定类字段；When 协议校验；Then 非白名单字段被拒绝，错误信息指向具体字段。

### H. 战斗 AI 分层决策（`S2 A11；S3 #13；增量说明 §五`）

**R-CA-01（普遍｜增量说明 §5.2）**：系统应当把战斗行动决策拆为「规则约束 → 候选集生成 → 评分 → 选择 → 结算」五步，且每步可单独测试。
验收：Given 一个战斗状态；When 分别调用五步；Then 候选集不含被规则禁止的行动，选择结果等于评分最高者（或按模板决胜规则）。

**R-CA-02（可选特性｜增量说明 §5.2、S2 A11）**：在模板配置战斗风格（如激进 / 保守 / 防御反击）时，系统应当把风格解析为一组评分权重与候选集过滤参数，不硬编码风格行为到引擎。
验收：Given 同一战斗状态换三种风格；When 决策；Then 至少一次选择不同行动；静态检查引擎内无风格名字符串分支。

**R-CA-03（可选特性｜S3 #13；用户决策 ⑤）**：在模板配置条件化 AI 时，系统应当支持如「低血量优先治疗」「按**公有**属性针对性选技能」等条件化策略；条件表达式只能引用 `PublicConditionContext`（见 `R-CA-06`）。
验收：Given 低血量且治疗技能可用；When 决策；Then 按模板条件命中治疗；条件不满足时不命中；Given 条件引用隐藏字段；Then 模板加载阶段即被拒绝（R-CA-06）。

**R-CA-04（普遍｜S4）**：战斗 AI 决策不得依赖 LLM，且同 seed + 同状态 + 同模板产生相同选择。
验收：两次决策结果逐字段相等；注入不可用 LLM 时行为不变。

**R-CA-05（普遍｜ADR-0001）**：战斗 AI 只能从引擎既有行动/技能/控制语义中选择，不得凭空生成行动或改写控制语义白名单与判定 preset。
验收：Given AI 输出一个未注册行动 ID；When 校验；Then 拒绝并回退到合法候选，状态不变。

**R-CA-06（非期望行为｜用户决策 ⑤）**：条件化 AI 的条件求值**只能读取公有字段**：玩家端投影可见的字段、`visibility === "public"` 的日志/效果、以及该阵营已公开的战斗状态；不得读取 `hidden` / `unknown` / `secrets`、`combatHints`（敌方私有）、NPC 私有目标或服务端内部状态。引用非公有字段的模板应在 Zod / 协议校验阶段被拒绝并给出字段路径。
验收：
- Given 模板条件引用 `player.hiddenAttributes` / `npc.knownGoals` / `enemy.combatHints`；When 加载；Then 拒绝，错误信息指向具体字段路径，且无部分初始化状态。
- Given 模板条件只引用公有字段；When 两次同 seed 决策；Then 结果逐字段相等，且与玩家投影中的对应事实一致。
- Given 静态扫描 `combat-ai.ts`；Then 决策上下文类型仅由 `PublicConditionContext` 生成，不接收完整 `WorldStateV2`。

### I. 横切约束（`S4`）

**R-NFR-01（普遍；R2.2 去阶段化）**：系统应当保证同初始状态 + 同输入 + 同 seed 的完整可复现性，覆盖开局抽取、事件实例、终止标记、装备动态补正、AI 决策、结局、评价与归档；不含阶段序列。
验收：跨两组完整回放，最终归档逐字段相等。

**R-NFR-02（非期望行为）**：如果模板或运行时输入未通过 Zod 校验，系统应当拒绝加载并返回可诊断错误（字段路径 + 原因），不得带病进入模拟。
验收：Given 缺 `openingId` 的模板；When 加载；Then 报错含字段路径，且无部分初始化状态。

**R-NFR-03（非期望行为；R2.2 去阶段化）**：如果 LLM 输出结构校验失败或超时，系统应当回退到模板文本/变量填充，不得阻塞终止与归档流程，不得写入权威状态。
验收：Given 强制 LLM 失败；When 生成结局叙事与人生总结；Then 本局仍能完成终止并归档，文案为模板回退版本。

**R-NFR-04（普遍）**：`hidden` / `unknown` 信息不得进入玩家端 API 投影；R3 时间穿越产生的隐秘未来事件同样适用（本轮不实现该来源）。
验收：对投影结果做字段级断言，服务端内部记录不受影响。

**R-NFR-05（普遍）**：开局流程、终止条件、结局类型、评价维度、装备栏、战斗风格、历法与时间语义必须全部由模板/适配器表达，核心引擎不得出现世界观专属常量；MVP 不为逻辑拆分新增独立 npm 包。
验收：静态扫描 `game-core` 无世界观专名常量；包数量与当前 monorepo 一致。

**R-NFR-06（普遍｜`AGENTS.md` §4）**：每个新增能力应当至少提供正常路径、边界条件、无效输入三类测试，且 `pnpm typecheck` 与 `pnpm test` 通过。
验收：CI 命令输出 0 错误；新增测试文件可追溯到本文件需求编号。
