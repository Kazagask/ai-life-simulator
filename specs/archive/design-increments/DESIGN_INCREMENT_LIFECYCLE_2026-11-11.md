# AI人生模拟器：开局、结局与人生评价系统补充方案

**版本：2026-11-11**\
**用途：下一轮迭代设计补充，可作为现有技术方案的增量 Spec。**

> 本文补齐此前技术方案遗漏的开局系统、结局系统和人生评价系统。三者统一归入
> Lifecycle（生命周期）模块，但职责彼此独立。设计沿用项目既定原则：世界观模板化、事件驱动、轮次与世界时间解耦、避免预先编排完整剧本。

------------------------------------------------------------------------

## 一、设计目标与边界

每个世界观模板都应当具备完整的生命周期配置：

1.  **开局
    Opening**：决定本局从什么状态开始，初始化角色、世界、人物关系、初始目标，并组织开局事件。
2.  **模拟 Simulation**：由轮次、时间、事件、玩家行动和 NPC
    自主行动共同推动。
3.  **结局 Ending**：判断模拟何时结束，并确定本局发生了什么结局。
4.  **人生评价
    Evaluation**：独立评价主角这一生的经历、成就、关系、影响与遗憾。
5.  **归档
    Archive**：保存最终状态、事件历史、结局和评价，形成可回顾的本局记录。

核心引擎只提供生命周期调度和通用接口；具体开局流程、终止条件、结局类型、评价维度由世界观模板定义。

**重要区分：** - 结局回答：这一生最终发生了什么？ -
人生评价回答：这一生过得怎么样、留下了什么？ -
结局类型不能直接决定人生评价高低。 -
开局和结局都必须模板化，不能写死在核心引擎中。

## 二、Lifecycle 生命周期模块

### 2.1 模块职责

Lifecycle
统一管理一局游戏从创建到归档的阶段切换，避免轮次引擎、事件引擎或 UI
各自判断游戏是否开始/结束。

建议状态机：

`CREATED → OPENING → RUNNING → ENDING → EVALUATING → ARCHIVED`

首版只实现正常生命周期；存档恢复、异常中断等可沿用现有存档机制，暂不扩展复杂状态。

  阶段         负责内容                         完成条件
  ------------ -------------------------------- --------------------------------
  CREATED      创建本局实例，绑定世界观与模板   开局模板已选定
  OPENING      执行初始化、玩家选择、开局事件   开局模板的完成条件满足
  RUNNING      正常模拟                         任一终止条件满足或玩家主动结束
  ENDING       判定结局并生成结局记录           唯一结局确定并固化
  EVALUATING   计算人生评价、生成总结           评价结果生成
  ARCHIVED     保存最终快照与完整记录           本局只读归档

Lifecycle
不直接执行具体事件，不负责时间换算，也不负责计算人生分数。它只负责阶段编排和模块调用。

### 2.2 生命周期与其他模块的依赖

-   Opening 调用 Character、Relationship、World State、Event
    等模块完成初始化。
-   Simulation 调用 Turn、Time、Event、NPC、Combat 等模块。
-   Ending 读取模拟状态和历史记录，调用条件判定器筛选结局模板。
-   Evaluation 读取本局过程记录与最终状态，独立计算评价。
-   Archive 保存状态快照、事件历史、结局和评价。

不要让 Ending 直接修改角色属性，也不要让 Evaluation
反向改变结局或模拟结果。

## 三、开局系统 Opening

### 3.1 设计目标

开局不是简单创建角色，而是一段由世界观模板定义的初始化流程。

需要兼顾固定流程与随机性： -
固定必要步骤，确保人物背景和世界状态合理。 -
随机内容从模板事件池抽取，制造不同开局体验。 -
允许玩家在关键节点作出选择。 - 不要求模板预先编写完整剧本。 -
开局结束后复用统一事件系统进入正常模拟。

同一世界观可以提供多个开局模板，例如不同年代、身份、地点、人生阶段或剧情切入点。

### 3.2 通用开局流程

模板可以增删步骤，但建议提供以下通用能力：

1.  **选择世界观与开局模板**：选择世界、规则集、难度和开局方案。
2.  **角色创建/选择**：创建主角或选择模板角色；模板可定义出生、身份、背景、初始能力等字段。
3.  **确定开局参数**：起始时间、地点、随机种子、初始规则及可选参数。
4.  **初始化世界状态**：创建主角、初始
    NPC、组织、地点、物品/装备、属性和信息权限。
5.  **初始化人物关系**：创建初始关系及关系来源；不能默认所有 NPC
    都认识主角。
6.  **组织初始目标**：生成显式任务、短期目标、长期目标或隐藏动机。
7.  **抽取并执行开局事件**：从开局事件池按条件和权重抽取，形成开局事件链。
8.  **交接模拟引擎**：未完成的即时事件进入当前事件栈；未来触发事件进入未来事件队列；标记开局完成。

开局可以有必经步骤、可选步骤和分支步骤。不要把全部开局内容都做成随机事件，否则容易破坏角色背景与世界状态的一致性。

### 3.3 开局事件池

开局流程应当能够使用既有 Event Engine，而不是另造一套剧情系统。

事件池建议支持：

  配置             说明
  ---------------- ----------------------------------------
  tags             事件标签，用于按身份、地点、背景等筛选
  weight           抽取权重
  conditions       事件出现的前置条件
  required         是否为必选事件
  countRange       抽取数量范围
  exclusiveGroup   互斥组，避免冲突事件同时出现
  sequence         固定顺序或步骤约束
  seed             使用本局随机种子，支持复现
  effects          事件产生的状态变化
  nextEvents       后续事件或事件链

建议支持"固定主事件 + 若干随机遭遇/关系事件"的组合。

### 3.4 开局模板结构

建议至少包含：

  字段                   说明
  ---------------------- ------------------------------
  openingId              开局模板唯一 ID
  name / description     名称与说明
  entryConditions        模板适用条件
  steps                  开局步骤及顺序
  characterSetup         主角创建、选择及初始设定规则
  worldSetup             初始时间、地点、世界状态
  npcSetup               初始 NPC、关系与信息权限
  eventPools             开局事件池与抽取规则
  objectives             初始任务、目标或动机
  choices                开局阶段提供给玩家的选择
  completionConditions   开局结束条件
  handoff                完成后如何交接给模拟引擎

### 3.5 开局与事件栈/未来事件队列

沿用项目既定的简化方向，不预设完整剧本： -
当前需要连续处理的事件进入事件栈。 -
有明确未来时间或触发条件的事件进入未来事件队列。 -
开局事件使用统一事件定义、条件判定、效果结算和事件记录。 -
事件实例记录来源 `opening` 及对应 `openingId`。 -
模板原始事件定义与本局事件实例分离。

## 四、结局系统 Ending

### 4.1 结束条件

结束条件由世界观模板定义，建议支持：

  条件类型       示例
  -------------- ----------------------------------------
  时间条件       到达指定日期、年龄、人生阶段或时间节点
  角色状态       主角死亡、永久失去行动能力、达到某状态
  目标条件       主要目标完成、失败或全部失效
  世界状态       世界危机解决/失控、关键世界状态达成
  事件条件       指定事件完成、某条事件链终结
  玩家主动结束   玩家选择结束本局，模板可配置是否允许
  组合条件       多个条件以 AND / OR 组合

结束条件应区分： -
**立即终止**：用于死亡等必须立即结束模拟的特殊情况。 -
**事件结算后终止**：默认方式，当前事件完成状态更新后再检查，避免事件执行到一半被截断。 -
**进入结局阶段**：满足条件后停止普通模拟，执行结局流程。

结束条件检查应在明确的模拟边界执行，例如事件结算后、时间推进后或玩家主动结束时。不要无意义地在每个内部计算步骤重复检查。

### 4.2 结局判定流程

1.  收集当前世界状态、主角状态、关键人物关系、已发生事件和重要选择。
2.  筛选满足触发条件的结局模板。
3.  按优先级、专属条件和互斥规则确定结局。
4.  若没有专属结局命中，使用模板定义的普通/兜底结局。
5.  生成结局类型、标题、摘要和叙事内容。
6.  固化最终状态与结局记录。
7.  将结果交给独立 Evaluation 模块。

若多个结局同时满足，必须有明确且可测试的优先级/决胜规则。默认不依赖随机数决定关键结局，除非模板显式配置随机判定。

### 4.3 结局模板结构

  字段                 说明
  -------------------- ------------------------------------
  endingId             结局模板唯一 ID
  name / description   结局名称与说明
  triggerConditions    触发条件
  priority             多个结局同时满足时的优先级
  endingType           成功、失败、普通、隐藏、特殊等类型
  narrativeConfig      叙事所需变量、摘要与生成指引
  visibility           是否隐藏及解锁条件
  exclusiveGroup       互斥组
  fallback             是否为兜底结局

建议支持多个候选结局、隐藏结局、互斥结局和默认结局。结局模板只负责选择和描述结局，不负责计算人生评价。

### 4.4 结局叙事约束

结局内容可以来自： - 模板预设文本。 - 模板变量填充。 - LLM
基于本局记录生成叙事。

若使用 LLM： - 输入必须包含已确认的事件、人物关系和最终状态。 -
不得擅自创造未发生的关键事实。 - 不得修改游戏状态或补写不存在的选择。 -
输出应经过结构校验，失败时回退到模板文本/变量填充。

## 五、人生评价系统 Evaluation

### 5.1 与结局系统分离

结局与人生评价是两个独立结果： - 结局描述最终命运和关键结果。 -
人生评价衡量整个过程及其影响。

不能因为成功结局就自动给高评价，也不能因为死亡或失败结局就自动给低评价。人生评价需要综合过程记录，而不只是读取最终属性面板。

### 5.2 通用评价维度

首版建议提供以下通用维度，模板可增删、改名或调整权重：

  维度   评价内容
  ------ ------------------------------------------------
  成就   目标完成、能力成长、事业与重要里程碑
  人际   亲密关系、友谊、家庭、信任及影响过的人
  幸福   主观满足、生活质量、重要愿望实现情况
  影响   对社会、组织、世界或他人造成的长期影响
  道德   行为选择及其后果，不简单压缩为善恶二元值
  遗憾   未完成目标、失去的人、错过的机会和未解决的问题

模板可以增加世界观专属评价维度，例如守护、探索、知识、名望、自由等。

### 5.3 评价输入

建议综合以下数据： - 最终角色与世界状态。 -
关键事件、重大选择及其后果。 - 目标完成情况。 -
人物关系变化及最终关系状态。 - 角色成长轨迹与重要经历。 -
对世界、组织和其他人物的长期影响。 -
结局类型（作为背景信息，不直接决定分数）。

### 5.4 评价输出

建议输出： - 总体评价或等级（可选，不应取代分项）。 -
各维度得分/等级及解释。 - 关键成就与重要关系总结。 -
主要贡献、遗憾和未竟之事。 - 人生总结文案。 - 评价依据：关联事件
ID、选择记录或状态变化，便于解释和调试。

### 5.5 评分与叙事职责

建议采用"规则计算 + AI 总结"的分工： -
分数/等级由确定性规则或可解释评分器计算。 -
维度权重、评分区间和解释规则由模板配置。 - LLM
负责将评价依据组织成自然语言总结，不负责凭空决定分数。 -
评价结果必须能够追溯到事件、选择或状态变化。 - Evaluation
完成后归档，本局不再接受普通模拟状态修改。

## 六、核心数据边界与状态流转

建议生命周期状态：

`CREATED → OPENING → RUNNING → ENDING → EVALUATING → ARCHIVED`

关键数据建议分离： - `OpeningTemplate`：世界观提供的开局定义。 -
`OpeningRun`：本局开局执行进度和选择记录。 -
`EndingCondition`：模板定义的终止条件。 -
`EndingTemplate`：模板提供的结局定义。 -
`EndingRecord`：本局最终命中的结局及其依据。 -
`EvaluationConfig`：模板定义的评价维度、权重和规则。 -
`EvaluationRecord`：本局评价结果及其证据。 -
`EventDefinition`：模板中的原始事件定义。 -
`EventInstance`：本局实际生成/执行的事件实例。

以上是逻辑边界，不要求首版每项都拆成独立数据库表或 npm
包。可以按现有项目的数据存储方式实现。

### 6.1 生命周期关键约束

1.  Opening 完成前，不进入正常轮次模拟。
2.  Opening 生成的事件必须进入统一事件系统。
3.  Ending
    命中后，停止接收普通模拟行动；必要的当前事件结算完成后再固化最终状态。
4.  Ending 只确定结局，不计算人生评价。
5.  Evaluation 只读取模拟记录和最终状态，不修改结局。
6.  Archive 保存可回顾的完整记录。
7.  每次阶段切换都应有日志，便于测试和恢复。

## 七、建议测试用例

  --------------------------------------------------------------------------------------------
  测试场景                            验证重点
  ----------------------------------- --------------------------------------------------------
  同一世界观不同开局                  多个 OpeningTemplate 能初始化不同角色/地点/背景

  固定开局 + 随机事件                 固定步骤不变，随机事件受条件、权重和 Seed 控制

  开局事件链                          开局事件能生成后续事件并正确交接模拟

  开局互斥事件                        互斥组避免矛盾事件同时出现

  多终止条件同时满足                  Ending 优先级和决胜规则稳定

  无专属结局命中                      正确进入兜底结局

  隐藏结局                            解锁条件和可见性正确

  玩家主动结束                        模板允许时可结束，不允许时不能绕过规则

  事件结算中触发结束                  按配置在结算边界终止，不产生半更新状态

  结局与评价独立                      相同结局可得到不同人生评价；不同结局也可能得到相近评价

  评价可追溯                          每个维度的评价能关联到事件/选择/状态证据

  LLM 输出异常                        结构校验失败时回退，不污染最终状态
  --------------------------------------------------------------------------------------------

建议用咒术回战验证剧情开局、人物关系和战斗结局；用 Steins;Gate
验证时间穿越后未来事件重置、世界线结局和人生评价差异；用现代人生模拟器验证年龄/人生阶段、长期目标和多维人生评价。

## 八、下一轮迭代建议

### P0：先审查，不直接重构

-   阅读现有代码、Spec 和数据结构。
-   检查是否已有开局、结局、评价相关实现。
-   输出模块差距、耦合点和最小改造建议。
-   确认 Lifecycle 与 Turn/Event/Time Engine 的接口边界。

### P1：生命周期骨架

-   实现 Lifecycle 状态流转。
-   定义 Opening、Ending、Evaluation 的模板接口。
-   增加阶段切换日志与基础测试。

### P2：开局模板

-   实现开局步骤配置。
-   实现开局事件池抽取。
-   实现主角/NPC/关系/世界状态初始化。
-   将开局事件交给统一事件栈和未来事件队列。

### P3：结局与评价

-   实现可配置终止条件。
-   实现结局模板筛选、优先级和兜底。
-   实现独立的人生评价维度与可追溯评分。
-   实现结局叙事和人生总结的模板化/LLM 适配。

### P4：跨模板测试与打磨

-   为咒术回战、Steins;Gate、现代人生模拟器分别配置开局、终止条件、结局和评价。
-   验证模板差异只通过配置/适配器表达，不要求修改核心引擎。
-   补齐回归测试与模板校验。

## 九、交给 Coding Agent 的任务说明

请先阅读现有项目代码和已有 Spec，不要直接重写工程。

1.  对照本文检查 Opening、Ending、Evaluation
    是否已有实现，输出差距分析。
2.  检查开局/结局/评价是否被错误耦合，尤其不能将结局类型直接映射为人生评分。
3.  检查开局事件是否复用 Event
    Engine，是否能交接给事件栈与未来事件队列。
4.  给出最小可行的模块接口、数据结构和实施顺序。
5.  先更新 Spec
    并等待/遵循项目既定开发流程，再逐步实施；不要擅自大规模重构。

实现约束： - 开局和结局都必须模板化。 -
开局兼具固定流程和事件池随机性。 - 不要求预先编排完整剧本。 -
结束条件由模板定义，支持多条件组合和明确优先级。 -
结局与人生评价必须分离。 - 评价应基于整个模拟过程且可追溯。 - LLM
负责叙事组织，不得擅自改变模拟事实或确定评分。 -
不要为生命周期模块重复实现事件、时间或条件判定能力。 -
不要为了逻辑拆分而过度拆包。

**本轮目标不是一次性做出复杂的结局演出，而是先建立可配置、可测试、可扩展的生命周期骨架。**
