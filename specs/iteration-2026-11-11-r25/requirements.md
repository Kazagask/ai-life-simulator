## 1. 功能需求

### 1.1 分层模型（`R-LM`）

> 现状（盘点，仅作验收背景，不写入实现细节）：NPC 死亡由模板手写 flag（如 `gojoAlive=false`）表达，属于把**实例状态塞进配置命名空间**；事件模板定义、运行期链状态与已发生触发痕迹之间没有明确分层。

**R-LM-01（普遍）** 系统应当把模板与运行期数据划分为三层并各司其职：**配置**（模板定义，加载后只读）、**实例**（运行期实体状态，可被结算写回）、**事实**（已发生记录，只追加）；任何一条运行期数据应当归属且仅归属其中一层。

- 验收：Given 加载完成的模板，When 结算任意轮次，Then 模板对象内容不变（加载后只读保障，逐字段比对）；Given 任意一次状态变更，Then 该变更落在实例或事实之一，不写回模板。
- 追溯：`USR-总述`｜依赖：无

**R-LM-02（非期望行为）** 如果引擎需要记录系统内部状态（NPC 存活、事件链进度、队列条目等），系统应当使用**实例字段**表达，不得写入模板 flag 命名空间；flag 命名空间保留给模板自定义叙事状态。

- 验收：Given 模板未声明任何 flag，When NPC 死亡 / 链推进 / 事件入队发生，Then 世界状态出现对应实例字段变化且 flag 集合不变；Given 引擎做生命周期判定，Then 判定输入不包含 flag。
- 追溯：`USR-总述`（现状 flag 混杂是本轮重构动因之一）｜依赖：`R-NP-02`

**R-LM-03（普遍）** 事实应当只追加：已发生记录（历史、触发痕迹）一经写入，不得被任何后续结算修改或删除；调度判定可以**只读**事实作为输入（冷却、once 等），调度结果不得反向改写事实。

- 验收：Given 一局推进 N 轮，Then 每条事实记录自写入起在后续快照中逐字段不变；Given 调度器依据触发痕迹判定冷却，Then 痕迹本身无任何变化。
- 追溯：`USR-总述`｜依赖：无

**R-LM-04（普遍，配置层边界）** 模板定义属于配置层，但系统应当允许世界初始化时把模板声明的**规则实例化**（例如 NPC 刷新规则 → `SpawnRuleInstance`），后续事件效果可依规则实例生成 NPC 实例（`unspawned → alive`）并只追加 spawn 事实；**运行时不得生成新的配置层模板定义**。若确需按 seed 派生新定义，须满足确定性（禁用 `Date`/随机/LLM）、不参与模板指纹、且先写 ADR。

- 验收：Given 模板声明刷新规则，When 世界创建完成，Then 状态中出现对应规则实例且可序列化、模板逐字段不变；Given 事件效果 `spawnNpc(ruleId)` 结算，Then 生成 NPC 实例 + 一条只追加的 spawn 事实，且 spawn 不由「已有某事实」自动触发；Given 运行时尝试写模板定义，Then 被拒绝。
- 追溯：`USR-评审`（2026-11-12「配置层只是yaml吗？…我们要考虑世界初始化的时候，可以生成一些模板吗？比如初始化后定义npc刷新规则，后续事件会触发spawn？」）｜依赖：`R-LM-01/02`、`R-NP-02`；更强形式见 `OQ-#46`

**R-LM-05（普遍，时间标量精度）** 世界时间应当以**整数分钟**（`number`）表示；无限期时间窗用 `undefined` + 显式 `hasEnd` 标记表达，**不得使用数值哨兵**。**【2026-11-12 第二批裁决 #45：保持现状、下期决策】** 本轮**不加** `MAX_WORLD_TIME = 2^52` 上界拒载、**不加** `{epochIndex, minuteInEpoch}` 双字段/BigInt，`worldTime` 维持现状（number 分钟）；本轮验收口径收缩为「**整数分钟 + `hasEnd` 无数值哨兵**」。上界校验与年号/纪元 `CalendarAdapter.format` 渲染随 #39/#43 下一期（R2.6）首批一并验收。

- 验收（收缩后口径）：Given 时间量或 `worldTime` 非整数，When 加载或推进，Then 拒绝并给出可诊断错误；Given 无 `window.end` 的实例，Then `hasEnd = false` 且排序视为 +∞、与极大世界时间不冲突（无数值哨兵共域）；Given 一个「几亿年」尺度的世界，Then 分钟整数仍精确（加 1 分钟无误差）。**本轮不验收数值上界拒载与年号/纪元渲染**（顺延下一期 R2.6）。
- 追溯：`USR-评审`（2026-11-12「时间系统按分钟算，那几亿年尺度的洪荒世界怎么办？会超出精度限制」「时间系统为什么只做公历？」）｜依赖：`R-LM-01`；核查见 `design.md` §3.5；`#45` 裁决见 `design.md` §0.3

### 1.2 事件模型（`R-EV`）

> 现状（盘点）：触发来源四种 `pool` / `chain` / `schedule` / `action-hook`；`schedule` 支持 `atTurn`（x 轮后）与 `atWorldTime`，**无队列**，每轮遍历全部模板事件判到点；`firedEvents` 只记 `turnIndex`；链 `ChainStateV2 { stepIndex, status }`，链步 `advanceWhen: nextTurn | onSettle`。

**R-EV-01（普遍，基线重申）** 每个轮次是一个槽位，只能承载一次事件**或**玩家自由行动，二者不并存。**【2026-11-11 用户补充裁决】随机事件同样是事件，也占一个轮次**——随机事件由服务端结算、随轮次结果返回，前端在通用事件区呈现（见 `R-EV-11`）。

> 现状已实现；本条作为重构不变量保留，防止队列化改造破坏槽位语义。

- 验收：Given 一局推进任意多轮，Then 任一轮的结算产物至多包含一个玩家选项事件或一次自由行动，从不同时出现。
- 追溯：`USR-一-总则`｜依赖：无

**R-EV-02（普遍）** 事件触发应当二分为**立即触发**与**延时触发**；立即触发事件**不入队**。**【2026-11-12 用户裁决】立即/延时的判据是「是否声明时间窗」，不是 `source` 类型**：`action-hook` 保留旧名（不改名），它既可以立即触发也可以延时触发；`chain` 步骤声明 `delay` 时同为延时；`schedule`/`pool` 恒为延时。

- 验收：Given `action-hook` 或 `chain` 事件**未**声明 `window/delay` 而被触发，Then 该事件不产生延时队列条目；Given `action-hook` 事件声明了 `window/delay`，Then 行动命中后产生一条延时队列实例并按窗口到期触发；Given `schedule` 或 `pool` 来源的事件，Then 任何时点不以立即触发形式占据轮次槽位。
- 追溯：`USR-一-总则` + `USR-评审`（2026-11-12「action-hook 别改名 他可能是立即触发 也可以时延时触发」）｜依赖：无
- 追溯：`USR-一-总则`「事件触发分为立即触发延时触发两种」+ `USR-一-允许`｜依赖：`OQ-#34`（呈现时点）

**R-EV-03（状态驱动）** 同一轮次至多产生一个立即触发事件（槽位唯一前置约束），该约束在**模板协议层**表达。**【2026-11-12 第二批裁决 #35 关闭】采用候选①「加载期静态拒绝」（`superRefine`）**，并显式豁免延时事件——**只统计「未声明 `window`/`delay` 的立即 `action-hook`」并按 `onActionId` 分组，同组 ≥2 条才报错**；声明了 `window`/`delay` 的 `action-hook`（延时）、`chain` 延时步、`schedule`、`pool` 全部不受此约束（理由：延时事件不占同一轮槽位）；错误信息须提示「可为后续 hook 声明 window/delay 转为延时」。关联 Q-R25-01 已关闭。

- 验收（#35 裁决 + 延时豁免）：Given 同一 `onActionId` 挂 1 条立即 + N 条声明 `window/delay` 的延时 `action-hook` 的模板，When 加载，Then 加载合法（延时不受约束）；Given 同一 `onActionId` 挂 2 条均未声明 `window/delay` 的立即 `action-hook` 的模板，When 加载，Then 报错且错误信息提示「可为后续 hook 声明 window/delay 转为延时」；Given 同一 `onActionId` 全为延时 `action-hook`，Then 加载合法；Given 构造的同一轮两条可立即触发事件，Then 实际占据轮次槽位的立即触发事件 ≤ 1。（三组加载期用例详见 `tasks.md` T1-01 DoD。）
- 追溯：`USR-一-原则`「前置定义槽位唯一」｜依赖：`OQ-#35`（已关闭）

**R-EV-04（事件驱动）** 当事件为延时触发时，系统应当按其时间窗口的**开始时间**入队；模板可以声明固定时间段（绝对起止），也可以声明相对时间（如「3 天后」），相对时间在**入队时换算**为绝对窗口；换算基准待决（`OQ-#37`）。

- 验收：Given 声明固定时间段 [T1, T2] 的延时事件，When 入队，Then 队列条目窗口为 [T1, T2]；Given 声明「3 天后」的事件在世界时间 W 入队，Then 队列条目窗口按分钟标量换算（3 天 = 43200 分钟）且换算结果可复现。
- 追溯：`USR-一-原则`「按绝对时间窗口开始时间入队」「模板可以写固定时间段 也可以写相对时间 如3天后 入队自定换算」｜依赖：`OQ-#37`

**R-EV-05（普遍）** 延时队列出队排序应当为三键稳定排序：窗口开始时间升序 → 结束时间升序（结束时间为空视为最大）→ 入队默认顺序（同键先入先出，不得重排）。

- 验收：Given 队列中开始时间相同、结束时间各异（含空）的多条事件，When 出队，Then 顺序为开始 asc、结束 asc（空最后）、同键按入队序；Given 两次相同输入的入队序列，Then 出队序列一致（可回放）。
- 追溯：`USR-一-原则`「排序具体优先级：开始时间asc＞结束时间asc（为空视为最大）＞入队默认顺序」｜依赖：`R-EV-04`

**R-EV-06（状态驱动）** 当延时事件到达出队位置时，系统应当**在出队时刻**做触发判定（条件等在出队时求值）；入队不等于触发。

- 验收：Given 条件在入队时不满足、出队时满足的延时事件，When 到达其窗口，Then 触发；Given 条件在入队时满足、出队时不满足，Then 不触发。
- 追溯：`USR-一-原则`「出队时做触发判断」｜依赖：`R-EV-04`

**R-EV-07（普遍）** 系统应当允许多个延时事件同时入队，并在同一窗口内相继出队，不因同窗多条而丢弃或合并。**【2026-11-12 第二批裁决 #36 关闭】采用候选②「留在队列」**：窗口内 `conditions`/`cooldown` 不满足一律 **hold 留队、每轮 drain 重估、不记错失**；仅当 `worldTime > window.end` 才出队并追加 `reason="window_expired"` 的错失事实；无 `window.end` 永不因时间过期，由显式 `missWhen` 兜底（R-EV-12/#42）；门控失败不构成错失。

- 验收：Given 同一窗口入队 3 条延时事件，When 依次出队，Then 3 条均完成出队判定（各自触发或按窗口到期规则处置），无静默丢弃；Given 窗口内 `conditions`/`cooldown` 不满足的事件，Then 留队、每轮 drain 重估且 `missedEvents` 零新增；Given `worldTime > window.end` 仍未触发的事件，Then 出队并追加 `reason="window_expired"` 错失事实；Given 无 `window.end` 且未声明 `missWhen` 的事件，Then 永不因时间过期出队；Given 门控失败的事件，Then `missedEvents` 零新增。
- 追溯：`USR-一-原则`「可以有多个事件同时入队」｜依赖：`R-EV-05`、`OQ-#36`（已关闭）

**R-EV-08（普遍）** `schedule` 事件应当在**世界初始化时**即全部入队；`pool` 保持当前「最后触发」的管线位置不变，且 pool 抽中的事件**只能触发延时事件**（抽中 → 延时入队，不得立即呈现）。**【2026-11-12 裁决】** pool 须先经 `probability/weight/once/priority/conditions` **入队门控**决定是否入池；无时间窗口时默认相对 0 分钟（仍走队列）；`OQ-#38` 关闭。

- 验收：Given 含 schedule 事件的模板，When 世界创建完成（第 0 轮结算前），Then 全部 schedule 事件已在延时队列中；Given pool 抽中且门控通过的事件，Then 该事件进入延时队列而非当轮槽位；Given 无 `delay/window` 的 pool 事件被抽中，Then 实例 `window.start = 抽中时刻` 并在下一次 drain 触发；Given 门控失败（once 已触发/概率未中/条件不满足），Then 不产生队列实例、**不产生错失记录**。
- 追溯：`USR-一-其他` + `USR-评审`（2026-11-12「入池要看上面那些策略 判断是否入池」「入池如果没有时间窗口呢？」）｜依赖：无

**R-EV-09（非期望行为）** 如果模板声明无法换算为绝对时间窗口的触发形式（`atTurn`「x 轮后」），系统应当在加载期拒绝并提示改用固定时间段或相对时间；`atTurn` 自本规格起退役。

- 验收：Given 含 `atTurn` 的模板，When 加载，Then 报错且错误信息指明字段与替代写法；Given 全部触发形式改为时间窗口的模板，Then 加载成功。既有模板需同步迁移（迁移属实现批任务，不在本规格展开）。
- 追溯：`USR-一-原则`「退役掉无法计算时间的事件触发形式 如x轮后触发」｜依赖：无

**R-EV-10（状态驱动）** 当判定事件链断裂（后续步无法推进）时，系统应当先检查延时队列中是否仍有该链的待出队条目；队列中仍有该链条目时不得判定断裂。

- 验收：Given 链的后续步作为延时事件尚在队列中，When 执行断裂判定，Then 结果为「未断裂」；Given 队列无该链条目且后续步已不存在，Then 判定断裂（断裂后处置沿用现有链语义，不新增）。
- 追溯：`USR-任务书`（与 `USR-一-原则` 的队列化改造配套）｜依赖：`R-EV-04`、`R-EV-05`

**R-EV-11（普遍，槽位呈现契约）** 随机事件也是事件，同样占据一个轮次槽位：服务端在轮次结果中直接返回其结算（转盘结果），玩家端在**通用事件区**呈现——该区域即轮次槽位的可视化，正常事件、随机事件、战斗与自由行动共用，一个轮次只呈现一个占位者。

- 验收（呈现部分，已实现）：Given 一轮内随机事件被触发并结算，Then 轮次结果携带 `wheelResult`，前端事件区以转盘揭示（扇区面积按权重等比），确认「继续」后槽位让位于下一个占位者；Given 同轮还有待决事件/战斗，Then 转盘优先呈现、确认后再呈现后续占位者（puppeteer 端到端 + 截图证据，见 `tasks.md` T0-10）。
- 验收（记账部分，随 T1-07）：Given 随机事件结算轮，Then 该轮的槽位记账按「被随机事件占用」处理（具体呈现时点口径随 `OQ-#34`）。
- 追溯：`USR-补充`（2026-11-11「随机事件也是事件 他应该也占一个轮次…三种事件 行动 都该在这里」）｜依赖：`R-EV-01`、`OQ-#34`

**R-EV-12（事件驱动，错失机制）** 当延时事件的**触发前提永久失效**时（即使该事件没有时间窗结束期限），系统应当将其判为**错失**并出队，不得无限留队；错失判定依据模板显式声明的 `missWhen` 谓词（与 `conditions` 同一条件 DSL），引擎不得隐式推断依赖关系；每次错失应当在事实层追加一条含**错失原因**（封闭枚举，【2026-11-12 修订】仅 `window_expired / miss_when` 两种，可附模板声明的人类可读标签）的记录。**门控类策略失败不构成错失**：`once`/`probability` 等在入队前已消费，失败时不产生实例，故不出现 `once_fired` / `probability_failed` 原因。

- 验收（按 `OQ-#42` 推荐口径 ①「到期出队时判定」书写，用户 2026-11-12 默认通过）：Given 事件声明 `missWhen: [npcState dead]` 且无 `window.end`、其指向的角色死亡，When 该事件首次到期出队，Then 该实例终局为未触发、事实层新增一条 `missedEvents` 记录（`reason = "miss_when"`，`label` 透传模板声明），且延时队列不再含该实例；Given 同 seed 同输入回放，Then 错失判定与记录逐字段一致（missWhen 为纯条件求值，无 RNG 消耗）；Given 未声明 `missWhen` 且无 `window.end` 的事件，Then 行为不变（条件不满足时留队）；Given 门控失败的事件，Then `missedEvents` 零新增。
- 追溯：`USR-补充`（2026-11-12 错失机制 + miss 原因）｜依赖：`R-EV-04/06`、`R-LM-03`；设计见 `design.md` §3.4.1

**R-EV-13（普遍，pool 与战斗解耦）** `kind: combat` 的事件不得作为 `pool` 来源入池；系统应当在加载期拒绝 `source: pool` + `kind: combat` 的模板并给出替代写法；想要战斗应当声明 `normal` 或 `random` 事件入池，再由该事件经 `chain` 立即步 / `nextEventId` **立即触发战斗**。

- 验收：Given 含 `source: pool` + `kind: combat` 的模板，When 加载，Then 报错且提示「用通常事件/转盘事件再触发战斗」；Given 一条 `normal` pool 事件通过链步骤指向 `combat` 事件，Then 结算后战斗会话建立并占该轮槽位。
- 追溯：`USR-评审`（2026-11-12「战斗事件限制入池了吗？我倾向是你想做 加一个通常事件或者转盘 这个事件再去立即触发战斗」）｜依赖：`R-EV-08`

**R-EV-14（状态驱动，结算轮）** 事件结算应当**推进轮次并占用该轮槽位**：`chooseOptionV2`/转盘确认后 `turnIndex += 1` 且本轮不允许自由行动；战斗结束同样算一次结算轮；用物品/装备穿脱**暂不**算结算轮。事件轮的 `worldTime` 增量由事件级 `timeCost`（TimeSpec，**缺省 0**）决定，缺省时只占槽不耗时；事件轮仍执行完整轮次管线（NPC 行动、pool 抽取、schedule drain）；同一窗口出队的多条事件**逐轮各占一槽**呈现。

- 验收：Given 一轮内事件被结算，Then `turnIndex` +1、该轮不再接受自由行动、`pending_event_required` 守卫按槽位语义生效；Given 事件 `timeCost` 缺省，Then `worldTime` 不变；Given `timeCost: 2h`，Then `worldTime` 增加 120 分钟；Given 战斗结束，Then 推进一个结算轮；Given 用物品，Then 不推进；Given 同窗 3 条到期事件，Then 连续 3 轮各呈现一条。
- 追溯：`USR-补充`（2026-11-12「事件结算我一直是以为会推进轮次的」「可以 加timeCost 战斗结束算结算轮，用物品先不算」，`OQ-#34` 裁决）｜依赖：`R-EV-01`、`R-EV-07`

**R-EV-15（普遍，配置域边界）** `probability/weight/once/priority/conditions/onActionId` 应当始终属于**配置层模板只读字段**：引擎只在候选产生/入队门控与条件求值时读取定义现值，不得把这些字段复制进事件实例、待决队列条目、`flags` 或存档；判定可以读取运行时状态（`firedEvents`/`turnIndex`、玩家/NPC 状态、注入 RNG、运行时 `actionId`），但字段本身的唯一来源是 `EventTriggerSchema`。

- 验收：Given 任一存档或 `scheduledEvents` 实例，Then 不含上述六字段的副本（静态扫描 + schema strict 断言）；Given 模板上这些字段被修改，Then 已入队实例在下次门控/出队判定时读到的是定义现值而非旧副本；Given 门控失败，Then 不产生实例也不写事实层。
- 追溯：`USR-评审`（2026-11-12「probability / weight / once / priority / conditions / onActionId 查一下消费链路 看起来像是配置领域的」）｜依赖：`R-LM-01`；核查证据见 `design.md` §0.2 #4

### 1.3 NPC 系统（`R-NP`）

> 现状（盘点）：NPC 无生命周期字段；`isEnemy` 与 `visibility: public|hidden` 并存；年龄为静态 int；关系仅 `relationship` 单值（-100..100）。

**R-NP-01（普遍）** 前端能否看到某个 NPC 的信息以及该 NPC 产生的事件，应当由 **NPC 投影原则**决定，与 NPC 的生命周期状态解耦；开局已死亡的重要角色也应当在面板可见。**【2026-11-12 第二批裁决 #41 关闭】采用候选①「合并」**：`visibility: public|hidden` 并入该投影原则的**单一判定入口 `projectNpc()`**，不再与动态已知标记各设一套判定；历史条目可见性 `R-VS-03` / `isPlayerVisible()` 口径不变。ADR-0012 决策 3「保留 visibility 静态闸并 AND 组合」与 Q-R25-07 的 A 案按此改写（合并 ≠ 简单 AND 两套并存）。关联 T2-03。

- 验收：Given 一个开局即为 dead 的模板重要角色，When 请求玩家端投影，Then 该 NPC 的面板信息可见（可见字段范围由投影原则决定，不因 dead 而消失）；Given 同一 NPC 分别处于 alive 与 dead，Then 投影可见性判定结果相同（可见性判定不读取生命周期字段）；Given `visibility` 与动态已知标记，Then 二者经 `projectNpc()` 单一入口判定、不存在并行的第二套判定；Given 历史条目，Then 可见性仍按 `R-VS-03` / `isPlayerVisible()` 口径、不因合并改变。
- 追溯：`USR-二-1`｜依赖：`R-NP-02`（先有三段生命周期，才有「与生命周期解耦」可验）；`#41` 裁决见 `design.md` §0.3、ADR-0012 决策 3

**R-NP-02（普遍）** 每个 NPC 应当具有完整生命周期 `spawn → alive → dead`；该生命周期应当用于决策：NPC 生成原则、行动环节是否跳过、是否触发事件、是否参加战斗；上述判定**默认判活**，模板无须书写判活条件。

- 验收：Given 任意 NPC 实例，Then 生命周期取值 ∈ {spawn, alive, dead} 且可从快照观测；Given dead NPC，When 轮次管线执行 NPC 行动环节，Then 跳过该 NPC；When 匹配战斗对手，Then 默认不选择 dead NPC；Given dead NPC 挂接的行动/事件，When 判定，Then 默认判活不通过、不触发。
- 追溯：`USR-二-2`｜依赖：`R-LM-02`

**R-NP-03（非期望行为）** 引擎的 `dead` 不承载业务解释：如果模板需要表达「失联」「隐退」等业务语义，应当由模板把该业务事件映射为 `dead`（引擎层面失联即 dead）；引擎不得为业务语义另设第二套存活判定。

- 验收：Given 模板将「失联」事件效果映射为 dead，When 该事件结算，Then NPC 生命周期转为 dead 且 `R-NP-02` 的全部判活行为生效；Given 引擎做存活判定，Then 判定输入只有生命周期字段，不读取任何业务语义字段。
- 追溯：`USR-二-2`「不和业务语义耦合，如失联也是dead」｜依赖：`R-NP-02`

**R-NP-04（普遍）** NPC 实例应当记录**出生时间**而非静态年龄；年龄应当在读取时按当前世界时间动态计算，且应当支持**三种时间模型**（具体枚举待决 `OQ-#39`；未决前实现不得锁死单一时间模型）。

- 验收：Given 出生时间 B 与世界时间 W，Then 任何年龄读取点输出为 B 与 W 的函数（动态），世界时间推进后同一 NPC 的年龄读取值随之增长且可回放；Given `OQ-#39` 决议后的三种时间模型配置，Then 年龄计算按配置切换且各模型下结果确定。
- 追溯：`USR-二-3`「年龄字段要动态计算，npc上挂的是出生时间，要支持三种时间模型」｜依赖：`OQ-#39`

**R-NP-05（普遍）** NPC 关系应当类型化：至少内置**亲属**、**朋友**、**师徒**三类并支持模板自定义类型；现有好感度（-100..100）作为独立维度保留，与关系类型分离并存，互不覆盖。

- 验收：Given 一个 NPC，Then 其关系数据可同时表达关系类型与好感度数值，二者互不覆盖；Given 模板声明自定义关系类型，Then 该类型可被记录与投影（本轮仅要求类型字段可扩展，不定义机制内容）。
- 追溯：`USR-二-4`「不应该只有好感度，还有亲属，朋友，师徒，模板自定义关系」｜依赖：无

**R-NP-06（事件驱动）** 当 NPC 实例记录了双亲或师父时，系统应当据此**推导**出亲属关系与师承关系（记录「因」推导「果」，与年龄同理：记录出生事实、推导年龄）；亲属与师承两类推导逻辑内置写死，推导算法允许复用成熟开源方案（**【2026-11-12 已裁决】分层复用，见 `R-NP-08` 与 `design.md` §4.5**）。

- 验收：Given NPC 记录双亲，Then 与双亲的亲属关系可推导查询，无需模板逐条手写；Given NPC 记录师父，Then 师徒关系可推导查询；Given 同一实例数据，Then 推导结果确定性可复现（同输入同输出）。
- 追溯：`USR-二-4`「亲缘关系、师承关系应当也是和年龄一样 通过记录师父，双亲来推导出来……直接找开源解决方案复用」｜依赖：`R-NP-05`

**R-NP-07（可选特性）—— DEFERRED** 自定义关系类型的通用 yaml 模板机制：用户将另行提供该机制；本轮只保留 `R-NP-05` 的类型扩展点，不定义机制内容、不展开验收、不派任务。

- 追溯：`USR-二-4`「后续我会做一个通用yaml模板机制」｜依赖：`R-NP-05`

**R-NP-08（事件驱动，断代与多跳称谓）** 关系推导应当支持**谱系不完整**：当只知道祖先、中间代数缺失时，系统应当以显式「断代」标记表达未知跳数，输出粗称谓或模板声明的标签，**不得猜测代数、不得伪造中间节点**；对于已知跳数的多跳亲属路径，系统应当能推导出中文称谓（如叔伯、舅公、甥外孙）；师承多跳称谓由模板 `titleRules` 声明。实现采用**分层复用**：图遍历/环检测/断代/师承自研确定性与离线可用，中文亲属称谓由成熟开源库 `relationship.js`（MIT、零运行时依赖、纯查表确定性）承担，引入前按 AGENTS.md §0 走 ADR。

- 验收：Given NPC 只声明「某祖先」且中间断代，Then 推导结果带 `gap: true`、辈分数字不可编造、称谓为粗称谓/模板标签；Given 完整多跳亲属链，Then 输出正确中文称谓且同输入同输出；Given 师承链长 3，Then 称谓按模板 `titleRules` 解析；Given 库不可用/被禁用，Then 退化为结构边 + 模板标签，不阻断模拟。
- 追溯：`USR-评审`（2026-11-12「辈分/谱系 如果中间不完整怎么办？…后续能把多跳称谓推导出来吗？真的没有成熟的库吗？」）｜依赖：`R-NP-05/06`；调研证据见 `design.md` §4.5、`OQ-#40` 已关闭
