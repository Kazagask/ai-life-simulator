## 一、项目总体设计原则

本项目是一个基于世界观模板驱动的 AI 人生模拟器。

核心目标：

1. 支持不同世界观快速接入。
2. 通过轮次、事件、人物自主行动推动模拟。
3. AI 负责动态内容生成，但不应成为每轮运行的必要条件。
4. 核心模拟逻辑尽量确定性、规则化。
5. 世界观差异通过模板和配置解决，而不是修改核心引擎。

技术原则：

- Node.js / TypeScript 技术栈。
- PWA 优先，后续考虑 H5、小程序。
- 尽量采用 Spec Coding。
- AI 编写大部分代码，优先保证模块边界清晰。
- 避免过度工程化，MVP 阶段不引入不必要的微服务。
- 核心逻辑与世界观数据彻底解耦。

## 二、时间系统

### 2.1 核心原则

轮次与游戏世界时间解耦。

不建立统一 Tick 系统，也不要求所有世界观使用统一时间单位。不同世界观可以拥有完全不同的时间表达方式，例如：

- 咒术回战：年、月、日。
- Steins;Gate：具体日期、时间。
- 奇幻世界：年号、季节、月份。
- 人生模拟器：年龄、人生阶段。

时间类型由世界观模板定义。核心引擎只负责调用世界观提供的时间适配器，不负责理解具体时间结构。

### 2.2 时间推进

不采用每轮固定推进一天的方式。事件可以自行指定时间推进目标：

- 短时训练：推进 3 小时。
- 长期修炼：推进 30 天。
- 剧情节点：直接推进到指定剧情日期。

### 2.3 时间穿越

预留时间穿越支持。穿越后需要处理未来事件：

1. 已经发生的事件保留，并记录实际发生日期。
2. 检查当前时间之后的未来事件。
3. 删除或撤销未来事件的执行状态。
4. 主角、亲友、重要 NPC 的未来事件转为隐秘状态。
5. 后续根据新的世界状态重新触发相关事件。

注意区分：

- 已经发生的事件记录。
- 尚未发生的事件实例。
- 世界观模板中的原始事件定义。

原始事件定义应当保留，不能因时间穿越而删除。

## 三、主线与事件系统

### 3.1 事件驱动 + 栈式执行

主线不应当是一条完全固定的剧情列表，采用事件驱动机制。

初步设计：

- 事件进入主线时入栈。
- 当前事件处理完成后出栈。
- 根据事件结果生成后续事件。
- 新事件可以继续入栈。
- 支持事件链和分支。

事件栈只是执行调度结构，不应成为唯一的事件存储。事件需要有独立 ID、状态、时间、来源和关联关系。

### 3.2 事件类型

| 类型 | 说明 |
|---|---|
| 主线事件 | 世界观预设的重要剧情 |
| 随机事件 | 根据规则和概率触发 |
| 动态事件 | AI 根据当前状态生成 |
| NPC 事件 | NPC 自主行动产生 |
| 玩家事件 | 玩家选择产生 |
| 时间事件 | 到达指定时间触发 |
| 条件事件 | 满足特定条件后触发 |

### 3.3 动态事件链

AI 不需要每轮介入，而是通过规则和概率决定是否触发动态事件。

触发条件可以包括：

- 人物属性、人物关系、当前事件、世界状态。
- NPC 行动、玩家行为、特殊条件。
- 世界线变化、随机概率。

动态事件可以生成后续事件，形成事件链。例如：

玩家拒绝帮助某 NPC → NPC 关系恶化 → NPC 私下寻求其他人的帮助 → 其他 NPC 获得信息 → 产生新的冲突事件。

动态事件必须能够影响后续模拟状态，而不只是生成一段文字。

## 四、NPC 自主行动系统

NPC 自主行动需要独立模块设计。但出于性能和 AI 调用成本考虑，不能让所有 NPC 每轮都执行行动。

### 4.1 行动触发机制

采用事件驱动，而不是全量轮询。触发因素可以包括：

1. 重要事件发生。
2. NPC 关系发生变化。
3. NPC 自身目标发生变化。
4. NPC 所在地点发生变化。
5. 特定时间到达。
6. 玩家行为影响 NPC。
7. 随机行动触发。

NPC 行动需要支持优先级和触发概率。

### 4.2 NPC 行动决策

每个 NPC 应具有：

- 人物属性、性格。
- 当前目标、长期目标。
- 人物关系、所处位置。
- 已知信息、隐秘信息。
- 当前状态。

行动决策不依赖 LLM。根据 NPC 的目标、状态、关系和环境，使用规则系统选择行动。

可采用效用评分：

**行动评分 = 目标匹配度 + 性格偏好 + 当前环境影响 + 关系影响 + 随机因素**

选出合适行动后执行。避免为每个 NPC 单独编写一套 AI。

### 4.3 行动结果

NPC 行动可以产生：

- 属性变化、关系变化、位置变化。
- 信息获取、信息传播、隐秘变化。
- 新事件，以及其他 NPC 的行动触发。

特别注意信息差：NPC 不应该自动知道整个世界发生的事情。每个 NPC 都应该有独立的信息认知范围。

## 五、战斗与行动 AI

这里的 AI 指游戏内部 NPC 决策算法，不是 LLM。需要区分普通行动决策与战斗策略决策。

### 5.1 战斗决策因素

- 当前生命值、当前资源。
- 攻击能力、防御能力。
- 技能效果、对手状态。
- 双方距离、战斗阶段。
- 战斗目标、性格与战斗风格。

### 5.2 分层决策策略

1. **规则约束**：检查技能条件、行动合法性、特殊状态等。
2. **行动候选集**：普通攻击、技能攻击、防御、闪避、恢复、逃跑、特殊行动。
3. **策略评分**：根据当前战况计算每个行动的收益。
4. **选择行动**：选择评分较高的行动，并加入适当随机性。
5. **执行与结算**。

不同 NPC 通过配置拥有不同战斗风格，例如激进型、保守型、防御反击型、技能优先型、逃避型。避免为每个 NPC 单独编写一套 AI。

## 六、战斗属性系统

采用通用基础属性 + 世界观自定义属性。

### 6.1 通用基础属性

| 属性 | 作用 |
|---|---|
| HP | 生命值 |
| ATK | 攻击力 |
| DEF | 防御力 |
| SPD | 速度 |
| HIT | 命中 |
| EVA | 闪避 |
| CRIT | 暴击率 |
| CRIT_DMG | 暴击伤害 |
| RES | 抗性 |

资源属性独立配置，例如 MP、灵力、咒力、体力、魔力。不同世界观不一定需要所有属性。

### 6.2 基础计算公式

- 基础伤害 = 攻击力 × 技能倍率
- 实际伤害 = max(最小伤害, 基础伤害 - 防御减伤)
- 暴击后伤害 = 实际伤害 × 暴击倍率
- 命中概率 = 基础命中 + 命中修正 - 闪避修正

最终结果需要限制在合理区间。以上作为默认公式，具体数值和曲线应可配置。

### 6.3 扩展机制

世界观可以：

- 增加自定义属性。
- 覆写基础属性计算公式。
- 覆写伤害公式。
- 增加特殊资源、特殊状态。
- 自定义属性之间的关联。

核心引擎提供默认实现，世界观模板可以覆盖。不要将咒力、查克拉等概念硬编码到核心引擎。

## 七、装备系统

装备系统采用通用装备模型，装备类型由模板定义。

### 7.1 装备栏

不固定装备栏数量和名称。世界观可以定义武器、防具、饰品、特殊装备及自定义装备栏。

例如：

- 咒术回战：咒具、防护装备、特殊道具。
- 奇幻世界：主武器、副武器、头部、身体、饰品。

### 7.2 装备数据

建议包含：

- 装备 ID、名称、类型、品质。
- 基础属性、特殊效果。
- 装备限制、世界观标识、自定义字段。

装备属性通过统一属性系统影响角色。特殊装备效果通过效果系统实现，不要在核心引擎中针对具体装备写死逻辑。

## 八、架构与组件化建议

### 8.1 核心模块边界

建议划分为：

1. Game Core：游戏状态与核心数据。
2. Turn Engine：轮次管理。
3. Time Engine：时间适配与推进。
4. Event Engine：事件管理与调度。
5. Character System：人物属性与状态。
6. NPC System：NPC 自主行动。
7. Relationship System：人物关系。
8. Information System：信息差与隐秘。
9. Combat System：战斗结算。
10. Combat AI：战斗策略。
11. Equipment System：装备管理。
12. World Template：世界观模板。
13. AI Adapter：LLM 调用及动态内容生成。
14. Evaluation System：人生评价。

### 8.2 组件化建议

优先组件化真正具有复用价值的模块：

- 时间适配器。
- 事件调度器。
- 属性计算器。
- 效果系统。
- 条件判定器。
- 随机数服务。
- NPC 决策器。
- 战斗计算器。
- 世界观模板加载器。

MVP 阶段不建议拆成多个独立 npm 包。采用 Monorepo 或清晰的模块化目录即可。只有当模块具备独立版本管理、独立复用需求时，再考虑抽成独立 Package。

### 8.3 架构约束

- 核心引擎不能依赖具体世界观。
- 世界观模板不能直接修改核心引擎内部状态。
- 模块之间通过接口交互。
- 属性、时间、事件类型尽可能配置化。
- 所有重要状态变化需要可追踪。
- 随机数最好支持 Seed，便于复现测试。
- AI 生成结果必须经过校验才能进入游戏状态。

## 九、测试剧本

测试不能只使用咒术回战，建议使用不同特征的世界观测试扩展性。

| 测试模板 | 重点验证 |
|---|---|
| 咒术回战 | 战斗、技能、属性、装备、人物关系 |
| Steins;Gate | 时间穿越、世界线变化、事件回滚、信息差 |
| 火影忍者 | 成长、修炼、师徒、组织、长期剧情 |
| 现代人生模拟器 | 年龄、人生阶段、职业、随机事件、人生评价 |
| 西幻 RPG | 装备、属性扩展、魔法、职业、战斗 |

其中 Steins;Gate 是重要的架构测试用例，重点验证：

1. 世界线变化率。
2. 世界线与事件发生概率的关联。
3. 事件收束机制。
4. 时间穿越。
5. 未来事件状态重置。
6. 不同人物对世界线变化的认知差异。

如果核心框架能够支持这些机制，说明模板化设计具备较好的扩展能力。

不要一次性把所有模块全部实现，建议分阶段推进。

- 时间系统。

### P2：战斗系统

## 十一、交给 Coding Agent 的执行要求

请先阅读现有项目代码和已有 Spec，不要直接重写工程。

### 第一部分：架构审查

对照本文检查现有实现：

- 哪些模块已经实现？
- 哪些模块部分实现？
- 哪些模块尚未实现？
- 哪些设计存在耦合？
- 哪些地方需要重构？

先输出架构差距分析。

### 第二部分：设计落地

优先补齐：

- 时间系统。
- 事件系统。
- NPC 自主行动系统。
- 属性扩展机制。
- 装备系统。

设计需要与现有代码兼容。不要为了追求理论上的完美架构引入过多抽象。

### 第三部分：实施

按照 P0 → P4 顺序推进。每个阶段：

1. 更新 Spec。
2. 实现代码。
3. 编写单元测试。
4. 验证现有功能没有回归。
5. 更新技术文档。

特别要求：

- 不要擅自改变已经确定的产品设计。
- 不要将 LLM 用于普通 NPC 每轮行动决策。
- 不要强制所有世界观使用统一时间 Tick。
- 不要将事件栈设计成唯一的事件存储。
- 不要将世界观专属属性写死在核心引擎。
- 不要过度拆分 Package。
- 不要在没有评估现有实现的情况下大规模重构。

**最终目标：建立一个轻量、可扩展、可复用的 AI 人生模拟器核心框架。**

## 十二、特别提醒

先做架构审查和差距分析，不要立即修改代码。所有新设计必须优先考虑能否通过现有模块扩展实现。

最值得优先验证的测试模板是 Steins;Gate：咒术回战主要验证战斗和人物系统，而 Steins;Gate 能同时检验时间系统解耦、事件回滚、信息差、动态事件与世界线联动，以及模板是否真正能够改变核心规则。
