## 一、项目总体设计原则

本项目是一个基于世界观模板驱动的 AI 人生模拟器。

核心目标：

1. 支持不同世界观的快速接入。
2. 通过轮次、事件、人物自主行动推动模拟。
3. AI 负责动态内容生成，但不应成为每轮运行的必要条件。
4. 核心模拟逻辑尽量确定性、规则化。
5. 世界观差异通过模板和配置解决，而不是修改核心引擎。

技术原则：

- Node.js / TypeScript 技术栈。
- PWA 优先，后续考虑 H5、小程序。
- 尽量采用 Spec Coding。
- AI 编写大部分代码，优先保证模块边界清晰。
- 避免过度工程化，MVP 阶段不引入不必要的微服务。
- 核心逻辑与世界观数据彻底解耦。

## 二、时间系统

### 2.1 核心原则

轮次与游戏世界时间解耦。

不建立统一 Tick 系统，也不要求所有世界观使用统一时间单位。

不同世界观可以拥有完全不同的时间表达方式。

例如：

- 咒术回战：年、月、日。
- Steins;Gate：具体日期、时间。
- 奇幻世界：年号、季节、月份。
- 人生模拟器：年龄、人生阶段。

时间类型由世界观模板定义。

### 2.2 时间推进

不采用每轮固定推进一天的方式。

事件可以自行指定时间推进目标。

例如：

玩家进行一次训练：

- 时间推进：3 小时。

玩家进行一次长期修炼：

- 时间推进：30 天。

玩家进入一段剧情：

- 时间直接推进到指定剧情日期。

核心引擎只负责调用世界观提供的时间适配器，不负责理解具体时间结构。

### 2.3 时间穿越

预留时间穿越支持。

穿越后需要处理未来事件：

1. 已经发生的事件保留，并记录实际发生日期。
2. 检查当前时间之后的未来事件。
3. 删除或撤销未来事件的执行状态。
4. 主角、亲友、重要 NPC 的未来事件转为隐秘状态。
5. 后续根据新的世界状态重新触发相关事件。

注意：不能简单删除所有未来事件定义，需要区分：

- 已经发生的事件记录。
- 尚未发生的事件实例。
- 世界观模板中的原始事件定义。

原始事件定义应当保留。

## 三、主线与事件系统

### 3.1 核心思路：事件驱动 + 栈式执行

主线不应当是一条完全固定的剧情列表。

采用事件驱动机制。

初步设计：

- 事件进入主线时入栈。
- 当前事件处理完成后出栈。
- 根据事件结果生成后续事件。
- 新事件可以继续入栈。
- 支持事件链和分支。

这样可以实现：

- 主线事件。
- 支线事件。
- 随机事件。
- AI 动态事件。
- NPC 行动产生的事件。
- 事件嵌套和连续剧情。

需要注意：事件栈只是执行调度结构，不应该成为唯一的事件存储。

事件需要有独立 ID、状态、时间、来源和关联关系。

### 3.2 事件类型

建议至少支持：

| 类型 | 说明 |
|---|---|
| 主线事件 | 世界观预设的重要剧情 |
| 随机事件 | 根据规则和概率触发 |
| 动态事件 | AI 根据当前状态生成 |
| NPC事件 | NPC 自主行动产生 |
| 玩家事件 | 玩家选择产生 |
| 时间事件 | 到达指定时间触发 |
| 条件事件 | 满足特定条件后触发 |

### 3.3 动态事件链

这是项目的重要特色。

AI 不需要每轮介入，而是通过规则和概率决定是否触发动态事件。

触发条件可以包括：

- 人物属性。
- 人物关系。
- 当前事件。
- 世界状态。
- 世界线变化。
- NPC 行动。
- 特殊条件。
- 随机概率。

动态事件可以生成后续事件，形成事件链。

例如：

玩家拒绝帮助某 NPC
→ NPC 关系恶化
→ NPC 私下寻求其他人的帮助
→ 其他 NPC 获得信息
→ 产生新的冲突事件。

动态事件必须能够影响后续模拟，而不只是生成一段文字。

## 四、NPC 自主行动系统

NPC 自主行动需要独立模块设计。

但出于性能和 AI 调用成本考虑，不能让所有 NPC 每轮都执行行动。

### 4.1 行动触发机制

采用事件驱动，而不是全量轮询。

NPC 行动可以由以下因素触发：

1. 重要事件发生。
2. NPC 关系发生变化。
3. NPC 自身目标发生变化。
4. NPC 所在地点发生变化。
5. 特定时间到达。
6. 玩家行为影响 NPC。
7. 随机行动触发。

NPC 行动需要支持优先级和触发概率。

### 4.2 NPC 行动决策

每个 NPC 应具有：

- 人物属性。
- 性格。
- 当前目标。
- 长期目标。
- 人物关系。
- 所处位置。
- 已知信息。
- 隐秘信息。
- 当前状态。

行动决策不依赖 LLM。

根据 NPC 的目标、状态、关系和环境，使用规则系统选择行动。

必要时可以采用效用评分

## 附录 A：与现行规格的差异与对齐清单（整理者注，非原文）

> 以下为 2026-11-11 落盘时对照现行规格（`specs/engine/CORE_ENGINE.md` V0.1、`specs/data/TEMPLATE_PROTOCOL_V2.md`、ADR-0001）整理的冲突与待决项。**在 ADR 明确之前，实现方不得单方面按本文推翻现行规格。**

| # | 主题 | 本增量说明 | 现行规格/实现 | 状态 |
|---|---|---|---|---|
| A1 | 内部时间表示 | 不建立统一 Tick；时间类型由模板定义；引擎只调时间适配器 | CORE_ENGINE V0.1：`WorldTime` 以分钟/统一整数 tick 表示；V2 协议 `time` 沿用 `TimeAmount` 统一单位 | **冲突，需 ADR**：是否废弃统一分钟模型、改为「模板自带 CalendarAdapter」；影响 `WorldState.worldTime`、`schedule` 事件、所有时间比较条件 |
| A2 | 时间推进目标 | 事件/行动可指定推进量或目标日期 | V1/V2 仅支持行动 `duration` 覆盖步长；无「推进到指定日期」 | **增量扩展**：需新增推进模式（相对量 / 绝对目标时间），绝对目标依赖 A1 的适配器 |
| A3 | 时间穿越 | 预留穿越：区分已发生记录 / 未发生实例 / 模板原始定义，未来事件撤销或隐秘化 | 无此概念；`once`、`cooldownTurns`、事件链状态机均假设时间单调递增 | **新需求（P1+）**：需事件实例（instance）与定义（definition）分离的存储模型；影响快照/事件日志结构，建议单独立规格 |
| A4 | 主线执行结构 | 事件栈式执行（入栈/出栈/嵌套），栈只是调度结构，事件独立存储 | V2：事件池（每轮条件筛选）+ chains 线性状态机 + `nextEventId` 选项链 | **部分冲突**：栈可作为 chains/nextEventId 之上的统一调度层；需明确与 chain 状态机的关系，避免两套调度并存 |
| A5 | 事件类型 | 主线/随机/动态/NPC/玩家/时间/条件七类 | V2 trigger.source 四类（pool/chain/schedule/action-hook）+ kind（normal/random/combat） | **大体兼容**：七类可映射为 source 的新增枚举（mainline/dynamic/npc）；NPC 事件依赖 §4 的 NPC 行动模块 |
| A6 | NPC 行动节奏 | 事件驱动触发，非全量轮询；触发源 7 种 + 优先级/概率 | CORE_ENGINE V0.1：每轮 schedule NPC 行动；V2 未实现 NPC 自主行动 | **方向调整**：需将「每轮轮询」改为「触发式调度 + 兜底随机」；NPC 决策仍规则化（效用评分可选），与 AGENTS.md「NPC 只用自身 knowledge」一致 |
| A7 | 多世界观时间表达 | 年月日 / 具体日期 / 年号季节 / 年龄阶段 | V2 world.yaml 仅 `startYear` + `TimeAmount` | **依赖 A1**：模板需可声明历法结构（年号、季节、纪年映射）供投影展示 |
