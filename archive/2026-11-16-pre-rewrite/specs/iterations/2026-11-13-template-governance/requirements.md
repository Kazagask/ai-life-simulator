> 状态列：**ACTIVE** 进本轮 DoD；**DEFERRED** 只登记不实现；~~RETIRED~~ 编号保留、原文保留、内容作废。
> 编号 `R-TG-*` 不重排、不复用；砍掉的标 RETIRED，不删号。
> **本文件为「砍板」后重写（2026-11-13 第二次收窄）：导入能力整体 RETIRED，范围收敛为「只做读 + 直接改服务端文件 + 运行时热加载」。**

## 0. 本轮基线（主理人裁决 R1–R4，权威，不再讨论方向）

用户原话（逐字）：

> 再砍一板需求 只做读 能选就行 砍掉前端导入模板的口子 但是可以直接改服务端文件 服务端能在运行时热加载就行 运行时丢模板导致报错可容忍（基本不会这么做）

| # | 裁决 | 落地到 |
|---|---|---|
| **R1 目录布局** | `specs/data/templates/<id>/<version>/`；内置 `jjk-2006` 迁入 `jjk-2006/1.0.0/`。语义指纹只拼 `文件名 + "\0" + 内容`（**不含路径**）⇒ 迁移不改指纹 ⇒ **现存可载旧档数量不减少**（实测基线见 §2 注） | R-TG-01 / R-TG-15 |
| **R2 身份来源** | **id = 目录名**，version = 版本子目录名（`^\d+(\.\d+){0,2}$`）。**取消服务端生成 `tpl-` id**——没有导入后「防作者自报撞车」的威胁模型消失（放文件的人就是运维自己） | R-TG-01 |
| **R3 热加载语义** | 请求驱动 + 内存快照隔离。触发：`resolve`/`listTemplates` 前 `ensureFresh()` 比对 mtime，变了才重扫该目录；**不启动定时器、不用 `fs.watch`**。生效：只影响新建世界与后续载入；已载入内存的世界持有自己的 `{state, template, lookup, entry}` 快照。失败：单模板隔离 + 日志，**运行期绝不 fail-fast**（启动期仍 fail-fast） | R-TG-16 |
| **R4 取消 `_meta.json`** | 目录结构即元数据：version 取目录名，id 取上一级目录名 | R-TG-01 |

**失败哲学随之改写**：不再是「内置 fail-fast / 导入隔离失败」，而是 **「启动期 fail-fast / 运行期隔离失败」**——两个时点，不是两个信任域。

> **两处对裁决的实现层收窄（细化，不改裁决方向）**——`design.md` 已按此写，实现前必须知道，否则会照旧口径写出相反的代码：
> 1. **R3 触发比对**：从「目录 mtime」细化为「**版本目录内所有文件 mtime 的最大值**（顶层 `*.yaml` + `assets/**` 递归）」，并明令**不得用目录 mtime 代替**——就地编辑一个已存在的文件**不会改变其父目录 mtime**，只 stat 目录会漏掉最常见的那种改动，也就是 R-TG-16 AC① 要验的场景。裁决本体（请求驱动、无定时器、无 `fs.watch`）不变；成本上限 ≤ 43 次 `stat`/请求。
> 2. **R1 指纹输入**：从「目录内全部 `*.yaml`」收紧为「**根上白名单内 11 个 `declarative` yaml**」，游离的非白名单 yaml（如 `notes.yaml`）**不参与指纹**。理由：现状 `computeFingerprint` 用 `filter(f => f.endsWith(".yaml"))`，加一个备注 yaml 就会砖掉全部旧档，而它在加载期本就被忽略——**被忽略的东西不该有让存档失效的权力**。「只拼文件名不含路径」不变 ⇒ 迁移不改指纹；对当前模板**零影响**（实测 `jjk-2006` 恰好只有这 11 个、无游离 yaml）。**实施提醒**：这不是沿用旧代码，`computeFingerprint` 的过滤条件必须改；且 design 侧 `H-2.1`（怎么算）与 `C-3`（载入判据）必须与 R-TG-15 一字不差——设计内部若一处写「只算 `*.yaml`」、另一处写「白名单」，实施方会照错的那处写出与 AC③ 相反的代码。

## 2. ACTIVE 需求正文（8 条，本轮 DoD 全集）

| 编号 | 类型 | 需求（EARS） | 验收标准（AC） |
|---|---|---|---|
| **R-TG-01** | Ubiquitous | 系统**应**把模板身份定义为「`id` = 模板目录名 + `version` = 版本子目录名（匹配 `^\d+(\.\d+){0,2}$`）」，二者组合唯一；**不得**由服务端生成 id，**不得**从 yaml 或任何清单文件读取 `version`。选择流程**应**为「先模板 → 后版本」两级 | ① 磁盘为 `specs/data/templates/<id>/<version>/`，内置 `jjk-2006/1.0.0/`；② `GET /api/templates` 返回 `[{ id, name, versions: [{ version, startYear, openings[] }] }]` 两级结构；③ 版本目录名不匹配 `^\d+(\.\d+){0,2}$` ⇒ 加载期报错（见 R-TG-04）；④ `world.templateId ≡ 目录名`，yaml 内 `meta.id` 不参与身份判定；⑤ **迁移不变量**：`jjk-2006/*.yaml` 移入 `jjk-2006/1.0.0/` 后 `semanticFingerprint` 逐字节相同 ⇒ **可载旧档数量不减少** |
| **R-TG-04** | Unwanted | **若**启动期任一模板版本目录加载失败（yaml 语法错 / Zod 校验失败 / **`meta.id` ≠ 目录名** / 版本目录名不合 `^\d+(\.\d+){0,2}$` / `specs/data/templates/` 下一个模板都没有），**则**服务应拒绝启动，**不得**降级为「跳过该目录」。**空版本目录（`<version>/` 内无任何 `*.yaml`）不算模板**：**应**忽略 + `warn`，**不得**触发 fail-fast | 逐个构造五种失败 ⇒ 进程非 0 退出，日志含目录名与 Zod 字段路径（**第 4 类不区分目录内是否为空**：`v2/` 与空的 `beta/` 都拒绝启动——空目录豁免只给「名字合法」的版本目录）；**反例①**：服务起来了但列表少一个模板 ⇒ 不通过；**反例②**：只 `mkdir 1.1.0` 还没拷 yaml 就重启 ⇒ 服务起不来 ⇒ 不通过（这是本轮唯一的工作流） |
| **R-TG-08** | Event-driven | **当**世界创建或从磁盘载入时，系统**应**把模板引用（`templateId` + `templateVersion` + `templateFingerprint`）写入/固化进存档信封，作为**不可变事实**；此后 `persist` **不得**查全局指纹表、**不得**改写该三元组 | ① 建局后替换或删除该版本目录，再触发一次 `save` ⇒ 信封三元组逐字节不变；② `store.ts` 内 `getTemplateFingerprint` 零命中（grep 断言）；③ 缺 ref ⇒ 抛 `template_ref_missing`（500），**不得**回落 `sha256:unknown` 占位符；④ 缺 `templateVersion` 的旧档按「该 id 仅注册 1 个版本且指纹相等」唯一性推断并回填，回填前后 `state` 深比较相等 |
| **R-TG-10** | Unwanted | **若**存档绑定的模板或版本不可解析，**则**系统应拒载并给出**封闭**原因码（`envelope_json_invalid` / `envelope_schema_version_unsupported` / `template_missing` / `template_version_missing` / `template_version_ambiguous` / `template_invalid` / `template_content_drift` / `world_state_invalid`）；**判定顺序写死「先定版本、再比指纹」**。世界列表**应**区分「可载 / 存在但不可载」，`GET /api/worlds/:id` **应**返回 409 `world_unloadable` + `reason`，**不得** 404、**不得**静默消失（修 E-03） | ① **四种缺模板形态各一例** ⇒ 列表可见 + 带对应 `reason` + 允许删除不可载世界：`template_missing`（`<id>` 目录没了）/ `template_version_missing`（版本目录没了）/ `template_invalid`（目录在但加载失败）/ `template_version_ambiguous`（该 id 有 ≥2 版本且信封无 `templateVersion`）。**其中 `template_invalid` 是防御分支：真实世界载入路径不可达**（启动期 fail-fast 先行、运行期对已载入版本保留旧 Entry），**不作为验收用例、不得据它设计文案**；若哪天变得可达（如放开运行期 invalid 回退），须同步补用例。其余三形态必须有可执行用例；② 「2 个版本且都不匹配信封指纹」**必须**归 `template_version_ambiguous`，**不得**归 `template_content_drift`（到不了比指纹那一步）；③ `GET /:id` 返回 409 而非 404；④ **迁移不改变任何载入判定**：以固定夹具矩阵（4 格，见下表注 ④）断言**迁移后的逐格结果 = 迁移前记录的一次性基线**——正样本仍载入（含无 `templateVersion` 者仍能推断回填）、负样本仍按**同一判定**拒载。**「迁移前」列只作一次性留档、不得写成 CI 用例**；**负 2 的基线是 N/A**（旧 loader 不读 `templateVersion`，会载入成功，属预期差异）；**正样本「不变」只对 `state` 成立、不对整个信封**（回填会新增 `templateVersion`）。**正样本信封指纹须在 setup 时按当前版本目录实时计算，不得写死常量**；仅负 1 使用「故意不匹配」常量。**不得**从 `data/worlds` 任取样本；⑤ 原因码是**封闭枚举、无自由文本 code**，且每条失败必须**同时带「码 + 具体对象」**——哪个文件 / 哪个 `(id,version)` / 哪个字段路径；只报「载入失败」不算可诊断 |
| **R-TG-14** | Event-driven | **当**用户在开局页选择模板时，系统**应**先选模板、再选版本，并按**所选版本**展示与提交该版本的 `openings`；提交的 `openingId` **应**属于所选 `(id, version)` | ① 两模板 openings 不同 ⇒ 切换模板后下拉项随之变化；② 同模板两版本 openings 不同 ⇒ 切版本后随之变化；③ 提交不属于所选版本的 `openingId` ⇒ 400 且错误含允许集合；④ `main.tsx:680` 的 `templates[0]?.openings` 恒取首项缺陷消失（断言页面不再出现跨模板开局） |
| **R-TG-15** | Ubiquitous | 系统**应**按「文件角色」分类模板目录内每个文件并计算**分层指纹**：`semanticFingerprint` **只算版本目录根上白名单内 11 个 `declarative` yaml**（`world/characters/skills/items/statuses/events` + `equipment/combat-ai/opening/endings/evaluation`，只拼文件名不含路径）、决定可载性；**游离的非白名单 yaml 不参与指纹**（这是对现状的有意偏离：现状会把任何 `*.yaml` 算进指纹）。`assetFingerprint` 只算 `assets/**`、**只用于诊断**、无资源时取确定空集常量；`code` 角色（`.js/.mjs/.cjs/.ts/.jsx/.tsx/.wasm/.node/.so/.dll/.dylib/.exe/.bat/.ps1/.sh/.html/.htm/.svg`）与非 `declarative`/`asset` 的散落文件**应**在**加载期 warn 并忽略**，**不得**导致拒载。**指纹「怎么算」以本条为需求侧唯一权威**；design 侧**单点定义在 H-2.1**，C-3 允许复述但**冲突时一律以 H-2.1 为准**（实施方读到两个版本时不需要判断谁对，直接按 H-2.1 写）；「何时据此拒载」见 R-TG-10。若本条与 H-2.1 冲突，属缺陷，**按本条改 H-2.1，不得反向改本条去迁就实现** | ① 只改 `assets/` 内文件 ⇒ `semanticFingerprint` 不变、旧档仍可载；② 改任一**白名单** yaml ⇒ 语义指纹变、旧档 `template_content_drift`；③ **版本目录根上放一个游离 `notes.yaml` ⇒ `semanticFingerprint` 不变、旧档仍可载、日志 warn**（现状会变指纹并砖掉全部旧档，本轮必须不成立）；④ 无 `assets/` ⇒ `assetFingerprint` = `sha256:e3b0c442…b855`（非 `undefined`）；⑤ `GET /api/templates` 暴露 `assetCount`；⑥ 版本目录内放 `.js` / `.svg` ⇒ 加载成功 + `warn` 日志含文件名，模板仍可用；⑦ 根目录散落 `.wheel.json` / `.md` / `.png` ⇒ `warn` + 忽略，**不拒载**（旧口径为「拒绝」）；⑧ 服务端代码路径无 `eval` / `new Function` / `vm`（grep 断言）；⑨ **迁移不变量**：`jjk-2006/1.0.0/` 的 `semanticFingerprint` 与迁移前逐字节相同，即 `sha256:9a945ac31fd9fb10716714bd608127ac87c9b24212721dd44015a16b7aec27e0`。**① 前提（2026-11-13 已实测）**：该目录 11 个 yaml 全在白名单内、零游离，故「取全部 `*.yaml`」与「取白名单 11 个」同值 = 上述 hash，且 `data/worlds` 当时有 8 份档记录的就是这个值。**② 推论（只在「白名单文件内容不变」时成立）**：记录值 ≡ 白名单 hash ⇒ 新口径按白名单重算必然相等，**与目录里多了游离文件无关**；但**白名单里任一 yaml 被改，② 与①会同时变假**——那正是 `template_content_drift` 要检测的东西，**属预期行为，不是本条被推翻**。⚠️ **边界**：本条只证明「指纹不变」= 必要条件，不等于「旧档仍可载」——载入还要过 state schema / `templateVersion` 推断 / 目录扫描三道，任何一道坏了本条仍是绿的；「旧档仍可载」由 R-TG-10 AC④ 走真实 `loadPersistedWorlds` 路径实测承担，**两步都绿才算安全，禁止只测本条就宣布旧档没事** |
| **R-TG-16** | Event-driven | **当**一次 `resolve` 或 `listTemplates` 调用发生时，系统**应**先 `ensureFresh()`，比对每个 `<id>/<version>` 的「**该版本目录内所有文件的 mtime 最大值**」（顶层 `*.yaml` + `assets/**` 递归），**仅在变化时**重扫该版本并换入新 Entry；**不得**用版本目录自身的 mtime 代替；**不得**使用定时器或 `fs.watch`。热加载**只**影响新建世界与后续载入，已载入内存的世界**应**持有自身 `{state, template, lookup, entry}` 快照并保持不变。单个版本热加载失败**应**隔离（保留旧 Entry，无旧 Entry 则标 `invalid` + 日志），**不得**导致进程退出 | ① **就地改**某版本 `world.yaml` 的 `meta.name`（**不动目录、不增删文件**）不重启 ⇒ 下一次 `GET /api/templates` 反映新值——**这一条就是「不得用目录 mtime」的行为断言**，因为就地编辑不改父目录 mtime，用目录 mtime 实现则此条必红；② 已在跑世界推进一轮 ⇒ 快照逐字段不变、`POST /turns` 仍 200；③ 版本目录被改成非法 yaml ⇒ 该版本 `status:"invalid"` + 列表带 `reason`、其余版本正常、进程存活、日志含路径与首个 issue；④ 删除整个版本目录 ⇒ 列表不再列出，已载入世界仍可推进；⑤ 同 `(id,version)` 内容被改 ⇒ 新 Entry 生效于新建世界，旧世界仍用内存快照；**重启后**旧世界因指纹不符 ⇒ `template_content_drift`；⑥ 文件 mtime 未变时**不重扫**（连续两次 `listTemplates` 的重扫计数 = 0）；⑦ 代码内 `setInterval` / `fs.watch` 零命中（grep 断言）；⑧ 单次 `listTemplates` 的 `stat` 调用数 = 各版本文件数之和（当前 43），**不重解析 yaml**（计数断言）；⑨ **结构断言**：`ensureFresh()` 的实现路径中目录 mtime 不参与变更判定（grep 断言无「`readdir` 后直接 `stat` 目录」的写法；允许 `stat` 文件）。**已知局限（须写进文档）**：受 mtime 精度与竞态影响，最多**晚一次请求**才看到变更 |
| **R-TG-17** | Unwanted | 系统**不得**提供任何通过 API 新增、修改、删除、注册模板的端点；模板的增删改**只**经由服务端文件系统（**唯一**模板端点是只读的 `GET /api/templates`） | ① `POST /api/templates/imports`、`PUT` / `PATCH` / `DELETE /api/templates*` 全部 404 或 405；② 代码库内无 multipart 依赖、无导入 `bodyLimit` 配置、无 `LIFE_SIM_ENV` / `TEMPLATE_IMPORT_TOKEN` / `encoding`／`base64` 导入载荷（grep 断言）；③ 前端无上传控件 |

> **R-TG-10 为什么必须区分四种「缺模板」形态**（不可合并成一种）：`template_missing`（`<id>` 目录没了）/ `template_version_missing`（版本目录没了）/ **`template_invalid`**（目录在、但 yaml 坏了或 `meta.id` ≠ 目录名）/ `template_version_ambiguous`（≥2 版本且信封无 `templateVersion`）。
> 合并的代价是误导运维：`template_invalid` 若被报成 `template_missing`，运维会去查「目录怎么没了」，而目录好端端在那——**这正是热加载下最常见的一种失败**（改坏了 yaml，目录从未移动）。因此 R-TG-16 AC③ 允许「该版本标不可用」，就**必须**同时给出 `template_invalid` 这个原因码，否则 R-TG-10 AC⑤「原因码封闭且可诊断」自相矛盾。
> **但可达性不同，处置也不同**：`template_invalid` 在**真实世界载入路径上不可达**（启动期 failFast 先行 `throw`；运行期对已载入版本保留旧 Entry），故保留为**防御分支**、不作用例；而 `template_version_ambiguous` 是**真可达**分支（手放第二个版本目录即可构造），必须有验收用例。不要因为两者都「少见」就一刀切。

> **🔴 旧档份数不以绝对值为判据（2026-11-13 实测修正）**：历史文档长期写「**6 份**可载」，但实测 `data/worlds/` 现有 **65** 份存档（原记录 63 份），其中「`schemaVersion=2` 且指纹 = `sha256:9a945ac31f…ec27e0`」的有 **8 份**，而不是 6 份。
> 原因不是谁算错，而是**这个数字会自己长大**：`apps/server/smoke/cloud.smoke.mjs`「**每次新建世界**」（`PROJECT.md §8`），CI 的 L5 每跑一次冒烟就多一份带当前指纹的存档。
> 所以凡是把「6 份」写进 AC 的地方，QA 照做必然**误报失败**（实测已 8 份，只会继续增加）。
> **判据改为**：**不写死份数**——改用**固定夹具矩阵逐格比对**（见下条注 ④）；对 `data/worlds` 只做**全景统计**，不与历史数字比。基线（2026-11-13 快照，非断言）：65 份总数 / 8 份指纹匹配。

> **④ 的夹具矩阵（4 格）——为什么必须是矩阵，「一份样本」不够；以及「迁移前」列为什么不能进 CI**
> 单份夹具配「数量不减少」会**空转**：1 → 1 恒真（夹具没放对时 0 → 0 也是绿的），这条 AC 永远不失败，也就保护不了任何东西。4 格才让「迁移不改变判定」有内容：
>
> | 格 | 夹具 | 基线（迁移前，**一次性记录、不入 CI**） | CI 断言（迁移后，**永久**） |
> |---|---|---|---|
> | 正 1 | `schemaVersion=2` + **有** `templateVersion` | 载入成功 | 载入成功；`state` 深比较不变；信封 `templateId` / `templateFingerprint` 不变 |
> | 正 2 | `schemaVersion=2` + **无** `templateVersion`（走 C-2 唯一性推断） | 载入成功（旧 loader 不读该字段，行为同正 1） | 载入成功；`state` 深比较不变；信封**新增** `templateVersion`（回填），其余关键字段不变 |
> | 负 1 | 信封指纹 = **故意不匹配的常量** | 拒载（旧码 reason = `template_fingerprint_mismatch`） | 拒载 `template_content_drift`——**同一判定的重命名后继，不算回归** |
> | 负 2 | `templateVersion` 指向**不存在的**版本目录 | **N/A —— 旧 loader 无版本概念、会成功载入；这是预期差异，不是回归** | 拒载 `template_version_missing` |
>
> **三处必红点，写死防止 QA 照字面实现**：
> 1. **负 2 的基线必须记 N/A**：旧 loader 只有「`templateId` + 指纹」两道关，**根本不读 `templateVersion`** ⇒ 该夹具在迁移前会被**成功载入**，不是拒载。若要求前后同结果，这一格必红，且不是回归。
> 2. **负 1 只要求「同一判定」，不要求「同一条代码路径」**：迁移前是「世界级指纹 vs 全局指纹表」，迁移后是「`(id,version)` 可解析 + 语义指纹」——判据来源不同，只是当前模板下对同一夹具给出等价的拒载。**将来重构 C-3 不算破坏迁移等价性**，别把实现路径也锁进 AC。
> 3. **正 2 的「不变」只对 `state` 成立，不对整个信封**：回填会**新增** `templateVersion`。若断言「信封逐字段相同」，这一格必红。**正 1 同理，只断言 `state` 与两个关键信封字段，不写「信封逐字段」**。**`savedAt` 不属于任何不变量**——它表达「什么时候写过」，天然可变，写进判据等于断言「程序不许再保存」；`templateId` / `templateFingerprint` 表达的是「世界绑定到哪个模板」，才是不可变的那个东西。
>
> **上表「逐格相同」的适用边界 —— 迁移是「单向收紧」（源自 `design.md` G-1）**
> 新 loader 多了版本解析、指纹基准也换了，所以**迁移不是等价变换，是一次收紧**。方向写死：**「接受」不允许增加，「拒绝」允许增加**（fail-closed 才安全——误载等于让玩家看到一条伪人生）。
> - **可载性只增不减**：原本可载 ⇒ 迁移后必须仍可载（正 1 / 正 2）；
> - **拒绝允许增加**：原本**被误接受**的档，迁移后**允许**被拒载（负 2 就是这一类，故基线 N/A）；
> - **原因允许细分**：原本原因粗糙的，迁移后**允许**换成更精确的码（负 1 的 `template_fingerprint_mismatch` → `template_content_drift`）。
>
> **回归的判据（写死，否则 QA 只知道豁免、不知道红线）**：逐格比对是**列内纵向**（每格「迁移后 vs 该格基线」），不是格间横向。**只有以下四类才算回归**——
> 1. **原本被拒载的，现在被接受**（最危险：误载 = 玩家看到一条伪人生）；
> 2. **正样本载不进来**；
> 3. **任一格相对其自身基线的差异，无法归入「新增拒绝」或「原因细分」**；
> 4. **无基线的格（负 2）按「绝对期望」判定**：迁移后**必须**拒载且 `reason = template_version_missing`；**载入了即回归**。这类格**不与基线比对、也不适用「差异归类」**——它没有基线可 diff，若照第 3 条处理就会被读成「无差异 ⇒ 通过」而**空过**。
>
> **四类合起来才封闭**：前三类相对基线（误载 / 正样本失败 / 差异不可归类）+ 第四类绝对期望（无基线格）。缺第 4 类，负 2 永远是漏的。
>
> **正样本的信封指纹必须在 setup 阶段按当前版本目录实时算**（H-2.1 口径）**，不得写死常量**——写死则模板一改（本项目最高频动作）本条就假红，而「历史指纹该不该被接受」**本来就不是 AC④ 要测的东西**（那是 AC② 的事）。实时算 ⇒ AC④ 对模板改动**静默免疫**。**只有负 1 该用常量**，且须注明「故意不匹配」，避免后人当成抄漏的值。
>
> **「基线」列为什么不能做成 CI 用例**：按 B-1，迁移后 loader 只认 `<id>/<version>/`，旧平铺布局不再被支持——硬要在 CI 里长期对跑两种布局，等于**逼实现保留旧布局兼容，与 B-1 直接冲突**（一条 AC 把方案本身否掉）。所以拆成两件事，别混：
> 1. **基线 = 一次性证据（不是测试）**：`T-TG-10`（目录迁移）执行**前**，用真实目录跑一次 `loadPersistedWorlds`，把「几份可载 / 几份拒载及各自 reason」+ 上述 3 格基线结果记进交付报告留档。
> 2. **迁移后 = 可重复测试（CI 永久）**：上面矩阵的「CI 断言」列，逐格执行。
>
> 证明链：**基线（人手一次）→ 迁移 → 矩阵（CI 永久）**。没这一步澄清，QA 会以为表里两列都要跑，然后发现「基线」那一列根本跑不了。
>
> **与 AC② 的边界**：AC② 管「模板内容变了 ⇒ 应当拒载」，AC④ 管「迁移不该导致拒载」，**两者只在「模板内容未变」的前提下才不冲突**。正样本指纹 setup 时实时算 ⇒ AC④ 对模板改动免疫；负 1 的常量在模板改动后**仍应拒载，永不需更新**。
>
> **负样本两格尤其重要**：只测「能载」的矩阵无法证明「该拒的还在拒」，而 C-3/C-4 的全部价值就在**拒载可诊断**上——若只做正样本，一个「把指纹校验整个删掉」的实现也能让 AC 全绿。

## 5. 结论

**本轮 DoD 只含 ACTIVE 8 条**（R-TG-01 / 04 / 08 / 10 / 14 / 15 / 16 / 17）。RETIRED 9 条编号与原文保留、不进验收、不得复用；DEFERRED 项（模板市场 / owner / 审核 / 模板副本 GC / 监听文件式热加载 / zip / 资源下发 / 自定义函数执行 / 字节快照 / 存档上云 / 抗 YAML 别名炸弹）只登记不实现。

**🔴 需求级变更（必须传递给后端与 QA）**：因为砍掉导入，**`R-TG-15` 的 `code` 拒绝逻辑从「导入期拒绝」改为「加载期忽略 + warn」**。
- 旧口径：`code` 角色文件在导入时即被拒（`import_code_assets_not_supported`），坏包整包不进。
- 新口径：目录里混入 `.js` / `.svg` / `.exe` 或散落文件（如 `.wheel.json`）时，加载器**warn 并忽略该文件**，模板照常注册可用。
- 依据：没有导入端点后，「拒绝坏包」保护的是不存在的攻击者（放文件的人就是运维自己）；此时**拒载只会让运维自己改完文件却起不来服务**。
- 保留的红线：`eval` / `new Function` / `vm` 在服务端代码路径仍然**零命中**（R-TG-15 AC⑦），`code` 文件只是**不被读取**，不是「可以执行」。

**两条与裁决无关、可立即开工的**：R-TG-08（`persist` 现查全局表 ⇒ 静默改写旧档指纹，纯缺陷修复）与 R-TG-14（`main.tsx:680` 恒取 `templates[0]` 的存量缺陷）。
