# ADR-011 补正层数收敛、资源上限口径与战斗仪器

- 状态：已接受（2026-11-19）
- 关联：ADR-003（属性类型与自定义资源）、ADR-008（必中与闪避）、ADR-009（补正时长）、ADR-010（演员同构）、`BACKLOG.md` B-07
- 涉及：`packages/shared/src/schema/{status-effect,world}.ts`、`packages/shared/src/{v2,v2-state}.ts`、`packages/game-core/src/v2/{engine,battle,turn,sim}.ts`、`packages/game-core/src/index.ts`、`apps/server/src/cli/inspect.ts`、`apps/web/src/main.tsx`、`specs/data/templates/jjk-2006/3.0.0/{world,statuses}.yaml`、`test/unit/{adr-011,sim,world-tidings}.test.ts`

## 背景

三件互不相干、但都在同一个下午被同一组数字逼出来的事。

**一、`stacking: refresh` 没有独立语义了。** 它是因为「时长写在补正定义上」才存在的：`refresh` = 层数重置 + 时长重算，`stack` = 层数相加，`unique` = 不重复。ADR-009 把时长挪到施加点之后，每条补正的实例只剩一个 `expiresAt`，而**每次施加都自带时长**。于是：

- `refresh` 与 `unique` 的差别只剩「层数取新值还是取旧值」，在 `stacks: 1`（模板里 15 条 refresh 全是 1）时完全相同；
- `stack` 那条「层数相加但**不动**到期点」变成了明确的错误：第二次下毒按第一次的到期点算，读起来就是 bug。

**二、咒力有两个口径，而 MP 上限一半来自常数。** 属性 `cursedEnergy`（0..200）与资源 `mp`（面板也叫「咒力」）并存是对的：前者是「你有多强」，后者是「你还能放几发」。但上限公式是 `40 + 2 × 基础咒力`，那个 40 让「天与咒缚（零咒力）」拥有 40 点咒力池——一个语义上不成立的东西。用户裁决：**去掉 base，上限只由属性决定**。

**三、补正写负数，会一路算进命中骰。** 天与咒缚写 `attributeModifiers: { cursedEnergy: -8 }`（「出生时被拿走全部咒力」），开局选它的人基础咒力 5 ⇒ 有效咒力 **-3**；而有效属性链只有上界（`caps`），没有下界。负数会真的进命中判定与伤害公式，而面板上看不见（投影投基础值）。

**四、上面三条改完，没人知道数值还对不对。** 技能消耗、倍率、闪避、装备词条全汇进 `performBattleAction`，而这条链路只有真打一场才暴露问题（MP 够不够放第二发苍、无下限把命中率压到多少、天逆鉾该给多少）。手算一次就错一次。

## 决策

### D1 层数只有两档；再施加时**时钟的形态听这一次、数值只往后推**

`stacking` 收敛为 `stack | unique`：

| 档 | 层数（连施两次） | 时长 |
|---|---|---|
| `stack` | 相加（1+2 ⇒ 3） | 只增不减 |
| `unique` | 不动（1 ⇒ 1） | 只增不减 |

`refresh` 退役，模板里的 15 条全部迁移到 `unique`（`stacks` 恒为 1 ⇒ 语义无损）。

「再施加」拆成两个互不干涉的问题，这是本节的核心：

- **层数**由 `stacking` 决定。`stack` 累加（`absorbed-curses` 收集咒灵要能攒），`unique` 恒定（重复中毒不变成双倍毒伤，只是续期）。
- **时长**只有一个 `expiresAt`，而时长是「这一次施加」的属性，所以：**形态**听这一次（带时长 ⇒ 有时钟；挂载 / `untilCured` ⇒ 没有），**数值**只往后推（`max`）。

为什么数值必须取 `max` 而不是「最后一次说了算」：后者会让一次轻施加把长补正缩短。`grief`（丧失，长线情绪）剩 5 天，被一次新事件再施加 3 天 ⇒ 剩余时间从 5 砍到 3，「这件事会跟着你很久」被一句轻话抹掉。层数已经涨了、时间反而短了，读起来是坏的。缩短补正的正确手段是 `cureStatus`，不是「再施加一个更短的」。

已永久（挂载）的实例**不会被有期施加降级**：身份不是「一次施加」。

战斗域同一套：`roundsLeft` / `expiresAt` 各自取 `max`，时钟种类仍听这一次（`{rounds}` 与 `{value, unit}` 互斥，切换时钟时旧字段删掉）。迟到的一击必须能把「还剩 1 回合」推回「还剩 3 回合」——方向是延长，所以与「只增不减」同构。`battleOnly` 是「谁来清理」的标记而非时长，仍按这一次重写。

顺带修掉一处两域不一致：`unique` 的层数，模拟域是「锁在首次施加的值」（`Math.max(1, existing.stacks)`），战斗域曾是「可被更高层数抬上去」（`Math.max(existing.stacks, stacks)`）——同一个「重伤 ×2」在事件里与战斗里会得到不同层数。现统一为前者。

### D2 数值属性的有效值下限为 0

`effectiveAttributes` 在套完 `caps` 之后对所有数值键做一次 `< 0 ⇒ 0`。

理由：属性是**量**，「没有」与「欠着」在规则上是同一件事。补正可以写 `-8`（表达「拿走」），但负数不该出现在命中骰与伤害公式里——那会让「天与咒缚被术式打中时反而更准」这种荒谬结果成为可能。上限仍由 `caps` 管，下限不开放给模板配置（没有第二个合理取值）。

### D3 咒力上限只由咒力属性决定（模板侧）

`jjk-2006/3.0.0` 的 `resources.mp` 从 `{ base: 40, ... }` 改为 `{ base: 0, perLevel: 5, perAttribute: { cursedEnergy: 2 } }`。

- **不做 `cursedEnergy: -999`**。用户提出过这个写法（防止后续补正把上限加回来），但它会顺带打穿 HP：`hp = 75 + 5 × 基础咒力`，-999 ⇒ HP 夹到 1。而且**不需要**它：`computeMax` 读的是**基础属性**，补正只改有效值，所以「基础 0 ⇒ 上限 0」已经成立，唯一能让它回升的是显式 `adjustAttribute`（那是剧情事件，应当被允许）。
- 仍保留 `perAttribute` 系数 2，因此这是一次**真实的数值变化**：玩家开局（咒力 5）MP 从 50 掉到 10，而苍要 18。技能价必须重调——这件事交给 D4 的仪器去量，不再手算。
- `jjk-shinjuku/1.0.0` 不动（它是另一个世界，`base: 80`、系数 1，池子口径不同）。

### D4 战斗数值仪器：`pnpm inspect sim`

`packages/game-core/src/v2/sim.ts` + `inspect sim` 子命令。**它不是协议的一部分**，不进快照、不进存档、不改 `schemaVersion`。

关键约束：**不复写任何战斗规则**。模拟器只做三件事——建世界、摆对手、每回合挑技能——然后交给真实的 `performBattleAction`。所以报告里的数字就是玩家会遇到的数字；它证明的东西不是「模拟器算得对」，而是「战斗规则跑出来是这样」。

```
pnpm inspect sim --tpl jjk-2006@3.0.0 --as npc-gojo --dummy hp=5000,agility=8
pnpm inspect sim --tpl jjk-2006@3.0.0 --as npc-toji --vs npc-gojo --repeat 30
```

输出：胜率 / 平均回合 / 每回合输出与承伤 / 命中率 / 每局咒力消耗 / 技能使用分布。决策策略是「按期望伤害挑，血量过半以下才把治疗算进分数」——它只需要稳定、可解释、不随机；战术偏好应当体现为模板数值，而不是模拟器的聪明程度。

第一个发现（本轮实测）：**甚尔对五条 30 局 0 胜、0 伤害、1.1 回合被打死**。0 伤害是「无下限」正确工作（`evade: 1`，非必中碰不到），1.1 回合是「HP 只由咒力算」的后果（甚尔 HP 75 vs 五条 675）。两个都不是代码 bug，是**内容缺口**：前者要天逆鉾，后者要重新想「天与咒缚的人怎么算血」。

### D5 世界事实有自己的上屏出口：`tidings`

**问题**：事实不经过玩家，所以它拿不到「本轮收获」——五条悟 2007 年学会赫，玩家那回合可能只是在修炼。要让它上屏，今天只能写一个「只为了显示一句话」的事件，那是 DSL 被当排版用。

**做法**：`scheduledFacts[]` 增可选 `tidings`（**玩家可见**的一句话）。事实触发时写一条 `history`，类型新增 `world`（前端标签「世」，复用「碑」的样式）：

- `note` 与 `tidings` **严格分开**：`note` 是作者注（含「为什么写在时间表而不是事件」这类设计说明，直接上屏会穿帮），`tidings` 才会被原样当正文；
- 不写 `tidings` ⇒ 纯状态修改，不上屏（旧模板零改动，行为不变）；
- 走 `history` 而不是新增响应字段 ⇒ 前端零改动（编年史本来就会渲染），也不需要动 `TurnGain` 的形状。

这一条**没有解决**「多线兼容语法」的整体问题（一个事件要同时服务高专 / 五条 / 诅咒师三种站位，条件与选项仍然靠手写组合）。它只补了一个具体缺口：**世界单方面发生的事，不该为了上屏而被写成一个事件**。

### D6 范围外：战斗面剩下的四件事（后续一轮一起做）

这四件都需要协议增量，且互相咬合，所以不在本 ADR 里半做：

| 项 | 要什么 | 备注 |
|---|---|---|
| 装备授予技能（天逆鉾「必中」） | `equipment.grantsSkill` + 技能侧免费复用 `hit: guaranteed` | 道具目前只能给属性词条，给不了行为；走技能是最短链路 |
| 消耗修正（六眼 MP -90%） | `combat.mpCostMultiplier`（累加），`cost = ceil(base × max(0, 1 + Σ))` | 要同时改 `missingCost` / `payCost` / AI 筛选 / 展示；取整规则必须显式 |
| 召唤 | 战斗内新增单位 | 与「胜负判定」耦合 |
| 胜负条件 / 中立单位 | `settle.combat` 扩展 | B-07 魔虚罗四机制的前置 |

明确**不做**乘法面（`attributeMultipliers`）：天与咒缚用「基础属性 0」表达比乘法干净，乘法只会把「上限该不该跟着动」这个坑再挖一遍。

## 验收

- `pnpm test`：69 文件 / 471 例全绿（新增 `adr-011` 5 例、`sim` 4 例、`world-tidings` 2 例）。
- `pnpm inspect check`：error 0 / warn 7（与基线同）。
- `inspect sim --as npc-gojo --dummy hp=50000,agility=8`：单发苍的伤害 = `(18 + 140×0.9) × 1.3 ≈ 187`，由 `sim.test.ts` 断言。
- `inspect sim --as npc-toji --vs npc-gojo`：伤害 0、命中 0%——`battle-hit-evade` 的结论在整局尺度上仍然成立。
- 事实到点 ⇒ 编年史多一条 `world`，文案取自 `tidings`（不是 `note`），且同一事实只写一次。

## 后果与风险

- **玩家开局 MP 从 50 变 10**（咒力 5）。技能价（苍 18 / 赫 32 / 领域 50）未同步调整，前期战斗会明显变紧。这是 D3 的直接代价，必须靠 `sim` 量出新的价格曲线再改。
- `stacking: refresh` 从 schema 消失 ⇒ 任何仍写 `refresh` 的模板会在加载期**拒载**（不是静默降级）。
- 再施加刷新时长 ⇒ 持续伤害类补正（`curse-poison` / `cursed-burn`）更容易被「续」住。当前没有技能反复施加它们，等 W2 的术式落地时再评估是否需要「不可续」的第三档。
- 属性下限 0 会让「负数补正」在数值上等价于「清零」。若将来需要「负属性」（如诅咒反噬），必须另开字段，不能放宽这一条。
