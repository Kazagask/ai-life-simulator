# ADR-013 召唤协议简化：技能点名、无限杂兵、英雄永久损失

- 状态：已实施（2026-11-20）
- 关联：ADR-003（自定义资源）、ADR-009（补正）、ADR-010（演员同构）、ADR-012（召唤 / 中途加入 / 胜负条件）、`SPEC §1.6`（归属判据）
- 涉及：`packages/shared/src/{v2.ts,schema/skill.ts,schema/world.ts}`、`packages/game-core/src/v2/{battle,projection}.ts`、`apps/server/src/admin/sim.ts`、`specs/data/templates/jjk-2006/3.0.0/{skills,characters,statuses}.yaml`、`test/unit/adr-012.test.ts`

## 背景

ADR-012 做出了召唤，随即被用户连续否掉四版设计：`refund`、`stock`、`@cost`、以及「代价统一 + `@paid` 流水 + 生命周期钩子」。第四版（`docs` 里已删）本身是自洽的，但用户一句话推翻了它的前提：

> 不好弄啊，那收回来之后召唤物 hp / 状态怎么搞。我倾向先简化：杂兵献祭就献祭了，也不搞池子做库存了，就当无限（基本上大部分都怎么搞的）；英雄单位就用宝可梦那种模式，死了 / 献祭就没了，召唤不了了。协议就统一在技能里 summon 点名就行了，消耗啥的也不返回。战斗内收回再召唤，状态继承；第二次战斗状态自动回满。

这段话把整条推导链的根挖出来了：**`curses` 池不是「召唤需要燃料」，而是「我没法维护几百只咒灵」的规模压缩。** 一旦接受「杂兵本来就是无限的」，池子存在的两个理由（限制强度、给旋涡凑祭品）就分别被「场上的 `limit`」和「献祭场上单位」接管 —— 账本没了，之前所有需要账本的字段（`consume` / `refundOnDeath` / `recall.refund` / `consumeResource.includeDeployed`）也就一起没了。

前三版之所以越修越像补丁，是因为一直在**给账本补对账规则**，而用户要的是**不要账本**。

## 决策

### D1 协议唯一入口：技能里 `summon` 点名

```yaml
summon:
  ref: enemy-grade2-curse   # 点名的就是 characters.yaml 里的角色 id
  count: 3                  # 一次几只
  tier: minion              # minion | hero
  limit: 3                  # 场上限；缺省 minion 3 / hero 1
  levelScale: 0.8
  onSummonerDown: dismiss
```

- 单位从**角色卡**现场实例化（`buildUnit`），与开场单位同源：装备、补正、心情、技能权重全部继承，不存在第二套迷你数值。
- `ref` 在加载期校验（`world.ts`）：写错一个 id 就等于多出一个**永远召不出的技能**，界面上它还在，点了没反应 —— 这类错必须在校验期炸，不能等玩家发现。
- 没有 `summonables` 注册表、没有 `kind: stock|named`、没有 `persistence`：这些开关都是为了在同一个函数里区分两种召唤而存在的。现在两种召唤的差别落在 `tier` 一个已有的字段上，不需要新开关。

### D2 杂兵 = 兵力，不是库存

- **召唤不消耗任何资源**（MP 除外，那是技能的价）。`summon.consume` 已删。
- 稀缺性由**场上的 `limit`** 表达：一次召三只、场上最多三只。这已经足够让「召灵」不是无本万利 —— 玩家每回合只能做一件事。
- **阵亡不回补、召回不返还**：没有账本，也就没有「打完一场数量对不上」这类 bug。ADR-012 D9 那套「存量 = 池 + 场上」的记账规则连同 `finishBattle` 的收场返还一起删除。
- `limit` 的语义是「场上最多几只」，不是「还能召几只」：`count: 3` 在站着两只时补满第三只，而不是因为 `2 + 3 > 3` 直接拒绝。旧语义会逼玩家先收灵再召 —— 那是纯粹的操作税。
  （**补满那半句继续有效**；「满了怎么办」已被 **ADR-016 D3** 接管：满员不再是拒绝，而是把最早上场的同档单位挤进回收架，且只从**友方**里出人。）

### D3 英雄 = 个体，死了就是没了

`tier: hero` 的单位是**这一只**，不是一份兵力：

- 阵亡或被献祭 ⇒ 写进 `state.lostSummons: string[]`（存 `ref`），本局**再也召不出来**。
- 判定单点：`summonLost(state, spec)`。引擎拒绝（`summon_lost`）、模拟器挑招都走它 —— 各处各写一遍 `lostSummons.includes(ref)` 必然出现「AI 还在挑、界面上没了」。
- ~~面板上**直接不显示**这个技能，而不是灰着~~ —— **已被 ADR-015 D3 取代**（2026-11-20 用户裁决）：
  藏起来让玩家分不清「没学过」与「学过但没了」，技能页与战斗面板现在都**照常列出**，挂 `seal: { code: "summon_lost", text: … }`。
- 只记玩家自己的（`summonedBy === selfId`）。NPC 的召唤物死在场上就是本场没了，不需要跨战斗的账本；而 `lostSummons` 存的是角色 id，全局记会误伤同名的另一只。
- 纯新增字段 ⇒ 不升 `schemaVersion`、不拒旧档（旧档读作「什么都没失去」）。

### D4 回收架 `battle.bench`：收回 ≠ 阵亡

「收回之后再召，状态继承」和「第二场自动回满」看似矛盾，其实是**作用域**问题：

- 收回的单位进 `battle.bench`，连同伴随它的一切（hp / 补正 / 冷却 / `enteredRound`）停在战斗状态里；同一场里再点名 `ref` 就原样搬回场上。这就是「同一只」。
- `battle` 在战斗结束时整个丢弃 ⇒ 回收架随之消失 ⇒ **下一场是新的一批，满血满状态**。不需要写任何「重置」代码，边界由数据结构本身给出。
- 认亲用 `summonRef + summonedBy`，不用实例 id：实例 id 是运行时编号，玩家看不见，也不该被当成身份。

### D5 献祭：烧场上单位换伤害

```yaml
sacrifice: { count: all, perTier: { minion: 15, hero: 55 } }
damage: [ { preset: fixed, value: 10 } ]
```

- 与已删的 `consumeResource` 的区别：那条烧的是**库存计数**，这条烧的是**单位本身**。没有池子之后「我有几只」就等于「场上有几只」。
- 献祭在**伤害之前**结算：烧掉的那几只正是这一击威力的来源。返回值是**加成**，技能的 `damage` 照常算，两者相加。
- `perTier` 表示每档单位折多少伤害 —— 虹龙与杂兵不是同一个价（用户口径），而**差价属于技能不属于单位**：同一只杂兵被不同术式烧掉，能换来的东西本来就不一样。
- 挑谁先烧写死为**先杂兵、后英雄**（同档内先召的先烧）：不指定目标时不该先烧最贵的。顺序只由状态决定，所以玩家、AI、模拟器算出同一批。
- 没有祭品 ⇒ `sacrifice_empty`，不白扣 25 点 MP。献祭掉的单位**不进回收架**，这是献祭与召回的唯一区别。

### D6 顺带修掉的真 bug

| bug | 修法 |
|---|---|
| 召唤物实例 id 撞名 | 用 `battle.summonSeq` 单调计数（旧实现取 `allUnits().length`，单位阵亡 / 被收回后长度变短，下一批就复用旧编号；`writeBack` 按实例 id 找人，撞名等于把伤害写到别人身上） |
| `limit` 语义导致「先收灵再召」的操作税 | 见 D2：上限 = 场上最多几只 |

### D7 模板迁移（`jjk-2006/3.0.0`）

**① 咒灵操术（献祭流）**

| 项 | 改成 |
|---|---|
| `sk-summon-curse` | `count: 3 / limit: 3`，删 `consume`、`refundOnDeath` |
| `sk-summon-dragon` | `ref: curse-rainbow-dragon`（新卡，不再借 `enemy-grade1-curse` 的皮）、`tier: hero`，删 `consume`、`refundOnDeath` |
| `sk-recall` | `recall: { count: 1 }`（删 `refund`） |
| `sk-uzumaki` | `sacrifice: { count: all, perTier: { minion: 15, hero: 55 } }`、`damage: fixed 10`；删 `consumeResource` |
| `characters.yaml` | 删三处 `resources: { curses: ... }`（`npc-geto` / 2018 夏油 / `npc-kenjaku`）；新增 `curse-rainbow-dragon` 卡与 `sk-wyrm-coil` / `sk-wyrm-breath` 两招 |
| 删除字段 | `summon.consume` / `summon.refundOnDeath` / `recall.refund` / `consumeResource` / `ConsumeResourceSpec` / `BattleEnemy.summonCost` / `BattleEnemy.refundOnDeath` |

数值：三只杂兵 = 10 + 45 = 55；单只虹龙 = 10 + 55 = 65。前者的 55 与 ADR-012 时代持平，后者的 55 变成 65 —— 献祭英雄比献祭三只杂兵更疼，才符合「个体 vs 兵力」的定价。

**② 十影（召唤流，同一套协议）**

用户口径（2026-11-20）：「十影那个也走这套流程，没有漩涡献祭，一样的，除了脱兔全是英雄单位（实际上是削弱了，原作能同时召唤多个）」。

| 项 | 改成 |
|---|---|
| 脱兔 | `sk-ten-rabbits`：`shiki-rabbits`、`tier: minion`、`count: 3 / limit: 3`、`levelScale: 0.7` |
| 其余七种 | `sk-ten-shadow` / `-nue` / `-gama` / `-orochi` / `-enzuru` / `-kangyu` / `-mahoraga`：全部 `tier: hero`、`limit: 1`，原文的伤害招式改成点名式神 |
| 换手 | `sk-ten-recall`（影法术·收），`recall: { count: 1 }`；AI 权重写 0（收回是手操按钮，不是出招） |
| 献祭 | **没有**。十影整套技能都不声明 `sacrifice` —— 那是咒灵操术「拿存量换一发」的私有解法 |
| 魔虚罗 | 代价从「一次性伤害」挪到**施放点**：`applyStatus: exhausted { value: 2, unit: day }`，与召唤物本身无关 |

三个刻意为之的形状：

- **英雄位只有一个**（上限按档统计，ADR-012 D2）。原作能同时放好几只，这里是明确的削弱；换手靠 `sk-ten-recall`，收回的式神进 `battle.bench`、状态原样保留。
- **玉犬合成一张卡**。原作是黑、白两只；拆两张卡会让「一次只站一只」变得滑稽，合一张（一对犬一起打）刚好保住「十种」的手感。
- **魔虚罗不再是「一发 45 点伤害」**。它现在是个真单位（CE 54 / 体格 15 / 375 血、`sk-shiki-wheel` 必中），也是 B-07 遗留的「魔虚罗未配」的收尾。
  **后续（ADR-014）**：这个单位是**未调伏**形态 —— `summon.faction: neutral`（站中间、双方都打）、法轮每回合回血并叠「适应」、
  阵亡不记 `lostSummons`。宿傩那一版（已调伏）留到剧情追上再做。

两处**不做**：① 原作里式神死亡会把力量过继给其余式神（玉犬死了，别的式神变强）—— 那需要一张「阵亡收益表」，
先把永久损失这条语义跑熟再说；② `npc-sukuna-megumi`（宿傩借惠之身）仍带着 `sk-ten-shadow`，
所以 BOSS 会**把玉犬召到敌方阵营**（这很原作）。`markSummonLost` 只记 `summonedBy === selfId` 的那一只，
敌人的玉犬死掉不会污染玩家的 `lostSummons`。

### D8 边界：名册（真·宝可梦）仍是下一轮

十影本轮用的是**同一套 `summon` 协议**：式神从角色卡实例化、英雄档阵亡即永久失去。它没有「名册」——式神不是攒下来的个体，是术式的一部分，每次召唤都是新的一份（`battle` 结束即丢）。

真·宝可梦式（调伏、个体养成、跨战斗存活）还缺三件事 ——

| 缺什么 | 怎么补（下一轮） |
|---|---|
| 名册 | 复用演员表：`state.npcs` 中 `ownerId === selfId` 的子集（不新建 `state.summons`，否则又是一套演员、又一次双真相） |
| 获取 | 调伏 = 事件 / 技能流程（`spawnNpc` 或改 `ownerId`），不是新的战斗原语 |
| 跨战斗状态 | `finishBattle` 增加 NPC 回写（今天只回写玩家，NPC 的 hp / statuses 随战斗丢弃） |
| 动词 | `deploy: { ref: <npcId> }` —— 从名册取人上场，与 `summon` 分开 |

**本轮不预判复用**（SPEC §1.6）。但 D3 已经把「英雄是个体」这条语义先立起来了：`lostSummons` 是它最小可用的形态，等名册落地时，这张表会自然变成「名册里被删掉的那一格」。

## 验收

- `pnpm test` 71 文件 / 511 例全绿；`pnpm inspect check` error 0 / warn 7；`tsc` 0；`pnpm build` 通过。
- 全仓 `curses` 0 引用（除 `archive/` 与 p0 夹具里无关的同名字片段）。
- `adr-012.test.ts` 的「召唤生命周期」组（9 例）覆盖 D2–D5：不扣资源、补满而非硬塞、收回继承血量、跨战斗满血、英雄阵亡 / 献祭后 `summon_lost` 且面板无此技、杂兵不记账、三杂兵 55 / 虹龙 65、献祭后不可召回、无祭品 `sacrifice_empty`。
- 「十影」组（6 例）覆盖 D7②：脱兔一次三只且只花 8 点 MP、英雄位共享（玉犬在场时召鵺 `summon_limit`）、收回→换手→再召回来是同一只且带伤、整套技能都不声明 `sacrifice`、魔虚罗给自己挂 `exhausted`、玉犬阵亡后面板只少了那一招。

## 影响

- `summon` / `recall` 的 schema 变 ⇒ 模板指纹变，旧档 `template_content_drift` 拒载。
- `resource-scaled` 与 `gainResource` 在本模板已无使用者（池子撤了），但作为通用协议保留：它们只依赖 `cost` / `resources`，别的世界要用仍需这两条。
- `apps/server/src/admin/sim.ts`：挑招打分加上 `sacrificeValueOf`（与引擎**同源**，不是另写一套），否则旋涡只剩 base 10，永远排在普通攻击后面。
  另修一处仪器空转：`coverage` 姿态原先「召满 ⇒ 无条件召回一只」，遇到**没有献祭**的流派（十影）会变成「召回→重召」的永动机；现在只有在场上有东西可烧、或回收架里有货时才召回，其余情况退回正常打分。
- `apps/server/src/cli/inspect.ts`：新增 `--skills a,b,c`。十影的英雄位只有一个，不指定就永远量到「id 排第一的那只」（`sk-ten-enzuru`，一个治疗）—— 仪器该由操作者指定带哪套上场。
- `projection.ts`：战斗技能列表过滤掉已失去的英雄召唤。

## 附：被否掉的四版

| 版本 | 被否的原因（用户原话 / 提炼） |
|---|---|
| `refund` / `stock` 字段 | 开关式设计：引擎要在四处分支，且它记录的是可推导的信息 |
| `@cost` | 「本质还是 @cost，只不过你这个指针能支持多属性了 —— 可以，但不够优雅」 |
| `@paid` 流水 + 生命周期钩子 | 自洽，但前提（召唤必须耗资源）是错的；钩子是对账规则的精致化 |
| 本版 | 取消账本：杂兵无限、英雄永久、收回进回收架 |

值得记下来的一点：**「不够优雅」通常意味着「这个抽象不该存在」**，而不是「写法还不够好」。前三次修改都在改写法，第四次才动到抽象。
