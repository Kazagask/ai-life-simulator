# ADR-003：属性类型与自定义资源协议

- **日期**：2026-11-19
- **状态**：**已裁决**（2026-11-19 用户确认 D-1 / D-2 / D-3，D-4 裁决为「两种模式都要」）
- **关联**：`specs/iteration-2026-11-19-attribute-types/`
- **前序**：ADR-001（前实例化开局）、ADR-002（表现层协议）

## 背景

用户提出「人物属性优化」与「资源支持自定义」两件事。核对代码后，这不是加几个字段，
而是**属性/资源两套契约都建立在「标量数值」假设上**：

| 环节 | 现状事实 |
|---|---|
| 模板 | `attributes.order/defaults/caps/labels` 只有 `Record<string, number>`；没有类型概念 |
| 存档 | `V2CombatantBase.attributes: Record<string, number>`；玩家 / NPC / 战斗单位 / 敌人共用 |
| 效果 | 只有 `adjustAttribute { attribute, value: number }`；没有「设为某个词」的写法 |
| 条件 | `AttributeConditionSchema` 只有数值比较（eq/gte/…） |
| 公式 | 资源 `perAttribute`、技能 `scaleBy`、补正 `attributeModifiers`、装备动态补正都直接读数值 |
| 投影 | `player.attributes: Record<string, number>`；`attributeViews` 不存在 |
| 资源 | `resources` 只允许 `hp` / `mp` 两个键；`adjustResource.resource` 是 `"hp" \| "mp"` 枚举 |
| 战斗 | `BattleState.player` 只有 `hp` / `mp`；技能消耗硬编码 `cost.mp`；战斗视图只有 `costMp` |
| 资源条 | 适配器 `deriveStatusBar` 硬编码 hp/mp 两条；`statusBar` 的 resource 段实际未被消费 |

用户要的三类属性（文本+样式、阶梯进度、复合称号）和「能量豆」类自定义资源，
在上述假设下**都无法表达**。

## 决策

### D1 属性值放宽为 `number | string`，类型由模板声明决定

`attributes: Record<string, AttributeValue>`（`AttributeValue = number | string`），
玩家 / NPC / 战斗单位 / 敌人共用同一形状。类型不在值里（不做 tagged union），
而是查模板 `attributes.defs[id].kind`；**没有 def 就是 `number`**（零迁移）。

理由：属性名是模板词汇，类型是模板声明；把 tag 塞进每个值会让存档膨胀，也会让
「同一个属性在旧档里没 tag」变成迁移问题。

**代价**：每个数值消费者必须显式窄化。用两条纪律收口：
1. 加载期校验「数值面只接受数值属性」；
2. 运行时统一走 `numericAttr()` / `effectiveAttributes()`（后者只输出数值键）。

### D2 四种属性类型

| kind | 存储 | 展示 | 典型 |
|---|---|---|---|
| `number`（缺省） | number | 数字 | 咒力 / 智力 |
| `enum` | 选项 id（string） | 选项 label + `style` | 生得术式「无下限术式」、等级「特级」 |
| `ladder` | number（累计值） | 当前档 label + 本档进度条 | 修为 15/100 → 练气初期 |
| `composite` | **不存储** | 由 sources 派生的称号 + `style` | 名誉：恶名 + 善名 → 恶贯满盈 / 亦正亦邪 |

`composite` 是**只读派生**：不可被效果写入、不可被条件引用（要判就判 sources）。
这样不存在「称号与两条轴不一致」的第二真相。

### D3 文本属性是「选项 id」，展示词与样式归模板

模板声明 `values: [{ id, label, style? }]`；存档只存 id。投影期解析成
`AttributeView { id, label, kind, value, display, style, progress?, tier?, sources? }`，
前端只消费 view，不查模板、不硬编码世界观词。

`style` 与 ADR-002 同一套闭集（预设 / `ui.styles` / 模板自定义），
加载期经 `validateStyleRefs` 校验，未知 id 拒载。

### D4 阶梯 = 两种模式（用户 2026-11-19 裁决「两种都要」）

```yaml
cultivation:            # 累计式：tiers[].at 是累计阈值
  kind: ladder
  mode: cumulative      # 缺省
  tiers:
    - { id: qi-early, label: 练气初期, at: 0 }
    - { id: qi-mid,   label: 练气中期, at: 100 }

sword-intent:           # 归零式：tiers[].at 是本档升到下一档所需
  kind: ladder
  mode: reset
  tiers:
    - { id: novice, label: 初窥, at: 80 }
    - { id: adept,  label: 小成, at: 200 }
```

- **cumulative（缺省）**：数值单调累计；当前档 = 最后一个 `at <= value` 的档；
  进度 = `(value - tier.at) / (next.at - tier.at)`；**升档不减数值**。
- **reset**：数值是「本档内的经验池」；升档时**扣掉本档所需**、档位 +1（可连升）；
  当前档必须落存档（`state.player.attributeTiers[id]`），因为同一个数值在不同档位
  含义不同（20/80 与 20/200 无法只靠数值区分）。
- 两种模式都展示 `value / 本档需求`（如 15/100）；最后一档无下一档时不显示进度条
  （`attributes.caps[id]` 存在则用它当分母）。
- 结算收获时：cumulative 用数值差分；reset 发生升档时展示档位变化（不展示「-90」这种
  被扣掉的数值，避免玩家误读）。

### D5 复合属性 = 优先序规则表

```yaml
fame:
  kind: composite
  sources: [infamy, virtue]
  cases:
    - when: { infamy: { gte: 2 }, virtue: { gte: 2 } }
      label: 乱世枭雄
      style: rainbow
    ...
  fallback: { label: 默默无闻, style: gray }
```

- `sources` 必须是数值属性（number / ladder）；
- `cases` 按声明顺序**首个全匹配**生效；`fallback` 必填；
- 只做展示派生，不进条件 / 效果 / 公式。

### D6 `hidden` 属性

`defs[id].hidden: true` 的属性仍进 state、仍可被效果/条件/公式使用，
但**不进属性面板**（`attributeViews` 过滤掉）。用于「恶名 / 善名」这种
只作为复合属性输入的轴；复合属性的 view 会带 `sources` 供详情展示。

### D7 数值面只接受数值属性（加载期 fail-fast）

以下位置引用属性 id 时，目标必须是 `number` / `ladder`：

- `attributes.caps`
- `resources.*.perAttribute`
- `mood.bands[].attributeModifiers`
- `statuses[].simulation.attributeModifiers`
- 技能 `hitCheck.attacker/defender`、`damage/heal[].scaleBy`、战斗 `fleeCheck`
- 转盘 `weightBy`
- 装备 `dynamicModifier` 的属性键

`adjustAttribute` 的目标必须是数值属性；`setAttribute` 的目标必须存在，
文本目标的值必须是已声明选项 id（字面量在加载期校验）。

### D8 自定义资源

```yaml
# world.yaml —— 规则（进指纹）
resources:
  hp: { base: 100, perLevel: 0 }
  mp: { base: 50, perLevel: 0 }
  beans:
    label: 能量豆
    base: 5
    perLevel: 0
    initial: 0
    cap: 5
```

```yaml
# ui.yaml —— 纯渲染（不进指纹）
resources:
  beans: { display: pips, dangerAt: 0 }
```

- `resources` 在 `hp` / `mp` 之后追加任意 id（`hp` / `mp` 仍必填，引擎对它们有硬语义）；
- 上限 = `base + perLevel × growthLevel + Σ perAttribute[attr] × 基础属性值`，再取 `cap`；
- `initial` 缺省 = 上限；hp 的下限仍为 1，其余为 0；
- **刻度样式 / 告警阈值是渲染**，放 `ui.yaml`（与 `styles` 同一理由：改配色不该让旧存档拒载）；
  缺省 `display: bar`、`dangerAt: 0.25`（hp/mp 维持现状）。
- 自定义资源存 `state.player.resources: Record<string, number>`（**不含 hp/mp**），
  战斗镜像 `battle.player.resources` 同形，战斗结束回写；
- 效果 `adjustResource.resource` 放宽为已声明资源 id；
- 回复 `regen.perTurn` / `regen.actions.*` 允许追加自定义资源键；
- 敌人 / 友军同样携带 `resources`（引擎对称，不做「只有玩家有」的特例）。

### D9 技能消耗可引用自定义资源

`cost` 从 `{ mp: number }` 放宽为 `{ mp: number, ...自定义资源?: number }`（catchall 数值）。
引擎逐项检查、逐项扣除；不足时抛 `not_enough_resource:<id>`（`mp` 保持
`not_enough_mp` 兼容），投影下发 `costs: [{ resource, label, amount }]`。

### D10 资源条只显示模板声明的段

资源条顺序与可见性由 `statusBar` 的 `source: resource` 段决定（现状字段终于被消费）。
**显示形态**（`display: bar|pips`）与告警阈值（`dangerAt`）写在 `ui.yaml.resources`，
投影下发 `ResourceView`，前端不猜。
未在 statusBar 声明的资源不显示（这是意图：资源存在 ≠ 常驻 HUD）。

### D11 版本与兼容

- `attributes` 值 union、`resources` 追加、`player.resources` 默认 `{}` 都是**向后兼容的放宽**：
  旧档（全数值、无自定义资源）可直载，**不升 schemaVersion**；
- 模板语义变化（新属性、新资源）由模板指纹承担，旧档照旧拒载；
- 文本属性的引入不改变现有数值属性的任何求值顺序。

### D12 战斗内每回合回复（2026-11-19 追加）

自由行动轮的 `regen.perTurn` / `regen.actions` 与战斗轮**不是同一条管线**：
战斗里每回合都有一次 `roundEnd`，而自由行动只在提交行动时结算。
因此新增一份独立声明，而不是复用 `perTurn`：

```yaml
# world.yaml（玩家）
regen:
  perTurn: { hp: 0, mp: 0 }
  combat: { hp: 1, beans: 1 }     # 战斗内每回合结束

# characters.yaml（敌人 / 友军）
- id: npc-x
  combatRegen: { hp: 3 }
```

- **任意已声明资源**，缺键 = 0；不强制 hp/mp（`perTurn` 强制是因为引擎对它们有硬语义）。
- 值必须非负：战斗内的持续伤害走补正的 `onRoundEnd`（能吃到攻击方属性与公式），不在这里。
- 结算位置：`roundEnd` 末尾、`checkBattleEnd` 之前；只写**战斗镜像**，结束由 `finishBattle` 回写。
- 按各自上限夹取：玩家走成长公式，敌人/友军走 `combatUnitResourceMax`（growthLevel = 0）。
- 实际回复 0 不写日志；有回复则写「R{n} 你/某某 回复 N 点{资源名}」，直接进战报。

**按属性加权**（2026-11-19 追加）：回复值可以是常数，也可以是
`{ base, perAttribute: { <属性>: <系数> } }`，求值 `base + Σ 系数 × 基础属性值`，四舍五入到整数。
该写法对 `perTurn` / `actions` / `combat` / `combatRegen` **四处通用**：

```yaml
regen:
  combat:
    beans: { base: 0, perAttribute: { body: 0.4 } }   # 体魄 5 ⇒ 每回合 2 颗
```

- 用**基础属性**（与资源上限 `perAttribute` 同一口径）：回复量不随临时补正波动；
- 加权系数只能引用数值属性，写文本属性 / 未声明属性在加载期即拒载；
- 求值结果 `Math.round`，再按资源上限夹取。

## 代价

- 属性/资源的「同一条链路」从 schema 到 UI 都要改一遍；改动面大，必须用加载期校验 +
  定向回归兜住（见迭代 tasks.md 的 T1..T8）。
- 模板作者要理解 kind 与 composite 的优先序；文档写在 `specs/SPEC.md`，不只写 ADR。
- 资源条改为模板声明后，历史模板如果只声明了 hp 而没写 mp 段，MP 将不再常驻显示
  （jjk 已写两段；valmont 只写 hp 段 ⇒ 行为变成「只显示生命」，与模板意图一致）。

## 备选（否决）

| 方案 | 否决理由 |
|---|---|
| 文本属性另存 `textAttributes` | 两套清单、两个投影、条件/效果按 kind 分派，长期必然漂移 |
| 复合属性写成普通 enum、由效果维护 | 双真相；任何一处忘写就出现「恶名 ++ 但名誉默默无闻」 |
| 资源定义（上限 / 初始 / 消耗）放进 `ui.yaml` | 资源规则是判定输入，放展示域会让指纹漏掉规则变化；只把 `display` / `dangerAt` 留在 ui |
| 把 hp/mp 并入统一 `resources` 映射 | 战斗/死亡/治疗对 hp 有硬语义，全量重构的收益远小于风险 |
