# ADR-006 战斗施加的目标、NPC 的登场时点、关系行怎么说

- 状态：已实施（2026-11-19）
- 影响：`packages/shared`（skill / view-model / v2 契约）、`packages/game-core`（battle / projection / presentation）、`packages/rpg-ui`（adapter / NpcCard / RelationList）、`specs/data/templates/jjk-2006/3.0.0`（characters / world / events / skills / opening）
- 起因：用户四条验收意见（2026-11-19）中的三条半 —— ①「施加效果没写施加给谁」②「开局 NPC 该到章节时间点再生成，不要靠事件生成」③「甚尔/漏壶/羂索/宿傩该是 NPC，敌人只留野怪」④「关系只有推断/确知和一个数值，没有完全不知道；不实例化的写着『无档案』」

三件事放在一份 ADR 里，是因为它们回答的是同一个问题：**一个东西在世界上存在，与它被玩家看见，是两件事**。

---

## D1 · 施加点必须自带收件人

### 问题

`applyStatus` 只写补正与概率。收件人靠隐式约定：缺省 = 技能目标；写了 `onSelf: true` = 施放者。

两个坑：

1. **推不出来**。无量空处的技能目标是 `all_enemies`，可它的「领域展开」增幅落在**自己**身上，压制与眩晕落在**敌人**身上。只有「自己 vs 技能目标」两档时，数据里读不出这件事，只能靠注释。
2. **`onSelf` 在目标循环里执行**。打三个敌人，就给自己叠三层 `domain-active`；目标全部闪开时，自己那一层反而挂不上。挂在谁身上跟「打没打中谁」本来无关。

### 决定

`StatusApplicationSchema` 增 `target`，四档，缺省 `skill`：

| 值 | 收件人 | 是否走技能命中 |
| --- | --- | --- |
| `skill`（缺省） | 技能目标，逐个结算 | 是（目标闪开 ⇒ 不施加） |
| `self` | 施放者本人 | **否**，只走 `chance` |
| `all_enemies` | 施放者视角的全场敌方 | 否，只走 `chance` |
| `all_allies` | 施放者视角的全场我方 | 否，只走 `chance` |

`onSelf` 保留为 `self` 的等价旧写法（既有模板与旧档不必改），两者同时出现且指向不同收件人 ⇒ 拒载（两处说法打架，不猜优先级）。引擎侧 `applyTargetOf` 是唯一口径，展示层 `applyTargetLabel` 与它同构。

技能详情写成「施加 领域展开 ×1（自身）」「施加 领域压制 ×1（全体敌人）」。`skill` 那一档**不加后缀** —— 上一行已经写了 `目标：全体敌人`。

### 已知缺口

「打中了才给自己挂」没有独立表达。需要时写成 `target: skill` 且技能目标是自己（走命中判定）。现有模板没有这种技能（黑闪是必中），故不新增字段。

## D2 · NPC 一律定时登场，事件生成只是兜底

### 问题

乙骨的登场挂在 `ev-np-01` 的胜负出口上。玩家没走到那场战斗（或走了别的线），他就永远停在 `unspawned`：不上人物面板、不参战、不能当关系端点。人物出场不该是某条支线的副产品。

### 决定

1. **定时是常态**：`world.yaml npcSpawnRules[].when` 写时间条件（`{ time: { gte: … } }`），引擎在每轮 tail 求值（`evaluateSpawnRules`，既有实现，无协议改动）。到点即 `spawnNpc`：幂等、写 `spawnLog`、按规则的 `age` 重算 `birthTime`。
2. **时间点与章节门同源**：门的 `window.start` 是多少天，这一章的人就用多少天。门开了，人也在。
3. **参战另加一层保险**：任何以他们为 `enemies[].ref` 的事件同时声明 `npcs: [rule-…]`，占槽时先 `materializeEventNpcs`。定时是常态，事件内兜底是为了不让「时间没走到」把一场战斗变成空场 —— `enemiesExhausted` 会被判即胜，白送 `onVictory`。
4. **事件不再负责生人**：`ev-np-01` 里的 `spawnNpc` 效果已删。登场机制只留一条，避免两处各写一遍。

### 连带

- 2006 开局的实例表只有 2006 那一届（+ 理子，`visibility: hidden`）；虎杖 / 伏黑 / 钉崎 / 乙骨 / 漏壶 / 宿傩三形态 / 羂索 / 甚尔全在 `unspawned`。
- 甚尔在怀玉末（`ev-hv-07b` 六个出口）统一置 `inactive`（阵亡）：他这一章的戏演完了，不该在 2018 年还在后台跑自主行动。

## D3 · 关系行说人话

### 问题

1. **「无档案」在撒谎**。五条视伏黑为弟子，2006 年惠还没登场 ⇒ 行尾一个「无档案」胶囊。玩家读到的是「系统缺数据」，实际是「这个人还没出场」。这个词是家族扩展做多跳亲缘时引进的。
2. **裸数值没有参照系**。行的末尾直接印 `+32`、人物卡印「关系 10」外加一根同值进度条。玩家要判断的是「这一档算近还是远」，不是一个可以刷的点数。
3. **可见性词表只有两档**。内核是四档（known / inferred / unknown / hidden），适配器只翻了前两档，兜底是 `?? rel.visibility` —— 屏幕上会直接冒出英文 `unknown`。

### 决定

1. `RelationRow` / `NpcRelationVM` 增 `counterpartState`（`unspawned` / `hidden` / `enemy`）与 `counterpartStateLabel`，由投影按 `hiddenNodeIds` 的三条显式规则给出理由，适配器翻译成「尚未登场 / 未现身 / 不在名册」。`counterpartVisible` 保留（旧前端兼容）。
2. 数值换档位：`valueLabel`（关系行）与 `relationshipLabel`（人物卡）由适配器按 `value` 分档 —— 深厚 ≥60 / 亲近 ≥20 / 平常 ±20 以内 / 疏远 ≤-20 / 敌视 ≤-60。原值仍随行下发，落在 `title` 与进度条上。
3. 词表补全四档：确知 / 推断 / 未知 / 未明。`unknown` / `hidden` 仍被投影挡掉（不认识的关系不上屏、hidden 的来源不泄露）—— 但词表缺项的兜底会是英文，不能赌「这档永远不来」。

### 明确不做

放开「知道有这么条关系、但不知道内容」的 `?` 占位行。它会泄露「存在一段你不知道的关系」这个事实，属于信息设计问题（悬疑手感 vs 泄露），不是展示层能自行决定的。等产品口径。
