## 0. 决策摘要（已定）

| # | 决策 |
|---|---|
| 1 | `stake` 显式声明；内置 `spar / hard / deaths`；模板可按 key 覆盖；**默认 `deaths`（硬核）**。 |
| 2 | `spar` 支持 `hp_below` 失败条件；`hard` hp 锁 1、**绝不判死**；`deaths` hp 0。 |
| 3 | 战斗判死、战果、战评、死亡路由收进一个模块；**`deathRoutes` 是死亡结局的唯一权威**。 |
| 4 | `endings.triggerConditions` 不再参与死亡结局选择（只服务非死亡终止）；死亡路由直接引用 `endingId`。 |
| 5 | 战评 hook 在死亡前运行；**死亡不跳过成长判定**（后续如要跳过，用互斥组，另设计）。 |
| 6 | 资源协议统一到全部资源；`hp / mp` 保留为基础预设（状态存储不变）。 |
| 7 | `deathRoutes` 放 `world.yaml` **顶层**；旧 `deathRoute` 删除，不迁移。 |
| 8 | 死亡事件结算后自动 `hp = max(1, hp)`；无 `continue` / `revive`；事件致死用 `playerDeath` 再入路由。 |
| 9 | 死亡链上限、`powerRatio` 阈值由模板处理；**引擎不兜底**。 |
| 10 | 战斗力：模板可覆盖；引擎默认按**底层基属性**求和（派生折算回基属性，排除 signed / hidden）。 |
| 11 | `player / ally / enemy / neutral` 四侧战斗力全算；比值条件由模板用。 |
| 12 | 新增 `anyMatch` 条件（集合 + 字段谓词）。 |
| 13 | 天赋成长：`progress` + `tiers[{ at, tier, effects }]`；每阶给加点；黑闪 `0/1/4/8 → 无/紫/粉/橙红`。 |
| 14 | 具名 set 多钩子：默认先结算，再按事件引用顺序；**不做替换**（后续互斥组）。 |
| 15 | **判负阈值随 stake**：`dead → hp ≤ 0`，`down / yielded → hp ≤ 1`；`checkBattleEnd` 不再写 `hp = 1`。 |
| 16 | 四侧 power 全部取**开场快照**；另有 `player.powerEnd` 供叙事（不与开局口径混比）。 |
| 17 | 死亡路由**不接受任何 HP 判据**（R-EN-07）：没有 `hpRatio`，也没有 `resource.hp`。 |
| 18 | `killer` 只由**技能伤害**产生；持续伤害 / 环境伤害不产生 killer。 |
| 19 | 死亡结算必须发生在 `nextTurn` / 回复**之前**；否则「毒死之后回血复活」。 |
| 20 | `playerDeath` 在事件 / 行动 / 世界效果里都能触发路由；`cause` 由**边界**给，不由效果自己写。 |
| 21 | `grantAllocation` **保持单条 pending**；同批跨两阶是模板错误（可诊断抛出）。模板负责让一次只跨一阶。 |

## 1. Stake（会不会死）

```yaml
# world.yaml
combat:
  stakes:
    spar:   { label: 切磋, defeatState: yielded, hpOnDefeat: { mode: floor, value: 1 } }
    hard:   { label: 恶战, defeatState: down,    hpOnDefeat: { mode: set,   value: 1 } }
    deaths: { label: 死斗, defeatState: dead,    hpOnDefeat: { mode: set,   value: 0 } }
  defaultStake: deaths
```

```yaml
# events.yaml
settle:
  combat:
    stake: hard          # 不写 ⇒ combat.defaultStake（默认 deaths）
```

- `defeatState` 枚举：`yielded | down | dead`。模板自定义 stake 只能落这三态。
- **`defeatState: dead` 是唯一进入死亡路由的入口**；`hard / spar` 永不判死。
- `hpOnDefeat`：`floor` = `max(value, hp)`（不掉到 value 以下，也不往上抬）；`set` = 直接写 value。
- 缺省 `hpOnDefeat` 由 `defeatState` 推：`dead → { set, 0 }`，其余 `{ floor, 1 }`。

### 1.1 判负阈值（本轮新增的硬约束）

战斗里「玩家倒下」的阈值不再写死为 1：

| `defeatState` | 判负阈值 | `player_down` 的含义 |
|---|---|---|
| `dead` | `0` | `hp <= 0` |
| `down` / `yielded` | `1` | `hp <= 1`（旧语义） |

- `checkBattleEnd` **不再写 `hp = 1`**。判负只写 `over = "defeat"`；hp 由 `finishBattle` 的 `hpOnDefeat` 统一落。
- 阈值存进 `BattleState.defeatThreshold`（旧档缺省 1），供 `conditionMet(player_down)` 与战斗内兜底读。
- `hp_below` 仍是**比例**条件（`hp / maxHp <= ratio`），不受阈值影响；maxHp 现算，拿不到时回退开场快照。
- 道具治疗下限从 `Math.max(1, …)` 改成 `Math.max(battle.defeatThreshold, …)`：死斗里喝药不能把 0 抬成 1。
- **回合末回复不复活 0 血单位**（任何 stake）。这条是行为变更：旧实现里「毒伤打到 0 → 回合末 regen 回 2 → 继续打」不再成立。`hard` 的 1 血回复不受影响。

### 1.2 迁移

默认 `deaths` 是行为变更：jjk 现有 5 场战斗不写 `stake` 会全部变死斗。迁移时显式标：

- `ev-hv-06-block` → `deaths`（原本就是死局）；
- 其余 4 场 → `hard`。

挡枪这条改走 `deathRoutes` 之后（同一事实只留一条路）：

- `end-hv-early-death` 的 `triggerConditions` 清空（死亡路径不读它，留着会触发加载期 warn）；
- 同时删掉 `worldState: hvEarlyDeath` 终止条件 —— 它和 deathRoute 说的是同一件事，
  留着就是两条路（虽然路由先 `markTerminated`、终止边界会空转，但读起来是两个真相）。

## 2. 战评模块（战斗判定 + 评价 + 成长）

新增 `packages/game-core/src/v2/battle-evaluation.ts`，把现在散在 `battle.ts` 的东西收进来：

| 阶段 | 职责 | 现在的位置 |
|---|---|---|
| `judge` | 死亡名单、胜负、killer、stake、defeatState | `markDeaths` / `checkBattleEnd` 移过来（判负行为按 §1.1 改） |
| `report` | 产 `BattleResult`（资源、伤害、crits、statusStacks、四侧 power）并写 `state.lastBattleResult` | 新 |
| `grade` | 按 `combat.evaluation.grades` 匹配，首个命中 | 新，P2 上屏 |
| `hooks` | 默认 hooks → 事件引用 set（按顺序）→ 成长/奖励 | 新 |
| `settle` | 算收场资源表（`hpOnDefeat` + 资源夹取）、回写、history | 部分在 `finishBattle` |

**边界顺序不可换**：`judge → report → grade → hooks` 必须在 `finishBattle` **之前**跑完。
理由：`finishBattle` 会把 `battle.player.statuses` 这份镜像整体丢弃，黑闪层数、crits、
每单位伤害都只活在镜像里；先收场再战评，读到的就是空的。

`report` 与 `finishBattle` 共用同一个纯函数 `settleResources(battle, state, lookup)`：
它返回收场后的 `{ hp, mp, resources }`（已过 `hpOnDefeat` 与上限夹取）。
`report` 拿它填 `BattleResult`，`finishBattle` 拿它写世界——**同一个数只算一次**。

配置：

```yaml
combat:
  evaluation:
    grades:
      - { id: flawless, label: 完胜, when: [{ outcome: victory }, { metric: hpRatio, gte: 0.8 }] }
      - { id: hard-won, label: 苦战, when: [{ outcome: victory }] }

    # 默认钩子：世界层声明，通常战斗都跑，事件不需要引用
    hooks:
      - id: black-flash-growth
        when:
          - { statusStacks: black-flash, gte: 1 }
        effects:
          - type: advanceTalent
            talent: t-black-flash
            amount: { metric: statusStacks, status: black-flash, max: 3 }
            create: true

    # 具名组：只有战斗事件用指针引用时才跑；支持多钩子、多组
    sets:
      mahoraga-awakening:
        - id: mahoraga-growth
          when: [{ outcome: victory }, { metric: rounds, gte: 10 }]
          effects:
            - { type: advanceTalent, talent: t-ten-shadows, amount: 1, create: true }
```

```yaml
# events.yaml
settle:
  combat:
    evaluation: [mahoraga-awakening, other-set]   # 数组；按顺序结算
```

- **默认钩子不由引擎内置**（引擎不认识黑闪）；"不需要注册"指事件不用引用。
- 结算顺序 = 默认 hooks（声明顺序）→ 事件引用的 set（按数组顺序）→ 每个 set 内部声明顺序。
- **不做 replace**；后续如果需要，设计成互斥组。
- 战评 hook 在死亡路由之前跑（死了也吃成长）；P1 效果：`advanceTalent`、`setFlag/adjustFlag`、`log`；P2 接完整世界效果 DSL。
- `evaluation` 引用的 set 不存在 ⇒ 加载期拒。set 里 hook id 全模板唯一（诊断用）。

`evaluation hooks` 的 `when` 是一套**只读战果**的窄条件（`BattleEvalCondition`）：

```ts
type BattleEvalCondition =
  | { outcome: "victory" | "defeat" | "flee" }
  | { grade: string }
  | { metric: BattleMetric; eq?: number; ne?: number; gt?: number; gte?: number; lt?: number; lte?: number }
  | { statusStacks: string; eq?: number; gt?: number; gte?: number; lt?: number; lte?: number }
  | { anyMatch: AnyMatch };

type BattleMetric =
  | "hpRatio" | "rounds" | "damageDealt" | "damageTaken" | "crits" | "kills" | "powerRatio";
```

## 3. BattleResult（战果）

由 `judge/report` 产出，`state.lastBattleResult` 持久化（死亡事件在后续轮次重载后仍能读）。

```ts
interface ResourceSnapshot {
  id: string;        // hp / mp / 自定义
  label: string;
  current: number;
  max: number;
  ratio: number;
  preset: boolean;   // hp/mp = true
}

interface BattleResult {
  eventId: string;
  outcome: "victory" | "defeat" | "flee";
  stake: string;
  defeatState: "yielded" | "down" | "dead";
  grade?: string;
  rounds: number;

  player: {
    hp: number;          // 收场值：已过 hpOnDefeat 与夹取（与写回世界的数一致）
    maxHp: number;
    resources: ResourceSnapshot[];       // hp/mp + 全部自定义资源
    attributes: Record<string, number>;  // 世界状态有效属性（不含战斗临时态）
    power: number;                       // 开场
    powerEnd: number;                    // 收场（世界态，不含战斗临时态）
    damageDealt: number;
    damageTaken: number;
    crits: number;
    hits: number;
    kills: number;
    statusStacks: Record<string, number>; // 只含 visibility: known 的状态
  };

  sides: { player: number; ally: number; enemy: number; neutral: number }; // 全部开场值
  // 派生聚合不落盘：playerSide = player + ally，opposition = enemy + neutral

  enemies: Array<{
    ref: string;                 // characterId
    name: string;
    tier: "minion" | "hero";
    power: number;               // 开场
    damageByPlayer: number;
    damageToPlayer: number;
    defeated: boolean;
    killer: boolean;
    summonedByPlayer: boolean;
  }>;

  killer?: {
    ref: string;
    name: string;
    tier: "minion" | "hero";
    power: number;
    summonedByPlayer: boolean;
  };

  deaths: Array<{
    id: string;                  // 战斗实例 id（玩家 = selfId）
    ref?: string;                // characterId（玩家为空）
    side: "player" | "ally" | "enemy" | "neutral";
    name: string;
  }>;
}
```

- `killer` 是致命一击来源；条件判负（友军全灭 / 撑回合失败）时为空。
- `killer` 只由**技能伤害**产生：`afterDamage` 的加成仍算施放者，持续伤害（`onRoundEnd`）与
  环境伤害不产生 killer——状态实例上没有「谁上的」这一格，凭空补一个来源就是编数据。
  hp 费用（技能反噬）与献祭同理：自己把自己付死，没有凶手。
- `enemies[].damageByPlayer` 支撑"对宿傩造成了不小的影响"。
- `summonedByPlayer` 支撑"被自己召唤的魔虚罗打死"。
- `statusStacks` **只收 `visibility: known`**：隐藏状态的名字/层数不进存档、不进投影（ADR-002 纪律）。
- 资源统一 `id/label/current/max/ratio/preset`；`hp/mp` 仍是 `V2Player` 的基础字段，状态存储不变。
- 生命周期：`createBattle` 时清空（新一场战斗开始，上一场不再是"最近战果"）；
  死亡事件可能在这之后好几轮才结算，所以**不能**按轮次清。

## 4. 战斗力（Power）

### 4.1 默认口径：底层基属性

**只用可写的基础属性求和**，不做派生属性或 signed 修正的直接相加：

- 派生属性（`cursedEnergyOutput / Control / Efficiency / critRate / evadeRate / mpCostRate`）
  先折算回它的 `from` 基属性；折算的产物是**集合**，不是重复相加
  （`total → output / control / efficiency` 三条都指回 `total`，`total` 只算一次）；
- 排除 `signed: true`（典型：`mpCostRate` 是负数，直接加会"减战力"）；
- 排除 `hidden`；
- 最终集合必须是**基础数值属性**。

### 4.2 默认属性集合怎么来

每个模板算一次，`WeakMap<WorldTemplateV2, Weights>` 缓存（不是每场战斗现推，也不往模板对象上挂字段——
模板是只读的）。从模板推并集，取每条的基属性依赖：

1. `resources.*.perAttribute` 的键；
2. 战斗技能 `damage[].scaleBy` / `hitCheck.attacker / defender` 引用的属性；
3. 战斗钩子 `when[].chance.attribute` 引用的属性；
4. 属性角色（`role: critRate / evadeRate / mpCostRate`）的派生依赖基属性；
5. 若集合为空 ⇒ 退回"全部可见（非 hidden）、非 signed 的基础数值属性"。

解析时**递归**沿 `derived.from` 走到基础属性（ADR-074 已在加载期拒绝环依赖）；
`signed` / `hidden` / 非 `number` 的键在每一层都被剔除。

```ts
power(actor) = Σ effective[baseAttr] × weight   // 默认 weight = 1
```

jjk-2006 的推导结果（写进注释，便于回归）：
`{ cursedEnergyTotal, intellect, physique, agility }`。
`intellect` 是三条精神系技能的 `hitCheck.defender` —— 防御面也算战斗面；
`luck / reputation` 不被任何战斗面引用，自然不进集合。

### 4.3 模板覆盖

```yaml
combat:
  evaluation:
    power:
      weights: { cursedEnergyTotal: 2, physique: 1.5, agility: 1.5 }
```

- `weights` 的键必须是基础、非 signed、非 hidden 数值属性；加载期拒绝派生 / signed 键。
- 写了 `weights` 就**只算这些键**（不并默认集合）；`weights` 为空表拒载。
- 默认不做 0–100 归一；比值条件已经抵消量纲，绝对阈值由模板写。

### 4.4 四侧与比值

- 四侧全部取**开场**快照：`sides.player` 也是开场 power（§0 #16）。
  理由：死亡瞬间的 power 含战斗内增减益，与「敌方开场实力」不可比；
  「区完了」要问的是「你本来比他强多少」，不是「你死的时候还剩多少」。
- 开场快照在建场时算（`createBattle` → `BattleState.powerStart`），
  单位用 `buildUnit` 产出的有效属性（含 `levelScale`、装备、开场状态）。
- 玩家 `powerEnd` 用世界态有效属性（不含战斗镜像状态），只进 `BattleResult`，不参与 `ratio`。
- 条件用命名侧比值（不需要引擎预设计算字段）：

```yaml
- { battle: { ratio: { left: playerSide, right: enemy, gte: 3 } } }
```

`left/right` 支持：`player / ally / enemy / neutral / playerSide / opposition`。
例：`playerSide = player + ally`，`opposition = enemy + neutral`。

- **除零**：`right > 0 ⇒ left / right`；`right == 0 && left > 0 ⇒ +∞`（`gte` 成立）；
  两侧都 0 ⇒ `1`。不产生 `NaN`。
- 不提供 `all`：分母含中立，语义是"全场总和"，没有真实判据需要它。
- 任意两侧比值不做；真需要时再加，不然条件 DSL 会先变成表达式语言。

> 修正：不能再用 `killerTier: minion` 判"区完了"。必须看**敌方全体与自己的实力差**，
> 否则"被絹索的二级咒灵补刀"也会误判。

## 5. 死亡路由（`world.deathRoutes`）

### 5.1 定位

- **`deathRoutes` 是死亡结局的唯一权威判定**。
- `endings.triggerConditions` **不再参与死亡结局选择**；死亡路由直接 `endingId` 引用（一处判定，一处引用）。
- `endings` 目录仍保留，服务非死亡终止（时间到、主动结束、worldState）。
- 新增 `resolveEndingById(state, templates, endingId)`：只做记录与叙事（title / summary / masked），
  **不跑** `triggerConditions` / `unlockConditions` / `priority` / `exclusiveGroup` —— 那些是"决胜"，
  死亡已经由路由决完了。隐藏结局的 `masked` 照常生效。
- 旧 `endings.yaml` 的 `deathRoute` 删除，不迁移。

### 5.2 协议

```ts
interface DeathRoute {
  id: string;
  when?: DeathCondition[];   // AND；[] = 兜底
  then: DeathAction;
}

type DeathAction =
  | { kind: "ending"; endingId: string }   // 必填：死亡结局唯一权威
  | { kind: "event"; eventId: string };    // 事件；结算后自动 hp1，除非 playerDeath
```

- 路由顺序 = 声明顺序，首个命中；**必须有 `when: []` 兜底**（加载期校验，且兜底之后不得再有路由）。
- `then.kind: "event"` 的目标事件**只能是 `kind: normal`**：随机转盘要额外一轮确认，
  战斗会在 hp 0 上立刻再判负——这两种"死亡戏"都无法收敛。
- `when` 可混用：

```ts
type DeathCondition =
  | TaskCondition                                  // flag / attribute / npcState / relation / time / anyMatch…
  | { battle: BattlePredicate }
  | { cause: "battle" | "event" | "world" }
  | { deathDepth: { eq?: number; gte?: number; lte?: number } };

interface BattlePredicate {
  stake?: string;
  defeatState?: "yielded" | "down" | "dead";
  killer?: string | { ref?: string; tier?: "minion" | "hero"; summonedByPlayer?: boolean };
  damageTo?: { ref: string; gte?: number; lte?: number };
  playerPower?: { gte?: number; lte?: number };
  ratio?: { left: SideName; right: SideName; gte?: number; lte?: number };
  grade?: string;
  rounds?: { gte?: number; lte?: number };
}
```

- `battle` 条件在 `cause != battle` 时为 false；`anyMatch(battle.*)` 同理。
- **`battle` 谓词里没有任何 HP 字段**（§0 #17）。死亡已由 `defeatState: dead` 信号化，
  再拿血量当死亡判据就违反 R-EN-07；"死时还剩多少血"属于战评 `grade`，不属于死亡路由。
- `killer` 的字符串形态在加载期归一成对象，运行期只有一种判法。

### 5.3 事件路由

- `then: { kind: "event", eventId }`：把事件放进槽（`from: "death"`），**不终止**。
- 事件结算后：
  - 若事件里出现 `playerDeath` 信号 ⇒ **跳过自动 hp1**，带 `cause: "event"` 重新进死亡路由；
  - 否则 ⇒ `hp = max(1, hp)`，清 `deathPending`，继续游戏。
- 无 `continue` / `revive` 字段；"死亡后不一定游戏结束"由事件 + 自动 hp1 表达。
- `onDefeat.nextEventId` **在死斗里被死亡路由覆盖**：先落 `onDefeat` 的效果（旗标要留），
  再由路由决定槽；被顶掉的 `nextEventId` 不执行（加载期对 `stake: deaths` + `onDefeat.nextEventId` 报 warn）。
- `playerDeath` 效果：`{ type: "playerDeath", reason?: string }`，把 hp 置 0、落 `deathSignal`。
  它不直接终止，由死亡路由决定结局还是再事件。可在事件 / 行动 / 世界效果里出现；
  **不在战斗钩子里出现**（战斗中判死归 `stake`）。
- 递归不死：`deathDepth` 是**当前死亡链**的深度（进入路由即 +1，`deathPending` 清除时归零），
  持久化并暴露给条件；**引擎不设上限、不兜底**，模板自己用 `deathDepth` / 天赋 / flag 保证收敛
  （"赖着不死"的天赋由模板判）。想统计"这辈子死了几次"用模板 flag，不用 `deathDepth`。

### 5.4 例子

```yaml
# world.yaml
deathRoutes:
  # 被自己召唤的魔虚罗打死：不吃压力（先判，避免被实力差抢走）
  - id: own-summon-kill
    when:
      - { battle: { killer: { summonedByPlayer: true } } }
    then: { kind: ending, endingId: end-no-pressure }

  # 敌方全体远低于自己，却被补刀：区完了（看实力差，不看 killerTier）
  - id: humiliation
    when:
      - { battle: { ratio: { left: playerSide, right: enemy, gte: 3 } } }
    then: { kind: ending, endingId: end-humiliated }

  # 面板低，但重创宿傩：自豪吧，你很强
  - id: sukuna-proud
    when:
      - { battle: { killer: npc-sukuna } }
      - { battle: { damageTo: { ref: npc-sukuna, gte: 80 } } }
      - { battle: { playerPower: { lte: 30 } } }
    then: { kind: ending, endingId: end-proud }

  # 模仿絹索：两个跨战斗 flag，死亡事件转移肉身
  - id: kenjaku-transfer
    when:
      - { flag: copiedInnateTechnique, eq: true }
      - { flag: kenjakuPartEaten, eq: true }
    then: { kind: event, eventId: ev-death-transfer }

  - id: default-death
    when: []
    then: { kind: ending, endingId: end-default }
```

`kenjakuPartEaten` 由战评 hook 落（战评在死亡前跑，所以同场打伤絹索、随后被打死也来得及）：

```yaml
combat:
  evaluation:
    hooks:
      - id: kenjaku-part
        when:
          - anyMatch:
              over: battle.enemies
              where:
                - { field: ref, eq: npc-kenjaku }
                - { field: damageByPlayer, gte: 1 }
        effects:
          - { type: setFlag, id: kenjakuPartEaten, value: true }
```

跨战斗由 flag 承担；`anyMatch` 只判本场伤害。模仿絹索术式还需要 `copiedInnateTechnique`
（模仿生得术式）这个 flag，由前置事件/技能落。

## 6. `anyMatch`（新条件）

```yaml
anyMatch:
  over: battle.enemies      # 白名单集合
  where:
    - { field: ref, eq: npc-kenjaku }
    - { field: damageByPlayer, gte: 1 }
```

- `over` 白名单与字段：

| 集合 | 字段 |
|---|---|
| `battle.enemies / battle.allies / battle.neutrals` | `ref / name / tier / alive / damageByPlayer / damageToPlayer / defeated / killer / summonedByPlayer` |
| `player.statuses` | `statusId / kind / stacks / progress` |
| `player.inventory` | `itemId / count` |
| `npcs` | `id / name / lifecycle / isEnemy / visibility` |
| `relations` | `from / to / kind / value / scope / frozen` |

- **单位集合没有 `hp`**：战斗血量的逐单位精确值既不该进条件，也会把 R-EN-07 从后门放回来。
  需要"他伤得多重"就用 `damageByPlayer` / `damageToPlayer`。
- 集合里**任意一项**满足 `where` 的全部谓词即 true；按集合顺序短路，无随机。
- 谓词：`eq / ne / gt / gte / lt / lte / in`。字段类型决定可用谓词：
  数值字段只收 `gt/gte/lt/lte/eq/ne`，字符串/布尔只收 `eq/ne/in`（加载期按字段表校验）。
- 数据源：
  - 战评 hook 里读**刚生成的 `BattleResult`**；
  - 死亡路由 / 普通事件里读 `state.battle`（若还在）否则 `state.lastBattleResult`；
  - 两者都没有 ⇒ `battle.*` 集合为空 ⇒ false（不猜）。
- 底层改动：`TaskCondition` 新增一种 flat 条件；两个 evaluator（`engine.checkCondition` /
  `condition-evaluator.checkAllConditions`）都要吃 item 上下文；加载期校验集合与字段。

## 7. 天赋阶梯（成长型天赋）

### 7.1 数据模型

```ts
// StatusInstance（仅 kind: talent）
progress?: number;
tiersApplied?: number;      // 已结算过 grant 的阶数（0..tiers.length）

// 天赋定义
progress?: { label?: string; max?: number; initial?: number };

tiers?: Array<{
  at: number;               // 进度阈值；当前阶 = 满足 at <= progress 的最高一阶
  tier: string;             // 品级 id（走 ui.qualityStyles）
  effects: {
    attributeModifiers?: Record<string, number>;  // 持续加成
    combat?: CombatFacet;                         // 持续战斗面（含 hooks）
    grant?: Effect[];                             // 到达这一阶时一次性结算（如 grantAllocation）
  };
}>;
```

- **名字 / 通用描述只在天赋层写一次**，阶梯只有 `at / tier / effects`。
- 阶效果**按面替换**：写了 `attributeModifiers` 就替换属性面，写了 `combat` 就替换战斗面；
  没写的面沿用天赋的基础定义。同一面内是替换（不累加）——要累加就把总数写在这一阶。
  为什么不整体清空：只改品质的阶会把天赋自带的常驻钩子一并抹掉。
- 没有 `tiers` 的天赋 = 静态天赋，行为不变。
- 读取统一入口 `activeTierOf(def, inst)`；`effectiveAttributes / collectHooks / multiplierOf /
  costMultiplierOf / critOf / ledger / 投影` 全部走它。
- `progress` 不是层数：天赋实例永远一份，UI 显示「黑闪 · 觉醒 3 次」，不是「黑闪 ×3」。
- `advanceTalent` 是唯一写入口：单调递增、夹 `max`、不碰 RNG；跨阶时按顺序结算各阶 `grant` 一次。
  **只作用于 self**（没有 `who`）：P1 不给 NPC 做天赋成长；`grantAllocation` 本来就是玩家专属。
  `amount` 求值为 0 ⇒ 整体 no-op（`create: true` 也不建实例）。
- 非成长授予（开局 / 角色卡）用 `applyStatus`：按 `progress.initial`（缺省 0）初始化，
  `tiersApplied` = 初始进度已覆盖的阶数；**不结算阶 grant**。
  `advanceTalent(create: true)` 从 0 开始再加 `amount`，避免首次双计。
- `statuses` 在 `transplantActor` 的 `body` 组：夺舍会带走天赋进度。六眼现在也是这样；
  黑闪的"咒力核心"算身体还是灵魂需要另行决定。

### 7.2 黑闪阶梯（模板数据）

```yaml
- id: t-black-flash
  kind: talent
  name: 黑闪
  description: ...
  progress: { label: 觉醒次数, max: 100, initial: 1 }
  tiers:
    - at: 1
      tier: purple            # 模板 ui.qualityStyles 的键
      effects:
        grant:
          - { type: grantAllocation, id: bf-1, budget: 1, targets: [...] }
    - at: 4
      tier: pink
      effects:
        grant:
          - { type: grantAllocation, id: bf-4, budget: 2, targets: [...] }
    - at: 8
      tier: orange-red
      effects:
        grant:
          - { type: grantAllocation, id: bf-8, budget: 3, targets: [...] }
```

- `0 = 无天赋`，不会走这里；天赋第一次获得至少 1。
- 每次跨阶授予该阶加点（budget 是模板数据）。
- 连续跨阶**不合并、不排队**：同一时刻只能挂一条 pending，跨两阶就是模板写错（见 §10-1）。
  模板要保证一次只跨一阶；黑闪的 `max: 3` 已经保证单场最多跨一阶。
- `ui.qualityStyles` 需要补 `orange-red`（当前只有 `orange`）。
- 黑闪仍由**世界钩子**触发（不是天赋门槛）：`afterHit` + `crit` + `cursedEnergyControl × 0.3%`
  → `critExponent 2.5` + `applyStatus black-flash`。
- 战斗内 `black-flash` 仍是 `kind: battle`、`stacking: stack`、`damageDealt: 0.5`（定值，
  `stacksPerLayer` 未开）；层数只做计数。
- 战后由默认战评 hook 读 `statusStacks["black-flash"]` → `advanceTalent(t-black-flash, min(n,3), create: true)`。

## 8. 运行时顺序

### 8.1 战斗收场

```
battle over & defeat
  → judge：死亡名单 / 胜负 / killer / stake / defeatState
  → report：BattleResult（资源、伤害、crits、statusStacks、四侧 power）   ← 镜像还在
            资源用 settleResources() 的收场值，不读裸镜像
            **同时写 state.lastBattleResult**（后续死亡路由 / 死亡事件读它）
  → grade：按 grades 表匹配
  → evaluation hooks：默认 hooks → 事件引用 sets（按顺序）→ 成长/奖励
  → finishBattle：写 settleResources() 的结果、推 history
  → state.battle = null
  → onVictory / onDefeat / onFlee 效果（旗标在这里落）
  → if defeatState == "dead"：
       deathRoutes 首个命中
         → ending：resolveEndingById → markTerminated
                    （跳过 nextTurn / postSettleJudgements / 终止条件）
         → event：assignSlot({from:"death"}) 覆盖 successor
                  state.deathPending = { routeId, eventId }；state.deathDepth = 1
  → 未终止/未待死：postSettleJudgements → nextTurn
  → terminationConditions（非死亡终止；battleDefeat 只作非死亡剧情终止用）
```

**三处与现实现的冲突（本轮修正）**：

1. `finishBattle` 现在写死 `hp = 1`。改为 `hpOnDefeat`；死斗写 0。
2. 现在 `applyDeathRouteInPlace` 排在 `nextTurn` **之后**。死斗必须在 `nextTurn` 之前落结局/落死亡槽，
   否则 `nextTurn` 会先推进时间、跑 NPC/池，玩家在"死亡"状态下多过一轮。
3. `onDefeat.nextEventId` 会先占槽，死亡路由再抢。顺序改为"先效果、后路由"，并明确后者覆盖前者。

`checkBattleEnd` 保留为薄包装（3 处测试直接调用它），签名加可选 `lookup`（`hp_below` 现算 maxHp 用），
内部转调 `judge`；`markDeaths` 迁走后不留同名双份。

### 8.2 死亡事件结算

三条入口共用同一个死亡边界 `deathBoundary(state, cause)`，位置固定在**内容落地之后、回复/后续判定之前**：

```
advanceTurnV2：时间账 → 行动效果 → deathBoundary(cause="world")
              → 未终止：regen（deathPending/deathSignal 时跳过）→ postSettleJudgements
              → nextTurn → 终止条件

chooseOptionV2：选项效果 → deathBoundary(cause="event")
               → 未终止：postSettleJudgements → nextTurn → 终止条件

battleActionV2：见 §8.1
```

`deathBoundary` 内部：

```
if state.deathSignal：hp = 0；清 signal；depth += 1；按 cause 再入 deathRoutes
else if state.deathPending：hp = max(1, hp)；清 deathPending；depth = 0
else return
再入路由：ending ⇒ markTerminated；event ⇒ assignSlot(from:"death")、deathPending = { routeId, eventId }
```

- `deathPending` 期间**不跑** NPC 自主行动 / pool / 时间表（世界在死亡现场停住）。
- `deathPending` / `deathSignal` 存在时**跳过该轮 regen**（死人不回血）。

### 8.3 守卫

- `advanceTurnV2` / `battleActionV2` / `useItemV2`：`state.deathPending` ⇒ 抛 `death_pending`。
- `chooseOptionV2` **不拦**：它就是来结算死亡事件的。
- 槽被死亡事件占住时，普通事件天然被 `pending_event_required` 挡住，`death_pending` 是第二道锁。

### 8.4 持久化

`lastBattleResult` / `deathPending` / `deathDepth` 全部进存档；
`deathSignal` 也存（边界内瞬态，但存档可能落在两次写之间，读档时要能续上）。

## 9. 校验与迁移

**加载期校验**

- `settle.combat.stake` 必须存在于合并后的 `combat.stakes`（内置 + 模板）；`defaultStake` 必须存在。
- `stake.defeatState` 枚举；`hpOnDefeat.mode/value` 合法（`value` 非负整数）。
- `deathRoutes`：route id 唯一；`endingId` 必须存在；`eventId` 必须存在且 `kind: normal`；
  必须有 `when: []` 兜底，且兜底之后无路由；`battle.*` 不得出现 HP 字段，
  `attribute` 条件不得指向 hp（R-EN-07 的两道门）。
- 死亡路由引用的 ending 若带非空 `triggerConditions` ⇒ warn（死亡路径忽略它，条件应写在 route 上）。
- `power.weights` 的键必须是基础、非 signed、非 hidden 数值属性；派生 / signed 键拒绝；空表拒绝。
- `evaluation.grades`：id 唯一、`when` 非空、`when` 里不得出现 `grade`（自引用）。
- `evaluation.sets` 被事件引用却不存在 ⇒ 拒；`evaluation.hooks[].id` 全模板唯一。
- `anyMatch.over` 白名单、`where[].field` 按集合校验、谓词与字段类型匹配。
- `tiers`：`at` 升序唯一；`tier` 是 `ui.qualityStyles` 的键（与 `status.quality` 同一口径，
  不做加载期白名单）；有 `tiers` 必须有 `progress`；
  `initial` 与每个 `at` 都要 `<= progress.max`（否则永远不可达，warn）；
  顶层 `attributeModifiers/combat` 与 `tiers` 不要同时写（warn）；`grant` 只在 `tiers[i].effects` 里。
- `advanceTalent.talent` 必须是 talent；`amount` 为数字时必须 > 0，为 metric 形态时运行期求值、0 即 no-op；
  `create` 缺省 false；`amount.metric` 只允许在 `evaluation.hooks` 里（世界效果没有战果上下文）。
- `playerDeath` 只允许出现在事件 / 行动 / 世界效果里，不出现在战斗钩子 / 技能里。

**迁移**

- 旧 `deathRoute` 删除（`EndingConfigSchema.deathRoute`、`resolveDeathRoute`、`applyDeathRoute` 一起删）；
  模板改用 `world.deathRoutes`。
- 默认 `deaths` 是行为变更：jjk 5 场战斗显式标 `stake`（§1.2）。
- 模板指纹变化，旧档 `template_content_drift` 拒载；`progress / tiersApplied / lastBattleResult /
  deathPending / deathDepth / powerStart` 均为可选字段，旧夹具不必全改。
- `pendingAllocation` 形状不变，不做迁移。
- `battleDefeat` 终止条件保留，但只服务非死亡剧情终止；死亡结局不再走 `terminationConditions`。
- `hp_below` 只加在 `BattleConditionSchema`，不影响 `player_down` 旧语义（阈值随 stake 是另一条改动）。

## 10. 未定项裁决（上一版 §10）

### 10-1 连续跨阶加点 → **引擎不合并、不排队；模板负责一次只跨一阶**

`grantAllocation` 维持现状：同一时刻只有一条 pending，同 id 幂等跳过、不同 id 抛错。
`advanceTalent` 若一次跨两阶、两阶都给加点，第二笔会撞上第一笔 —— 这是**模板错误**，不是引擎要兜的场景。

- 理由：用户裁决「连续跨阶加点由模板侧处理，引擎不兜底」。合并预算会改写法（`budget` 是谁的？），
  排队则要改存档 / 端点 / UI 三处，而且会掩盖"模板把两笔奖励挤在一次结算里"的设计问题。
- 模板怎么写对：单场成长量夹住（黑闪 `max: 3`，从 1 起跳最多到 4，只跨 `at: 4` 一阶）；
  真要一次跨多阶，就**只在最高阶给加点**，低阶只给 `effects`（属性/战斗面）。
- 诊断：运行期抛 `allocation_conflict: <pendingId> vs <newId>`，带两个 id；
  测试里只要造一次「+8 跨三阶」的用例，就能把这条守死。

### 10-2 非成长授予的初始进度 → **初始化进度，不补加点**

`applyStatus` 新实例写 `progress = initial ?? 0`、`tiersApplied` = 初始进度覆盖的阶数；不结算 `grant`。
已存在的实例**不重置**进度（再授予是幂等）。

- 理由：开局自带天赋的人已经在开局 DAG 里加过点；再补一笔等于双计。
  阶的**展示与持续效果**照常生效（黑闪初始 1 就是紫色），只是不给那一笔一次性预算。
- 被否：开局补 grant —— 会造出一个世界内 `pendingAllocation`，与开局加点节点并存，玩家要点两次。

### 10-3 默认战斗力集合 → **保留推导，每模板算一次**

保留 §4.2 的四类引用推导，但只在**每模板一次**的 `WeakMap` 缓存里算；不采用"全部可见基础数值属性"。

- 理由：全量集合会把 `luck / reputation` 也算进战力，`reputation` 还是可刷的；
  推导的复杂度是一次性的，且能解释"为什么是这几条"。
- 兜底保留：推导为空 ⇒ 全部可见基础数值。模板可用 `weights` 完全接管。

### 10-4 四侧 ratio 命名 → **六个名字，不做任意两侧**

`player / ally / enemy / neutral / playerSide / opposition`。

- 不加 `all`（分母含中立，语义是全场总和，没有判据需要它）；不做任意两侧
  （条件 DSL 一旦接受两个任意名字，下一步就会有人要求四则运算）。

### 10-5 事件致死与 `playerDeath` → **确认，且统一到一条规则**

自动 hp1 只在"死亡链内、且没有 `deathSignal`"时生效。任何 `playerDeath` 都触发路由，
`depth += 1`，`cause` 由边界给（event / world / battle）。**不单独给 `cause=event` 设默认路由**：
兜底路由 `when: []` 已经覆盖，模板不需要写两套。

### 10-6 grade 上屏 → **先算不显示**

`grade` 进 `BattleResult`（路由与 hook 可用），P2 再做展示；P1 不上屏、不进投影。
`grades` 表按声明顺序首个命中；`grade` 只读战果指标，不读别的 grade。

### 10-7 互斥组 → **继续推迟**

死亡跳过成长、set 互斥都等这套跑通再设计。当前用"先结算全部、模板自己写条件"表达。

## 13. 能力缺口（待立 ADR）

> 这两条都是 ADR-075 落地时暴露的**协议缺口**，不是这一版能顺手补的实现细节。
> 记录在这里是为了不丢，开工前单独立 ADR。

### 13-1 战评 → NPC 死亡：战果知道谁倒下了，世界不知道

**现象**

- `BattleResult.deaths[]` 已经能列出"这一场谁倒下了"（player / ally / enemy / neutral），
  但**没有任何规则把它写回世界**。`writeBackNpc` 明确拒绝写 `lifecycle`（打到 0 血 ≠ 剧本要他死），
  `setNpcLifecycle` 是唯一入口，只能由模板效果显式驱动。
- 具体后果：被打倒的敌方 NPC 下一场**满血回来**（`writeBackNpc` 对死者直接 `return undefined`，
  `npc.hp` 根本没被写），人物列表里也照常挂着。
- 无法表达"战败但留活口"与"当场击毙"的差别：jjk 第六幕的甚尔是"挡住三回合"的对手，
  不该因为 `hp` 归零就被判死；反过来，某些敌人被打倒就该退场。

**为什么现在做不到**

- `BattleResult.enemies[].defeated` 只有"单位不再行动"这一层，没有"死 / 倒 / 撤"的语义；
  `deaths[]` 里也没有 `killed` 与 `defeated` 的区分。
- `killer` 只记**玩家**的致命一击来源；敌方之间的击杀没有任何记账。
- 召唤物（`summonedBy`）、未实例化杂兵（`state.npcs` 里没有）、英雄档 NPC 是三条不同的路：
  前两者不该写 `lifecycle`，后者才需要。
- 时机：必须在 `finishBattle` 之后、`onDefeat` 效果与死亡路由之前 —— 否则"战评读到的世界"
  和"玩家看到的世界"不是一个。

**需要什么**

1. **战果 → 生命周期的声明式映射**：`deaths[]` 的 `side / ref / tier / defeated` + 条件
   → `setNpcLifecycle`（或更窄的 `battleCasualty` 效果）。
2. **"打倒"与"杀死"的区分**：是"hp 归零即死"，还是"要过一道 `killed` 判定"（最后一击、处决、
   模板 flag）；这决定 `lastHitBy` 是否足够。
3. **作用域与例外**：召唤物 / 杂兵 / 英雄 NPC 各走哪条；`shiki-mahoraga` 是 `characterId`
   不是 `state.npcs` 实例，绝不能被写成 `inactive`。

**候选（都还没裁决）**

- **A. `world.combat.casualties`**：`[{ when: [...], apply: [{ npcId, state, reasonCode }] }]`，
  `when` 读 `BattleResult`（含 `deaths`）。声明式、可加载期校验；但"每个 NPC 一条"会很长。
- **B. 收场效果 `battleCasualties`**：只允许出现在战斗 `onVictory/onDefeat/onFlee` 或死亡路由里，
  由模板逐条写。灵活，但和 A 的边界需要划清。
- **C. 默认策略 + 例外表**：`combat.casualties.default = { defeated: alive, killed: inactive }`。
  最省字，但把"留活口"变成例外，和本项目"显式优先"的口径相反。

**待裁决**：`deaths[]` 是否拆 `defeated / killed`；`killer` 是否要覆盖敌方互杀；
`reasonCode` 由模板给还是引擎给；"战斗中死、事件里复活"允许到什么程度。

### 13-2 胜利条件的运行时变更：魔虚罗的调伏仪式表达不了

**现象**

`CombatSettle.victory` 是**静态数组**，数组内是 **OR**（`victory.some(conditionMet)`），
没有 AND / 嵌套。`sk-ten-mahoraga` 召出的魔虚罗是 `faction: neutral`，不在 `battle.enemies` 里，
所以：

- `all_enemies`（胜利缺省）完全看不见它 —— ADR-014 现行口径就是"打死它不送胜利"；
- 想写"敌人全灭 **且** 魔虚罗倒下"也写不出来：两个条件在数组里是 OR，
  而且 `all_enemies` 一成立战斗当场就赢了，根本轮不到 `unit_down`。

**为什么现在做不到**

- 没有"战斗目标"这个运行时对象，`settle.victory` 建场后只读；
- 没有条件组合子（AND/OR 嵌套），只有"数组即 OR"；
- 没有"目标变更"的写入口：技能 / 召唤 / 钩子 / 状态都改不了 `victory`。

**需要什么**

1. **复合条件**：至少 `all` / `any` 两层（`ConditionGroup`），`victory` / `defeat` 各一棵；
   现有数组可无损映射成 `any`。
2. **运行时目标**：`battle.objectives = { victory, defeat }`，建场时从 `settle` 初始化；
   由新效果 `setObjective`（或钩子效果）替换 / 追加，**仅本场有效**。
3. **中立单位作为目标**：`unit_down` 已经查 `allUnits`（含中立），复合条件一到位就能组合；
   不需要把魔虚罗塞进 `enemies`（那会让它被"敌方全灭"直接算死，ADR-014 已否）。
4. **还原语义**：魔虚罗被收回 / 消失后目标是否回退？调伏仪式一旦开始应当**不回退**，
   但协议要能明确写"不回退"。

**待裁决**：目标变更的作用域（本场 / 本事件 / 本局）；是否允许中途还原；
`victory` 与 `defeat` 同时成立时的优先级（现在是先判胜、后判负）；
"调伏成功"是否要单独的战果字段（`objectiveCompleted`）供战评 / 死亡路由读。
