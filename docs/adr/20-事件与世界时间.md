**这一层的不变量**：**世界自己会往前走**，不需要玩家踩到某个分支。

## ADR-007 D1 · 世界时间表 `scheduledFacts`

```yaml
scheduledFacts:
  - id: fact-gojo-takes-megumi
    note: 一年级编成，五条把伏黑惠要到自己名下
    when: [{ time: { gte: { value: 4538, unit: day } } }]
    effects:
      - { type: addRelationEdge, fromId: npc-gojo, toId: npc-megumi, kind: disciple, scope: public }
```

语义**五条**，缺一条就会退化成「有人没登场」的 bug：

1. **不占事件槽、不进历史、不等玩家确认**。玩家看到的是后果（卡上多了一个人、关系行多了一条）。
2. **每轮 tail 求值一次**（结算已落地、时间已推进），所以判断与这一轮玩家做了什么无关。
3. **一事实一次**：执行后追加 `state.facts[{ factId, turnIndex, worldTime }]`（append-only），
   有记录就跳过 —— 存档里这条日志就是「发生过」的唯一凭据。
4. **跳年照常补齐**：条件写成 `time >= N day`，`advanceTo` 一次跨十年也会在下一轮把沿途到期事实顺序执行。
5. **顺序即声明顺序**：同一回合到期的按书写顺序跑。`fact-megumi-enrolls` 必须排在
   `fact-gojo-takes-megumi` 前面 —— 关系效果有判活检查，人还没登场就建边会被静默跳过。

效果表就是现有 `EffectSchema`（`spawnNpc` / `addRelationEdge` / `adjustRelation` / `setFlag` /
`adjustAttribute` / `setNpcLifecycle` …），**不新造语法**；`when` 不限定只能写时间（旗标也行）。

- 加载期校验：`id` 唯一；`when` / `effects` 走既有引用完整性；`spawnNpc.ruleId` 必须是已声明规则。
- RNG：条件与效果各用独立派生流（`scanStream`）⇒ 给同一 seed 加一条时间表**不会**改变既有对局的随机序列。
- **不保留第二套定时机制**：`npcSpawnRules.when` 与 `evaluateSpawnRules` 已删除。
  两套并存时，「为什么这个人没出现」永远要先问「是哪套没跑」。

## ADR-006 D2 · NPC 一律定时登场，事件生成只是兜底

登场不该是某条支线的副产品（乙骨的登场曾挂在 `ev-np-01` 的胜负出口上；玩家没走到就永远 `unspawned`）。

1. **定时是常态**：`npcSpawnRules` 只留「这个人是谁、登场时几岁」，什么时候登场交给时间表。
2. **时间点与章节门同源**：门的 `window.start` 是多少天，这一章的人就用多少天。门开了，人也在。
3. **参战另加一层保险**：任何以他们为 `enemies[].ref` 的事件同时声明 `npcs: [rule-…]`，
   占槽时先 `materializeEventNpcs`。否则「时间没走到」会把一场战斗变成空场，
   而 `enemiesExhausted` 会被判即胜 —— 白送 `onVictory`。
4. **事件不再负责生人**（`ev-np-01` 的 `spawnNpc` 已删）：登场机制只留一条。

连带：2006 开局实例表只有 2006 那一届（+ 理子，`visibility: hidden`）；虎杖 / 伏黑 / 钉崎 / 乙骨 /
漏壶 / 宿傩三形态 / 羂索 / 甚尔全在 `unspawned`。甚尔在怀玉末统一置 `inactive`（阵亡）——
这一章的戏演完了，不该在 2018 年还在后台跑自主行动。

## ADR-005 · 开局序章与第一幕

### D1 序章是**装饰**，没有写入口

服务端在 commit 时构造只读请求（世界 / 玩家 / 属性 / 术式体质名 / 玩家真正拍板的那几步 /
`lore.md` 的 `always` 段），交 `generateNarrative` 校验。输出 schema 只有 `{ text }`，
**没有** `effects` / `state` / `flags`。失败 / 超时 / 结构不符 / mock ⇒ `fallbackPrologue`
（模板拼的确定性文案）—— 没有兜底就等于「没配 key 的玩家看到空白开局」，有专门用例锁住。

### D2 序章进 `history`，不只活在响应里

响应体只活在一次 HTTP 里，刷新就没了。序章属于「这一局确实发生过的一句话」，所以进
`history`（`visibility: "public"`，`type: "milestone"`，`turnIndex: 0`），
同时在 commit 响应里回传（`prologue` / `prologueSource`）供结果页当场显示。
`type` 复用 `milestone`（标签显示「碑」）—— 新增 history 类型是协议改动，不值得为标签开一轮。

### D3 第一幕由模板声明

```yaml
trigger: { source: schedule, window: { start: { value: 1, unit: minute } }, once: true }
conditions: [{ flag: creationDone, eq: true }]
```

- **必须是 `schedule`**：主线不许用 `pool`（池子抽日常；门的出现时间由时间表决定）。
- **由引擎在 commit 末尾呈现**：`presentQueuedEventV2` 只做「槽空 ⇒ 扫队列 ⇒ 写槽」，
  不推 `turnIndex`、不耗行动、不加世界时间 —— 否则序章与第一幕之间会断一次点击。
- 正文必须对六种出身都成立（只写此刻，不写身份）。

### D4 主线门一律 `schedule`

`ev-ch1-gate … ev-ch7-gate` 从 `pool + probability 1 + time gte N day` 改为
`schedule + window.start = N day`。语义等价但不再消耗池容量、不参与随机抽取，
也不会因为队列被日常占满而把主线卡到 `timeReached`。早到不了就 `hold`（留队、每轮重估、零错失）。

## LLM 提交的事件真的会上桌（2026-11-21）

`story.submitBranch` 是模型**唯一**的写世界通道：它把定义写进 `state.generatedEvents`，
由引擎负责调度。这条链以前断在两处，两处都是"写了但永远不发生"：

1. **工具画像里没有它**。`toolProfile` 只能**收窄**工具表，而 jjk-2006 的 `narrative`
   画像只列了读工具 ⇒ 模型手里根本没有 `story.submitBranch`，一次也提交不出来。
   现在多一份 `story` 画像（读工具 + `story.submitBranch`），挂在 `lt.gm.interlude` 上：
   `fireMode: level` + `random: 0.08`（≈ 每 12 轮一次），让 GM 在"日常事件都跑完了、
   玩家连着几十天修炼"的时候还有开口的机会。
2. **池抽取只扫模板事件**。`resolvePoolV2` 以前只遍历 `template.events` ⇒
   `mode: "random"` 提交的分支永远留在 `generatedEvents` 里。现在候选池 =
   模板事件 ∪ 生成事件，生成事件是**一次性内容**：结算过就不再抽，已经排队等着的
   也不重复入队（它们的 `trigger` 没有 `once`，靠这两条收敛）。

口径不变：LLM **不入队、不占槽**；排不排、什么时候排由回合边界的引擎决定。
`certain` 走 `enqueueGeneratedCertain`（立刻/带延迟入队），`random` 走上面这条池。

### 提交即上演（2026-11-21）

事务边界是「**先结算、再 invoke**」（ADR-0035 D2），所以 `advanceTurnV2` 的 tail
跑完时模型还没开始写。以前这带来两段延迟：本轮写下的分支要等下一轮 tail 才入队、
再下一轮才上桌 —— 玩家体感「卡了半天无事发生」。

两条改动：

1. **`trigger.after` 省略 = 立刻**。编译期不再硬塞 1 分钟（`schedule` 也不再要求
   `window`）；`enqueueGeneratedCertain` 缺省用 `absoluteStart = worldTime`，
   入队即到期。显式写了 `after` 的照常排队。
2. **提交后同一响应内兑现**：`runWorldTransaction` 在 `gateway.invoke` 返回
   `committed` 之后调 `presentNewlyGeneratedV2` —— 入队 + 槽空就 `nextTurn` 摆上来
   （不推进 `turnIndex` / 世界时间）。槽已被占则留在队列等下一位。

### 选项必须有效果（2026-11-21）

实测模型会写 `effects: []`（或干脆不写），玩家点下去什么都不发生 —— 看起来就是坏事件。
工具描述里补了「每个选项至少一条，且至少一条改数值（mood/hp/mp）；旗标只是作者记号，
模板不会读」；`effects` 在工具表里改为**必填**，`SubmitBranchOptionSchema` 拒绝空数组
（整条被拒、模型本轮内重试）。省略仍然允许（旧存档兼容）。

### 词表：渐进披露的 `rule.lexicon`（2026-11-21）

只把「形状」写进工具描述是不够的 —— 模型还得知道**能引用谁**（属性 id、资源、关系 kind、
在场的角色、物品、状态），否则写出来的效果全是自造词。但这些内容有几十条，
每轮塞进 prompt 既贵又挤掉叙事素材。

所以做成**按需查询**：

- 不带 `section` ⇒ 只返回目录（effects / items / statuses）；
- `section=effects` ⇒ 9 种扁平形状（与 `BranchEffectSchema` 一一对应）+ 属性（id/显示名/当前值/上限）
  + 资源 + 关系 kind（来自 shared 枚举，不从模板猜）+ 在场角色；
- `section=items` / `statuses` ⇒ 物品 / 状态词表；
- 未知 section 退回目录；模板没注入时明确报错，**不臆造**清单。

配套的两条「怎么想」（写在运行时，不占模板）：
`loop.ts` 的 `BRANCH_WORKFLOW`（先查此刻 → 梳理走向 → 想清楚选择 → 查词表 → 提交），
只在该画像真的带 `story.submitBranch` 时注入；`story.submitBranch` 的描述里也写明
「写 effects 之前先查 effects」。

## 事件编排的其余硬约束（散落在实现里，汇总在此）

- **`nextEventId` / `enqueueEvent` 指向不存在的事件 ⇒ `inspect check` error（`dangling-edge`）**。
- **`source: chain` 却没有任何入边 ⇒ error（`orphan-chain-event`）**。
- **链上事件没有出口**（既无 `nextEventId`、又没写任何结局旗标）⇒ warn（`sink-event`）。
- **旗标被读却无人写** ⇒ error（读它的若是结局 / 解锁 / 终止条件）或 warn；
  **只写不读** ⇒ info（`flag-never-written` / `flag-never-read`）。
- **`as` 变体的兜底必须存在**（见 `10-开局与角色.md` D4），否则某个 self 会软锁。
- 事件的 `settle.combat` / `settle.random` 的指路目标若是多变体首节点 ⇒ 加载期拒载（无处挂 `visibleWhen`）。
