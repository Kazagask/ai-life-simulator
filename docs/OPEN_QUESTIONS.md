# 待决事项

Agent 不得擅自把本文件中的问题当作已定需求。

1. 是否需要账号/云存档；Demo 可先本地匿名世界。
2. PostgreSQL 在 P0 是否立即接入，还是先用内存仓储跑通闭环。
3. 是否需要真正的多 Agent 运行时；P0 不要求。
4. 咒术能力、战斗和任务系统的具体深度；P0 仅保留最小接口。
5. AI provider 的具体供应商和模型；先实现接口与 Mock。
6. 世界模板编辑器和用户导入模板的权限/安全模型。
7. 人生评价具体权重和展示形式；先采用可解释、可配置的规则评分。**【2026-11-11 已由 R2.2 规格收敛，不再是待决项】** 权威规格见 `specs/data/TEMPLATE_PROTOCOL_V2.md` §18 与 `specs/iteration-2026-11-11/requirements.md` §D（R-EV-01..06）；`specs/engine/CORE_ENGINE.md §8` 已标注由该规格取代，不得再保留第二份评价事实来源。
8. 心情机制的深度：心情对事件触发概率的影响方式、心情档位修正是否随时间衰减、心情与 NPC 行为选择的耦合程度。
9. 装备系统范围：equipment 物品的槽位/词条模型、装备与补正的关系（静态词条还是动态补正）；V0.1 Schema 已预留 type 但引擎忽略。**【2026-11-11 用户已决】词条统一采用「动态补正」**：每次结算按当前状态/层数/条件由 preset 白名单求值，不写回基础属性或装备实例，不提供 static/dynamic 二选一，不开放自由表达式；固定值只是无条件退化 preset。见 `specs/iteration-2026-11-11/requirements.md` R-EQ-04 与 `design.md` §9.1。
10. 判定/伤害表达式 DSL：preset 白名单之外的自由公式（如 `max(1, base - def)`）如何安全表达（沙箱求值器 vs 更细的 preset 扩展）；安全风险未评估前不开放。（2026-11 对齐结论：维持 preset 扩展路线，不开放自由表达式 DSL，见 ADR-0002。）
11. 模拟域 HP 归零的规则：重伤/昏迷/死亡的模板可定义程度，以及死亡是否允许（含玩家死亡后的世界处理）。**【2026-11-11 用户已决（玩家侧）】HP 与死亡结局解耦**：模拟中 HP 不低于 1（现有 `battle.ts:405-407/509`、`engine.ts:269`、协议 §10 已 clamp），死亡不由 HP 归零触发；战败（`over=defeat`）且模板死亡条件满足时，按 `deathMode: event` 生成死亡事件走既有事件链再触发结局，或按 `deathMode: direct` 直接触发结局；战败但条件不满足则继续模拟。NPC 侧死亡实体语义仍见 #21/#22（未决）。见 R-EN-07/08 与 `design.md` §9.3。
12. 扩展战斗语义：反射伤害、吸血、复活、召唤等需要新引擎原语的机制，何时纳入控制语义/效果白名单。
13. 敌人 AI 策略模板化：V0.1 用简单权重策略，是否引入条件化 AI（低血量优先治疗、按玩家属性针对性选技能）。**【2026-11-11 用户已决】引入条件化 AI，但条件求值只读「公有字段」**：玩家端投影可见字段、`visibility === "public"` 的日志/效果、该阵营已公开战斗状态；禁止读 `hidden/unknown/secrets`、`combatHints`、NPC 私有目标与服务端内部状态，引用非公有字段的模板在加载期由 Zod/协议校验拒绝。见 R-CA-06 与 `design.md` §9.2。
14. 性别档位的边界：档位是否可携带机制含义（称谓之外的人称/玩法差异），还是保持纯展示标签。
15. YAML 模板在运行时的存放位置与热加载：specs 目录仅作设计期产物，实现阶段移至何处、是否支持不重启更新。
16. 领域展开类大招的独占机制：V0.1 用长冷却（cooldownTurns: 99）近似"每场一次"，是否引入 oncePerBattle 字段或"展开回合内敌方行动受限"的领域规则。
17. 召唤物系统：夏油杰的咒灵当前以可叠层补正（absorbed-curses）代替，独立的召唤物实体（独立血条/独立行动回合）何时纳入引擎。
18. 按层数给属性的补正模型：现有 attributeModifiers 为固定值修正，层数缩放的属性修正（如每层咒灵 +2 咒力）需要新增 perStack 修饰模型。
19. 事件池 trigger.weight 的属性加权：转盘扇区已支持 weightBy（幸运+咒力等多属性叠加），池事件选择权重如需同样机制（幸运影响稀有遭遇）再扩展。
20. 事件并发/冲突规则：combat 事件同一时刻至多一场，当前并发时整条跳过（不消耗 once/冷却、不留触发与历史痕迹）；normal 事件不丢弃、按同一优先级稳定排序入待决队列（同优先级 FIFO）。二者共用「事件链 > 时间触发 > 行动触发 > 事件池」：combat 由轮次管线 resolver 顺序抢占体现，normal 由队列排序体现。是否需要「战斗队列」（依次进行）或「拦截延后」（下轮再触发）仍待定；combat 与 pendingEvent 并存时的交互优先级（战斗优先、事件排队）也需明确。若引入战斗队列将推翻附录 A 的 A4「不引入事件栈/队列」决策，需先走 ADR。
21. NPC 实体生命周期与「死亡」的引擎级语义（2026-11-11 梳理新增，未决；**玩家侧 HP/死亡规则已由用户 2026-11-11 定夺，见 #11，本条只讨论 NPC 侧**）：当前 `V2Npc`（`packages/shared/src/v2.ts:59-76`）无存活/死亡状态，`alive` 只存在于战斗镜像（`v2/battle.ts:287-297`），模板用手写 flag（如 `gojoAlive=false`）表达死亡事实，战斗结束只回写玩家 HP/MP。需确定：NPC 是否需要 `active / deceased / retired` 等状态机；重伤/昏迷/死亡是否分层、是否与玩家死亡规则（#11）共用；死亡后是否仍参与自主行动、事件条件、关系变化与玩家投影；死亡事实由规则效果、事件效果还是模板 flag 写入。
22. 「重要角色即使死亡也应存储」的判定与留存范围（未决）：重要性由模板静态声明、剧情引用、关系深度、玩家认知，还是运行时引用计数决定；是否可随剧情升级/降级；死亡角色要保留哪些数据（模板定义、本局实例、关系、秘密、信息权限、事件引用、评价证据、历史日志），分别保留到「活跃实例 / 只读归档 / 模板定义」哪一层；玩家在什么条件下获知死讯（`known` / `inferred` / `hidden`）。
23. 「次要角色即使存活也可清理」的清理语义（未决）：触发条件（世界时间、轮次、地点/距离、关系、重要性、引用计数、内存预算）；清理是删除实例、降级为摘要记录，还是移出活跃模拟集合；被 `pendingEvents` / `chains` / `battle` / `firedEvents` / `history` / 评价证据引用的角色是否禁止清理；清理后剧情再次引用该 id 时如何恢复（按模板定义重建 vs 拒绝）。
24. 清理与可复现性、归档只读的冲突（未决；**R2.2 口径**：本轮不引入 Lifecycle 阶段状态机，`ARCHIVED` 不再是一个阶段，而由 `archived` 只读标记 + `TerminationRecord` 表达，故「是否允许在 `ARCHIVED` 之后执行」应改按「归档只读后是否允许执行」理解）：`R-NFR-01` 要求同 seed 回放逐字段相等、`R-AR-02` 要求归档只读、`R-EV-04` 要求评价证据 ID 可解析，而清理会改变状态与引用。需确定清理发生在哪个阶段（轮次管线内 / 归档时 / 存储层）、是否允许在 `ARCHIVED` 之后执行、回放对比按「活跃集合」还是「全量记录」比较；`R-AR-03`「首版沿用现有存档机制、不新增独立存档子系统」与新增留存策略是否冲突。
25. NPC 关系网络的范围（未决）：当前只有 `npc.relationship`（NPC→玩家单值，`-100..100`），无 NPC↔NPC、无关系来源/档位/阈值/传播；`R-OP-05` 要求「不得默认所有 NPC 都认识主角」，但模板中所有初始关系均为 0。需确定关系实体模型（是否带来源、方向、可见性）、信息传播规则、关系变化是否触发 NPC 行动（增量说明 §4.1），以及死亡/清理后关系记录如何保留供评价引用。

32. **归档记录是否向玩家端暴露隐藏历史**（R2.3 立项时新增，待用户确认）：`R-NFR-04` 要求 `hidden` 不得进玩家端投影，但归档是"玩家自己的这一生"的复盘。两种口径——① 只下发 public 历史 + 给一条 `hiddenHistoryCount` 计数（`design.md §2.4` 的建议方案，避免"刚封存就能看答案"）；② 归档响应也返回全量，视为存档复盘。当前规格按 ① 写；若选 ② 需同步改 `R-VS-04`。另注：`npc_action` 的历史条目本轮**一律 public**（模板 `summary` 是可见行为，NPC 秘密在 `def.secrets` 不进历史），"玩家不在场"的分级需要先有在场/距离模型，与 #23/#25 相关。
33. **事件定义缺少可见性字段**（R2.3 立项时发现）：`EventV2Schema`（`packages/shared/src/schema/event.ts`）没有 `visibility`，而 `EndingTemplateSchema` 有（`schema/ending.ts:124`）。后果是 `hidden` 事件一旦触发，其标题与正文会以 `public` 身份写进 `history`，再经 `/api/worlds/:id/history` 全量下发。R2.3 `T2-01` 计划给事件加可选 `visibility`（缺省 `public`，向后兼容），需在协议 §8 记一笔；**若策划认为"事件本来就不该有隐藏语义"，则该字段撤掉，隐藏能力只能靠结局表达**——待确认。
