# ADR-002：表现层协议（样式 / 效果摘要 / 回合增量 / 叙事分段）

- **日期**：2026-11-18
- **状态**：**提议**（待用户裁决 D-1..D-5，见 `specs/iteration-2026-11-18-presentation/design.md` §7）
- **关联**：`specs/iteration-2026-11-18-presentation/`
- **前序**：ADR-001（前实例化开局）。旧 `docs/DECISIONS.md` 已归档，本 ADR 是新体系第二份。

## 背景

用户在同一轮提出六件表现层诉求：叙事区按回合追加、转盘落定位置改为「本轮收获」、
装备/消耗品/技能/补正详情要展示效果、模板可声明受控样式（如最高品质的流动彩虹）、
补正点击后毛玻璃展示、固定效果以下划线呈现。

这些都不是「某个组件写好看点」的问题，而是**协议缺口**：

1. **叙事只有入口没有兜底**。叙事正文走 `trace` 通道，但只有 LLM 产出才写；模板/mock 回合
   `generate.ts` 直接短路为 `source:"template"`，什么都不写。实测开局 + 1 回合后
   `GET /narrative?fromTurn=0` 的 `blocks` 为 0 —— 没有 LLM 就没有叙事区。
2. **投影不承载效果**。`StatusVM` 只有 `id/name/stacks`，`SkillVM` 只有 `id/name/description/kind`，
   `ControlSemantics`（`cannot_act` 等）建模了却从未出现在任何展示面。
3. **没有样式词汇**。`quality` 只是自由字符串 + 模板白名单，前端拿它当文字标签用；
   补正/技能连 `quality` 都没有。想让「六眼」处处是同一身彩虹，必须有**一处解析**。
4. **回合结果不可见**。`advanceTurn` 只回快照，客户端无法知道「刚刚发生了什么」，
   只能靠玩家自己比对前后属性。

## 决策

### D1 表现层字段一律是只读投影，不进权威状态

新增的样式、效果摘要、回合增量全部**只存在于投影 / 响应**：不进 `WorldStateV2`、
不参与判定、不进语义指纹、不影响 `seed` 复现。

理由：表现层的迭代频率远高于规则层；把它写进 state 会让每次视觉调整都变成存档事件
（上一轮已经因为 `relations.kind` 越界写过一次坏档）。

**代价**：回合增量刷新后消失（D-3 已裁决接受），历史只留在叙事段里。

### D2 样式词汇受控：枚举 + 颜色 token，解析在引擎投影期

模板只能写 `preset`（`rainbow/gold/silver/bronze/crimson/azure/jade`）、
`color`/`background`（3/6/8 位十六进制或引擎颜色 token）、`bold`、`animation`
（`none/rainbow-flow/pulse/glow`）。**不接受任意 CSS 字符串**。

解析顺序：实体 `style`（先查模板 `styles` 别名，再查预设）> `qualityStyles[quality]` > 默认。
解析发生在 `projection.ts`，因此服务端、`@life-sim/rpg-ui`、自定义前端拿到的是同一份
`ResolvedStyle`，不存在「各端各画一遍」。

理由：模板是**内容**，不是样式表。允许自由 CSS 等于把注入面、可维护性与可访问性
（减少动效、对比度）全部外包给模板作者；而用户要的表达力（彩虹 / 金色 / 加粗 / 流动）
用一个小枚举就能覆盖 90%。

### D2b 标签是模板词，样式是引擎词，两者分离（2026-11-18 追加）

**问题**：`rainbow` 是引擎的视觉变量名（CSS 类名 / 预设 id），但一开始被当成副标题
直接下发给玩家，详情浮层里出现了「RAINBOW」这种字样。玩家该看到的是模板自己的词
（神话 / 增益），而这个词需要**自己的样式**（神话是动虹、增益是绿）。

**决策**：

- 新增 `ui.yaml: tags`：`id → { name, style }`，样式规格与 `styles` 同一套闭集；
- 补正 / 物品声明 `tags: [id...]`，顺序即优先级；未知 id **加载期拒载**（与样式引用同一条纪律）；
- 投影期解析成 `ResolvedTag[]`（`{ id, name, style }`），与实体一起下发；
- **名字颜色解析顺序**：实体 `style` > 命中样式的第一个 tag > `qualityStyles[quality]` >
  `polarityStyles[polarity]`。这样「神话」标签在的补正，名字与标签同色；
  `quality` / `polarity` 退回成「没有标签时的简写」，不再是展示字段；
- 技能不参与标签（用户裁决），只保留品级样式。

**代价**：模板多一层词汇表；**收益**：界面上不再出现引擎词，换配色只改 `ui.yaml`。

### D2c 品级 / 增益 / 异常做成引擎预置标签（2026-11-18 追加）

**问题**：D2b 把标签交给模板声明，但品级这类词汇**每份模板都要用**；让每个模板抄一遍
10 行 yaml，只会让「同一个品级在两张卡上不同色」变成常态。

**决策**：

- 引擎内置 13 个预置标签（`DEFAULT_TAGS`），模板**一行不写**即可引用：

  | id | 名称 | 视觉 |
  |---|---|---|
  | `mythic-unique` | 唯一·神话 | 动态彩 |
  | `mythic` | 一品·神话 | 静态彩 |
  | `legend` | 二品·传说 | 金 |
  | `epic` | 三品·史诗 | 橙 |
  | `treasure` | 四品·珍宝 | 粉 |
  | `excellent` | 五品·卓越 | 紫 |
  | `rare` | 六品·稀有 | 青 |
  | `fine` | 七品·精良 | 蓝 |
  | `common` | 八品·寻常 | 白 |
  | `poor` | 九品·粗劣 | 灰 |
  | `abnormal` | 异常 | 红 |
  | `buff` | 增益 | 绿 |
  | `neutral` | 中性 | 灰 |

- `ui.tags` 里写**同名 id** ⇒ 覆盖该条（改名 / 换色），其余继续继承预置；
- 找不到的 id 仍然加载期拒载（预置集合属于「已知」）；
- 新增样式预设 `cyan`（青，六品·稀有）；`gray` 一色两用（九品与中性）。

**代价**：内核里出现中文词表（与 `FIXED_EFFECT_COPY` 同性质，属默认文案）；
**收益**：模板零配置就有统一品级阶梯，且随时可覆盖。

### D2d 战斗态用语义色，与身份色分离（2026-11-18 追加）

战斗面板要「一眼看出增益还是异常」，而品级色（金 / 彩）说的是身份，不是打法。两者在一张卡上冲突。

- 引擎从实体标签里取语义：只有预置的 `buff` / `abnormal` / `neutral` 三个 tag 有 tone；
- 投影额外下发 `StatusView.battleStyle`（按 `polarityStyles` 解析出的绿 / 红 / 灰）；
- 战斗面板用 `battleStyle ?? style`（**整颗芯片换色**，含边框）；非战斗仍用实体自身的身份色；
- 没有语义标签的实体（纯天赋）没有 `battleStyle`，战斗里继续用身份色。

配套的数据口径（用户裁决）：**品级标签只给天赋 / 称号 / 术式 / 装备**；
纯状态（眩晕、重伤、大吉、狂化…）只挂语义标签。这条口径让「同一件东西两个场景不同色」的
特殊情况降到最少，也让非战斗视图不会被品级色污染。

### D2e 品级（quality）与品级标签合流（2026-11-19 追加）

**问题**：装备本来就有一个 `quality` 概念（模板在 `equipment.qualities` 里声明白名单，
取值为 `common / uncommon / rare / cursed` 这类），但它**什么也不做**；真正决定名字颜色的是
另一行 `tags: [legend, buff]`。同一件装备要写两套词汇，且两套各说各话。

**决策**：

- `quality` 直接接受**引擎品级阶梯 id**（`mythic-unique` … `poor`）。写了它，
  `tagIdsOf` 自动生成一条对应的品级标签（名字 + 配色都来自预置），**不必再写 `tags`**。
- `tags` 仍然可用，优先级更高（「品级 + 增益」这类多标签场景）。
- 模板自己的品质词（如 `cursed`）继续走 `equipment.qualities` 白名单；
  校验规则放宽为「**阶梯 id 或白名单里的词**」——白名单不必再抄一遍阶梯。
- `ui.qualityStyles` 保留为「自定义 quality 词 → 样式」的旧通道，阶梯 id 不走它。

**代价**：`quality` 从「模板私有的分级」变成「引擎枚举 + 模板扩展」两段式；
**收益**：装备只写一行 `quality: legend` 就有品级标签与配色，两套词汇合一。

### D3 效果摘要由定义派生，动态补正只描述规则

`buildEffectSummaries(def)` 是纯函数：从补正 / 技能 / 物品 / 装备**定义**生成展示条目
（`咒力 +4`、`无法行动`、`1.2×咒力`、`冷却 3 回合`）。

动态补正（`preset: scaled`）**不展示结算数值**，只展示规则（`随咒力成长：3 + 0.2×咒力`）。
理由：它的值随结算上下文变化，任何「详情里的数字」都会在下一回合变成假话。

控制类固定效果统一收敛到引擎文案表（`fixed-effects.ts`），`kind: "control"`，
展示层据此加下划线（R-FX-01）——前端不重复维护「无法行动」这类词。

### D4 回合增量 = 基线 + 差分，不落库

引擎提供 `captureGainBaseline(state)`（只抓玩家可见五类：属性 / 补正 / 技能 / 物品 / 装备）
与 `diffGains(before, after)`。服务端在写操作前后各调一次，把结果塞进响应 `gains`。

理由：
- **不 clone 整状态**：状态里有 NPC 表、关系图、延时队列，整份 clone 的代价与世界规模成正比，
  而收获卡只关心自身上下文。
- **不落库**：增量是一次性呈现；写进 state 会引入「哪一轮的增量」这类派生字段，
  与 D1 冲突。
- 顺序固定（属性→补正→技能→物品→装备，同类按 id 排序）保证同输入同输出，可写单测。

### D5 叙事按回合追加，模板兜底写同一条 trace 通道

每个写操作收尾时：若该回合**已有**叙事块（LLM 写过）则跳过；否则由服务端合成一条
模板叙事块写入 trace（`reason: "turn.template"`）。`ContentBlockVM` 增加 `turnIndex`，
客户端据此只给最新回合播打字机。

理由：trace 已经是 append-only、带 `turnIndex`、有窗口校验与读回通道的成熟设施；
另建一套「回合摘要存储」等于复制它并承担两份一致性。

**取舍**：模板合成的文字会比 LLM 平实（取材是事件正文 / 历史摘要）。这是有意的——
没有 LLM 时宁可平实，也不要假的「文学腔」；有 LLM 时 LLM 的版本优先且不会被覆盖。

### D6 `schemaVersion` 保持 5

本轮**没有** `WorldStateV2` 结构变更（新增字段全在投影 / 模板定义里），因此不升版本、旧档可直载。
模板指纹会因 `ui.yaml`/`statuses.yaml` 改动而变化，这由模板版本（`jjk-2006/2.0.0`）承担，
不牵连存档格式。

## 影响

- `packages/shared`：新增 `schema/style.ts`；`view-model.ts` 追加字段（`strict()` 同步放宽）；
  `status-effect.ts`/`skill.ts`/`item.ts`/`ui.ts` 加可选字段。
- `packages/game-core`：新增 `v2/presentation/{style,effects,fixed-effects,gains}.ts`；
  `projection.ts` 接入样式与效果摘要。**不动 turn 管线语义**。
- `apps/server`：五个写操作响应加 `gains`；写操作收尾加模板叙事兜底；模板加载期校验样式引用。
- `packages/rpg-ui`：新增 `TurnGainsCard` / `EffectList` / `ModifierSheet` / `StyledName`。
- `apps/web`：叙事追加 + 假流式 + 浮层接线。
- 模板：`jjk-2006/2.0.0` 的 `ui.yaml` 加 `styles`/`qualityStyles`，六眼等最高品质补正加 `quality`/`style`。

## 追加修订（2026-11-18 验收返工）

1. **动虹与边框共用同一条时间轴**（D2 的实现细节）：字与 1px 描边读同一组 CSS 变量
   （同一渐变 / `background-size` / keyframes / 时长）。此前描边用另一套 `border-color`
   关键帧，玩家读出来是「字和框各转各的」。
2. **底层效果不带回合数**：`FIXED_EFFECT_COPY` 只写「战斗中无法行动」这类**能力限制**；
   「几回合」属于补正的 `duration` / `combat.battleRounds`，两处不许混写。
3. **转盘只在确认后进叙事**（D5 的补充）：`state.slot.eventId === wheelResult.eventId`
   说明这一格只是「呈现」、尚未结算，此时不把 `⚄ …` 写进正文；否则同一次巡逻会被
   叙述两遍（掷出一次、确认一次）。
4. **标签样式参与名字配色**（D2b 的延伸）：同一张卡上「标签是神话、名字是白的」不可接受。

## 未采用方案

1. **把样式直接写成 CSS 字符串**：注入面 / 可访问性 / 跨端一致性全部失控，否决。
2. **回合增量落库**：与 D1 冲突，且引入派生字段污染权威状态，否决。
3. **前端各自解析样式**：多端会漂移（正是用户抱怨「到处不一样」的根因），否决。
4. **另建回合摘要表**：与 trace 重复，否决。
5. **叙事只由 LLM 产出**：没 LLM 就没叙事，与用户「无 LLM 也要有」直接冲突，否决。
