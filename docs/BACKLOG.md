## 方向约束（2026-11-20，用户口径）—— 后续所有条目先过这一关

- **目标**：数据尽量在客户端，**没有云端也能玩**。LLM 的**调用形态保持不变**（一次 invocation =
  多轮工具循环 + 叙事正文，`story.submitBranch` 仍是唯一写入口），见下方「与这条方向无关的三条」。
- 三期，按序、不并行：
  1. **迁位置**：模板与存档不再挂在服务端机器上。
  2. **下资源**：模板从云端数据库下载 → 客户端校验 → 存客户端（资产同理）。
  3. **去服务化**：去掉 server，走 service worker；远端只负责上传云存档（LLM 由浏览器直连 provider，
     不需要中转 —— 见下方 key / CORS 两条）。
- **因此被否掉的**（不要再提，也不要顺手做）：
  - **#49** 服务端免密钥 LLM、B-01 的后续优化 —— 双杀（方向 + LLM 形态不变）；
- **一条已顺手清掉的**：`contract/branch-submit.ts` 的 `relationEdge` 旧 4 档 `visibility`
  **已做（2026-11-20，ADR-017）** —— wire 契约换成 `scope` + `knownBy`（`limited` 必带 `knownBy`），
  `visibility` 降级为 `@deprecated` 可选、只在 `scope` 缺席时兜底。它本来列在这条方向下「不想花就让它
  随契约层一起死」，因为是个真 bug（模型写不出 `scope: limited`）且只值 20 分钟，就做了。
  这层仍会随第 3 期整层消失 —— **做完就不再往上加东西**。
- **与这条方向无关的三条 —— 不要顺手冻结**（2026-11-20 用户纠正：这是核心内容）：
  SPEC §4.7 列的「叙事长期 agentic / 自由文本行动 / 多 Agent 观察者切换」是**已在运行的 agentic 形态的延伸**，
  不是另一条路线。今天叙事本身就是 agentic 的（§4.5），所以「冻结 agentic」等于「冻结现状」，是个假命题。
  - **Service Worker 能做**：`fetch`、多轮工具循环、SSE 流式（chunk 经 `postMessage` 转发给页面）都行。
  - 两个真实限制：① SW 空闲会被回收（Chrome ~30s），长循环要挂 `ExtendableEvent.waitUntil()` 或保持一个 fetch 在飞；
    被杀 = 这次 invocation 半途而废，正好落到既有的「回退模板文案」路径，不会坏档。
    ② **SW 不豁免 CORS** —— 端点不给 `Access-Control-Allow-Origin` 就读不到 body（opaque 不能读）。
  - **key 不是新增成本，反而是减少**：`life-sim-llm-config` 早就把 `apiKey/model/baseUrl` **明文**存在
    localStorage（B-01 的口径就是「可选，风险自担」），RSA 信封只保护 wire。去服务化之后 key 的存在位置
    从三处（浏览器 + wire 密文 + 服务端内存 Map）减到一处（浏览器）：`credentialEnvelope.ts` /
    `llmCrypto.ts` / `userCredentials.ts` 与 `x-life-sim-llm-session` 头一起作废 —— 没有第二方要交 key，
    信封就失去存在理由。
  - 所以唯一真回归是 **CORS**：玩家拿没开 ACAO 的自建网关在浏览器里打不通，而今天有服务端代打所以无感。
    解法：自建用户自己加一行头（最常见）／ 留中转。中转**只为平台 key 存在**，而 #49 已冻 ⇒ 现阶段不需要。
  - 其中「多 Agent / 观察者切换」与 LLM 无关，它缺的是**存储**（`selfId` 只做了关系缝，见 ADR-010），
    客户端迁移反而让这件事更容易。
- **两个必须在第 1 期之前定的前置决定**：
  1. **L2 扩展的运行时**。`registerServerExtensions()` 在服务端启动时注册 TS 模块，浏览器 / Service Worker
     跑不了下载来的任意 TS。三选一：编进 web bundle（白名单）／L2 降级为纯 yaml／保留一个薄扩展 host
     （那就没去干净）。它决定**模板包里要不要带代码**，所以拖不到第 2 期再定。
  2. **拒载在客户端的表达**。`template_content_drift` / `schema_version_mismatch` 今天只是服务端日志里的
     `save_skipped`；客户端自己持有模板后，这变成玩家眼前的一屏错误 —— 需要 UI 兜底 + 「保留旧模板版本」策略。
- **已经能用的地基（别重造）**：`semanticFingerprint` 覆盖 15 个声明式文件里除 `ui.yaml` 外的 14 个
  （13 yaml + `lore.md`，含 `rules.yaml`），就是第 2 期「校验后存客户端」要的东西；
  `assets/**` 有独立指纹但**不参与拒载**。
- **第 1 期的真工作量**不在搬文件，在 `apps/server/src/templates.ts` 的解耦：它把「扫目录 + zod 校验 +
  指纹 + 缓存 + 热加载」焊在一个 1700 行模块里，且全部依赖 `node:fs`。
  要拆成 ① 纯函数层（吃 `Map<相对路径, 内容>`，算校验 + 指纹）② fs 适配器（服务端）③ fetch/IndexedDB 适配器（客户端）。
- **`packages/game-core` 本来就能进浏览器**：只依赖 `@life-sim/shared` + `zod`，零 `node:` 导入。
  第 3 期的阻力不在内核，在 `templates.ts` 与存档读写。

## B-01 自定义 LLM 配置：前端缓存 + 非对称加密上报

- **状态**：**已实施**（2026-11-18）
- **提出人**：用户
- **类型**：改动现有链路（协议口径不变，但要动服务端凭证入口 + 前端存储策略）
- **已裁决（2026-11-18 用户补话）**：
  - **上报时机保持现状**（「保存并验证」时一次性上报），**不改成「开局后上报」**——
    因为这一步同时承担**连通性探测**，探测必须拿到真实凭证才能判「填错了」还是「服务端炸了」；
  - 佐证：**目前进入游戏后没有 LLM 配置入口**（面板只在进入世界之前的入口页），
    移到开局后等于把唯一的配置入口挪到玩家走不到的时点。

### 现状（2026-11-18 核对）

| 环节 | 事实 |
|---|---|
| 前端 UI | `apps/web/src/main.tsx` 设置面板「自定义 LLM（可选，风险自担）」，字段 `apiKey` / `model` / `baseUrl` |
| 上报 | 点「保存并验证」→ `POST /api/llm-credentials`（`apps/server/src/index.ts`），**明文 JSON**（走 HTTPS） |
| 服务端存储 | `userCredentials.mint()` 内存持有凭证，返回不透明 `sessionId`；绝不回显 / 落盘 / 进日志 |
| 后续请求 | 前端把 `sessionId` 存 localStorage，每个请求带 `x-life-sim-llm-session` 头；服务端 `lookup(sid)` 取回 |
| 探测 | `POST /api/llm-credentials/test`：只探连通性，不 mint、不入内存 |
| 声明文案 | 面板标题「（可选，风险自担）」、正文「本地只保存一个不透明的会话 id，风险自担」、已配置提示「（已本地保存，风险自担）」 |

### 要做的

1. **前端缓存完整配置**：`apiKey` / `model` / `baseUrl` 存前端（localStorage），刷新 / 重开页面不用重填。
   - 与现状的差别：现在只存不透明 `sessionId`，key 本身不留浏览器；改成「配置留在前端」。
2. **上报改成非对称加密（时机不变）**：仍是「保存并验证」那一次（`POST /api/llm-credentials`），
   只把请求体从明文 JSON 换成密文。
   - 建议：WebCrypto `RSA-OAEP`（SHA-256），前端持**公钥**加密，后端持**私钥**解密；
   - 载荷 `{ apiKey, model, baseUrl }` → base64 密文；服务端解密后仍走 `userCredentials` 内存存储，
     回 `sessionId`，前端继续用 `x-life-sim-llm-session`；
   - 探测接口（`/api/llm-credentials/test`）同理，否则「填错了」的诊断信息就断了。
3. **密钥写在代码里**：云端没有环境变量可用，公钥在前端常量、私钥在服务端常量（用户明确接受这个代价）。
4. **移除风险声明**：删掉面板标题 / 正文 / 已配置提示里的「风险自担」字样与相关注释
   （`apps/web/src/api.ts` 的注释也一并清理）。

### 实施要点 / 坑

- **不能把私钥塞进前端**：私钥只在 `apps/server`；前端只放公钥（混淆与否都不重要，公钥本就公开）。
- **密钥轮换**：写死意味着换 key 要改代码重发；第一版接受，注释里写明。
- **会话过期**：现在 `userCredentials` 是内存 Map，进程重启即失效。既然前端缓存了完整配置，
  可以在进入世界时静默重放一次加密上报（用户无感），或退到面板「重新验证」按钮手动重发。
- **世界绑定**：sessionId 保持全局，**不要**按 worldId 隔离——同一浏览器开第二个档不该要求重新填。
- **「进游戏后没有配置入口」是现状而不是目标**：本项不新增游戏内入口；如果以后要支持
  「游戏中换 key」，另立一条（会牵涉设置页在运行期的可达性，属 UI 结构改动）。
- **长度上限**：RSA-OAEP 2048 单块上限约 190 字节，`apiKey + model + baseUrl` 可能超；
  超了要在前端分段或改用「RSA 加密一次性 AES key + AES-GCM 加密载荷」的混合方案
  （推荐后者，代码量差不多，且不受长度限制）。
- **绝不回显 / 绝不落日志**：解密失败只回 `invalid_credentials`，不要把密文或明文写进日志。

### 待确认（实施前问用户）

- 缓存到 localStorage 需要用户接受「key 会留在浏览器」这件事（现状是刻意不落浏览器的）。
  如果只是为了「不用每次都填」，也可以只缓存 model/baseUrl、key 每次手填 —— 需用户拍板。
- 离线 / 私域部署时后端可能没有 HTTPS；非对称加密只解决「明文 HTTP 被抓包」，
  不替代 TLS，文档里要写清楚。

### 实施记录（2026-11-18）

- `apps/web/src/llmCrypto.ts`：WebCrypto **混合加密** —— 随机 AES-256-GCM 加密载荷，
  RSA-OAEP(SHA-256) 只包那 32 字节 key；`{ v:1, key, iv, data }` 全 base64。
  非安全上下文（`http://` 局域网）**直接拒绝**并给一句人话，绝不静默降级成明文。
- `apps/server/src/llm/credentialEnvelope.ts`：私钥 PKCS8(DER) base64 写死；
  解密任何一步失败一律返回 `null`，路由只回 `400 invalid_credentials`（不做原因区分）。
- 两个端点都**只接受信封**：`POST /api/llm-credentials`、`POST /api/llm-credentials/test`；
  明文 JSON 直接 400（不留兼容后门）。
- 前端缓存：`life-sim-llm-config` 存 `{apiKey, model, baseUrl}`，刷新 / 重开自动回填；
  不透明 `sessionId` 仍在 `life-sim-llm-session`；「清除」同时清两份。
- 保存流程：**先探连通性、再上报**。探测失败只给警告（不阻断保存），`reason` 映射成人话
  （连不上 / 超时 / 鉴权失败 / 端点非预期）；输入框保存后**不再清空**（本来就缓存了）。
- 文案：面板标题、正文、已保存提示里的「风险自担」全部删除，服务端注释同步改写。
- 验证：`pnpm test` 47 文件 / **306 例**（新增 4 例：前端加密→服务端解密往返、明文 400、
  密文篡改 400、解密后缺字段 400）；CDP 走查确认两条请求体都是 `{"envelope":…}` 且
  **不含明文 apiKey**、刷新后三格自动回填、面板无「风险」字样。
- 已知遗留（有意为之）：`apiKey` 以明文存在 localStorage（用户要求「缓存到前端」）；
  私钥写死 ⇒ 轮换密钥必须前后端同时发布，不能灰度混跑。

## B-03 补正 duration 的数据迁移 —— **已关闭（ADR-009，2026-11-19）**

- **原状态**：待实施（2026-11-18 用户提出「持续时长不该写在补正上」）
- **结论**：不只是「搬到施加点」，而是**换掉单位**。迁移时发现 `turns` 数的其实是
  「指针推进了几次」，而事件 `advanceTo` 可以一跳 4752 天、一格补正都不缩水
  （`events.yaml` 里 22 处 `advanceTo` 全在 518–4752 天）。照原计划只搬字段，
  会把这个 bug 一起搬过去。
- **落地**：定义侧删 `duration`；模拟域改用 `{ value, unit }` 世界时间（实例存绝对
  `expiresAt`，到期纯比较、不需要 tick）；战斗域用 `{ rounds }`；挂载即永久；
  `cureConditions.restTurns` → `restDays`。详见 `docs/adr/40-属性资源与状态.md`。
- **代价**：`jjk-2006/1.0.0` 与 `2.0.0` 随协议变更归档到
  `archive/2026-11-19-pre-adr009-templates/`（旧存档同时因指纹漂移失效）。

## B-04 开局 param 的后写覆盖（作者陷阱）

- **状态**：**已实施**（2026-11-20）—— 走的是当初倾向的「警告而非拒载」。
- `resolveParamMap` 按结果顺序 `Object.assign`，同一个 param id 在多格被设置时**后写覆盖先写**。
- 2026-11-18 的真实事故：`n13-entrance` 的 `begin` 也写了 `weapon`，把第六格选的天逆鉾
  静默覆盖成急救包（玩家看到的症状是「开局送的咒具没进背包」）。已删掉数据里的那处重复设置。
- **落地口径**：`apps/server/src/admin-data.ts#openingParamOverwrites(dag)` 报
  `opening-param-overwrite`（**warn**，进 `pnpm inspect check`），`AdminOrchestration.openingParams` 供
  `inspect` 展示。判据是**可达性**，不是「同一个 id 出现两次」：
  - 从某个 option 出发 BFS（`option.goto ?? node.goto ?? 数组下一个`，与 `opening-dag.ts#nextNodeId` 同源），
    收集沿途所有写入该 param 的 option；两个写者**互相不可达**就是互斥分支，不是冲突；
  - 同一个节点的两个 option 天然互斥，直接跳过。
  - 真实样例：`n-self`（自建）与 `n-canon`（借名）都写 `who`，两条路走不到一起 ⇒ **不报**。
    天真实现会把它当冲突，这条用例现在守在 `test/unit/admin-opening-params.test.ts`。
- 为什么只做 warn：这是**作者意图**层面的歧义，模板作者偶尔真想让后一格覆盖前一格
  （同一参数的分支内微调）；拒载会把合法模板挡在门外，而 warn 在 `inspect check` 里必然被看见。

## B-07 战斗内单位生命周期：中立单位 / 召唤 / 胜负判定 / 补正层数

- **原状态**：待实施（四项都是**协议级**改动，动手前先立 ADR）
- **状态**：**已实施**（2026-11-19，ADR-012）——四项全部落地，另加两级召唤物与专属资源池。
  落地口径与本条目当初的倾向有几处不同，记在下面「落地纪要」里。
- **提出人**：用户（2026-11-19）
- **触发场景**：魔虚罗（八握剑异戒神将魔虚罗）。它在现有引擎里只能二选一——写成「血很厚的杂兵」，
  或退化成「一个技能」，因为下面四个机制一个都不存在（ADR-008 D5 的评估）。
- **为什么不按角色特判**：这四项各自都还有第二个用户（中立怪 / 式神 / 守护战 / 叠层 boss），
  且都在引擎接缝上。按某个角色写死一次，后面每个召唤物与层数怪都要再来一遍，
  也直接违反内核「不得出现某作品专名判断」那条硬约束。

### 现状（2026-11-19 核对）

| 机制 | 现状 | 位置 |
| --- | --- | --- |
| 阵营 | 只有 `enemies` / `allies` 两个数组 + `player` 镜像，没有第三方 | `packages/shared/src/v2.ts:235` |
| 胜负 | `enemies.every(!alive)` ⇒ victory；`player.hp <= 1` ⇒ defeat；`allies` 全灭不判负；`over` 只有 `victory` / `defeat` / `flee` 三种 | `battle.ts:767`、`v2.ts:233` |
| 入场 | `createBattle` 一次 `buildUnits` 建完（`round: 1`），之后**没有任何加单位的通道** | `battle.ts:240` |
| 指令 | `skill` / `item` / `flee` / `pass`，无 `summon` | `v2-command.ts:21` |
| 层数 | 战斗侧 `multiplierOf` / `evadeOf` 只读 `status.combat` 的定值，`inst.stacks` **完全不参与**；而世界层属性修正按 `delta * inst.stacks` 乘 | `battle.ts:138`、`battle.ts:155`、`engine.ts:92` |

**层数这条最要紧**：同一个 `stacks` 在两条链上语义相反（世界层乘、战斗层不乘）。
所以「魔虚罗每层适应少受一点」不是一个新字段，而是先回答「层数到底乘不乘、在哪一层乘」。

### 四项各自要定的语义（难点不在实现量）

1. **中立单位**
   缺的是「第三阵营」。要定：能不能被玩家 / 敌人 / NPC 攻击；它自己打谁（最近 / 随机 / 只还手）；
   **参不参与胜负**（不参与 ⇒ 清场判定要跳过它；参与 ⇒ 判据变成「敌对阵营全灭」）。
   硬约束：中立单位**不能**塞进 `enemies`——现在它一死就等于全灭胜利。

2. **召唤**（战斗内入场）
   缺的是运行期加单位。要定：谁召唤（角色技能 / 补正触发 / 事件效果）、上限与去重
   （同名多只？只允许一只？被召唤物能否再召唤）、入场当回合行不行动、召唤者死亡后召唤物归谁、
   单位从哪建（`characterRef` 判活要不要复用 `resolveCombatRefs`）。
   与现有 `npcs:` 兜底的差别：那条是**开场**按事件声明建人，召唤是**战斗中**动态加。

3. **胜负判定拓展**
   判据现在写死在 `checkBattleEnd` 的两条 if 里。要定：判据能否由事件声明
   （全灭 / 击杀指定单位 / 撑过 N 回合 / 保护对象存活 / 敌方撤退）、中立与召唤物怎么计入、
   失败条件是否只有「玩家 hp ≤ 1」（守护对象死亡算不算）。
   落地形状倾向：`settle` 上扩一张 `victory: [...]` / `defeat: [...]` 条件表，`checkBattleEnd`
   变成求值器；但**默认行为必须与今天逐字节一致**，否则所有旧事件会静默漂移。

4. **补正层数**
   要定：层数在战斗里乘不乘（伤害倍率 / 减免 / 闪避 / 命中），以及「每层」是加算还是乘算。
   魔虚罗要的是「每层适应，减免递增」；而眩晕、领域压制这类补正要的是「叠层只影响时长或上限」。
   ⇒ 大概率要**按补正声明**（如 `combat.perStack: true`），而不是全局改语义——
   否则 41 条 `target: self` 的自增益（3.0.0 现况）会突然按层数翻倍。

### 依赖顺序

`1 → 3` 可以一起做（阵营与胜负是同一张表的两面）；`2` 依赖 `1`（召唤出来的中立单位得有地方放）；
`4` 独立。魔虚罗要 `1 + 4` 同时到位才立得住（敌我不分 + 每层适应）。

### 不做 / 降级（记下来避免重开讨论）

- **不做**「把魔虚罗塞进 `enemies` 再加一条不死判定」：那会让胜利条件在数据层撒谎。
- **不做**「用满额 `immune` 补正硬编码减免」当适应：层数不可见、不可交互，也解释不了「越打越抗」。
- 单角色特判（`if characterId === "npc-mahoraga"`）**一律否决**。

### 验收（做成什么样算完）

- 中立单位能与玩家 / 敌人互殴，且它 alive 与否**不改变胜负**；
- 战斗中后手召唤出的单位能行动、能被打死，战斗结束回写不炸；
- 事件能声明「击杀指定单位即胜利」，未声明时行为与今天完全一致（有回归用例）；
- 同一条补正叠 3 层与 1 层，在**声明了 per-stack 的字段**上数值不同，未声明的字段一点不变；
- 魔虚罗能用纯数据配出来：开场或中途登场、敌我不分、每层减免递增、打不死才算输。

## B-08 装备授予技能 / 施放消耗修正（战斗面批，与 B-07 同一轮）

- **原状态**：待实施
- **状态**：**已实施**（2026-11-19，ADR-012 D7 / D8）——`grantsSkill` 与 `mpCostMultiplier` 都已上线；
  天逆鉾实测从「30 局 0 伤害」变成「一刺 32 穿无下限」，六眼把苍从 18 压到 2。
- **提出人**：用户（2026-11-19）
- **类型**：**协议级**（`schema/equipment.ts`、`schema/status-effect.ts`、`battle.ts`），动手前随 B-07 一起立 ADR
- **触发场景**：
  1. **天逆鉾要「必中」**。设定上它「强制解除术式」，但引擎里解除术式没有通道；为了破「无下限」（`evade: 1`）只需要一件事：这一击是必中。道具现在只能给属性词条（`dynamicModifier`），给不了行为，所以甚尔拿着天逆鉾也碰不到五条（`inspect sim --as npc-toji --vs npc-gojo` 实测 30 局 0 伤害）。
  2. **六眼要「咒力消耗 -90%」**。消耗是死数字（`cost: { mp: 18 }`），没有任何修正入口；五条 240 点池只够 13 发苍。

### 落地形状（倾向）

- **装备授予技能**：`items.yaml` 的装备加可选 `grantsSkill: <skillId>`。持有即视为拥有该技能（战斗技能筛选读 `unit.skills ∪ 装备授予`）。天逆鉾 = 一件武器 + 一个 `sk-ten-spear`（`hit: "guaranteed"`、零消耗、短冷却），**复用 ADR-008 已有的必中词表**，不动闪避链路。
  - 不做 `traits: { ignoreEvade: true }`：NPC 的装备在 `buildUnits` 阶段就折进属性、不在战场对象里，要让「攻击方持有某物」参与判定得改战场单位结构，比授予技能重得多。
  - 待定：卸下装备时技能是否立刻消失（倾向「是」，因为「用技能」和「拿着它」是同一件事）；同一技能被两件装备同时授予时如何计数（倾向去重）。
- **消耗修正**：`StatusEffectSchema.combat` 加 `mpCostMultiplier`（累加，与 `damageDealt` 同形）。结算：`cost = Math.max(0, Math.ceil(base × (1 + Σ)))`。
  - 取整必须显式（ceil 而不是 round）：`18 × 0.1 = 1.8 → 2`，`32 × 0.1 = 3.2 → 4`；用 round 会让 `1.4 → 1` 这类「-90% 变成 -96%」的漂移。
  - 影响四处：`missingCost`（够不够）、`payCost`（扣多少）、AI 技能筛选（`aiTurn` 用 `missingCost`，自动跟上）、展示层（`effects.ts` 的技能摘要要显示修正后的价格）。
  - 不把消耗修正做成属性（`costDiscount` 属性）——那会让「六眼」变成可被别的效果放大的数字，而它不是。

### 验收

- 甚尔持天逆鉾 vs 五条：`inspect sim` 的 `hitRate > 0` 且 `dpr > 0`（今天恒为 0）；
- 不持天逆鉾时行为与今天完全一致（有回归用例）；
- 带六眼的单位施放苍，`missingCost` / `payCost` / AI 选择 / 面板价格四处一致，且 `ceil` 口径有断言；
- 未声明 `mpCostMultiplier` 的补正一点不变。

### 关联

ADR-008（必中 / 闪避词表）、ADR-011 D5（本轮明确不做，列了边界）、B-07（同一批战斗面协议增量：
召唤 / 胜负条件 / 中立单位 / 每层补正）、**ADR-012**（本轮实现）。

### 落地纪要

- **授予技能**：`items.yaml` 的 `grantsSkill`（加载期校验技能存在）。技能集唯一入口
  `playerSkills(state, lookup)` = 角色自带 ∪ 装备授予；`skill_not_owned`、投影技能列表、
  仪器挑招三处同源——之前各处自己 `.includes()`，就是「拿在手上却没有那一招」的来源。
- **两个「待定」的答案**：卸下即消失（技能集每次现算，不做运行时增删通道，因为没有换装指令）；
  两件装备授予同一技能去重（`Set`）。
- **消耗修正**：`combat.mpCostMultiplier` 累加，`ceil(mp × max(0, 1+Σ))`。四处一致靠
  `effectiveCostOf` 一个出口（够不够 / 扣多少 / AI / 面板价），`canUseSkill` 顺手把
  「耗尽池」的拒绝理由也统一了：`not_enough_mp` / `not_enough_resource:<key>`。

## B-19 关系双真相 —— **已实施（ADR-017，2026-11-20）**

- **原问题**：「你在我眼里多重要」有两个存处 —— `npc.relationship` 标量与关系边 `value`。
  事件改一个另一个原地不动，于是卡片 chip 与带 `kind` 的条件各说各话。
- **结论**：不是「两个存处同步」，而是**按端点分工**。`to === self` 的强度**只**存标量，
  边上的 `value` 只服务非 self 端点。
- **四道口子一起堵**：加载期（`to: playerId` 带 `value` ⇒ error，不静默丢弃）、
  写入期（`adjustRelation` 折进标量、`addRelationEdge` 把 `value` 当**绝对赋值**写标量）、
  读取期（`{relation, kind}` 条件在归一化 `to === selfId` 时读标量）、
  建世界期（模板声明的指向 self 的边折进标量，后写覆盖）。
- 详见 `docs/adr/50-关系与演员.md`；回归 `test/unit/adr-017.test.ts`、`test/unit/self-pointer.test.ts`。

## B-20 玩家侧关系缺失 —— **已实施（声明面，ADR-017，2026-11-20）**

- **原问题**：`characters[].relations` 的 `from` 恒为该角色，只能表达「他们视你如何」，
  没有「你视他们为何」的声明点 —— 关系图上玩家永远是被动的一方。
- **结论**：加 `world.playerTemplate.relations`（`from` 恒为 self），加载期校验未知 `to`、
  并禁止写 `value`（同 B-19：指向 self 的强度归标量）。
- **这是一个纯声明缺口**：投影早就认 `direction: "out"`，下游一行没改。
- **仍未做**：**玩家侧关系面板 UI**（读得到、没有界面展示）。这条仍挂在下面「仍需产品设计」里，
  但它不再是协议债 —— 数据面已通。

## B-21 情报档位的死旗标 —— **已实施（ADR-017，2026-11-20）**

- **原问题**：开局往 `flags` 里写 `infoVisibility:<npc>` / `relationSource:<npc>` 一串字符串，
  全仓**只有写没有读**。
- **结论**：删掉写入。它们**不是可判定的谓词**（没有 `condition` 读它），所以不需要迁移 ——
  旧存档里的死字符串留着也无害（没人读）。
- 「谁知道什么」由三个真实事实表达：`npc.visibility`、边 `scope`（含 `knownBy`）、`npc.secrets`。
- `OpeningNpcSetupSchema.visibility` 这个**输入字段**保留了一个空壳，只为在作者仍写它时
  报一句人话的弃用错误，而不是让 zod 抛 `unrecognized key`。

## B-22 装备词条 v2 —— **已实施（ADR-020，2026-11-20）；剩余能力按用户裁定冻结**

- **提出人**：用户（2026-11-20「先把装备那块做完吧：label 没有、效果不能加必中，再看看还缺什么，通用地想」）
- **已落地**：
  - `dynamicModifier`（单条属性）→ **`dynamicModifiers[]`**，属性与战斗轴可混排，每条可带 `label`（面板不再只有数字）；
  - 战斗轴 `combat: { hitChance | evade | damageDealt | damageTaken | guaranteedHit }`，与状态**同一批乘区**
    （`multiplierOf` / `evadeOf` / 命中判定各一处，不是两套公式）；
  - `guaranteedHit` **跳过命中骰与闪避门** —— 天逆鉾不再需要 `grantsSkill` 造一个假招式（旧做法已验证并回滚）；
  - 建场烘进 `BattleEnemy.gear` / `Combatant.gear`（战斗中不换装 ⇒ 一次求值，重载不重算）；
  - `equipment.categories: [{ id, label }]` → 投影 `categoryLabel`（面板不再出现 `cursed-tool`）。
- **冻结的七项**（2026-11-20 用户：「咒术世界好像暂时用不到吧」）：

  | 缺什么 | 为什么现在不做 |
  |---|---|
  | 耐久 / 层数 | `durability`/`stacks` 字段在，但没有任何规则读；没有剧本让咒具有损耗 |
  | 触发式词条 | 「命中时施加 X」要挂回合钩子，属协议级；现有装备都只是改数 |
  | `costMultiplier` 词条 | 状态能改价、装备不能；六眼是状态不是咒具，没有第二个用户 |
  | 套装 / 镶嵌 / 升级 | 需要新的定义层，属产品设计 |
  | 战斗中换装 | 建场即定死；换装要重算整场，当前没有换装指令 |
  | `grantsStatus` | 「戴上就中毒」表达不了；咒具没有这类设定 |
  | 负重 / 件数 | 槽位已限件数，重量没有剧本需求 |

- **解冻条件**：至少一个真实剧本需求（例如咒具耐久影响战斗、被动触发式咒具），**先立 ADR 再动协议**；
  没有第二个用户就不进内核（SPEC §1.6「先模板后上提」）。

## B-23 铁匠扩展（blacksmith）：负重 / 耐久 / 叠层 / 增幅 / 镶嵌 / 附魔

- **提出人**：用户（2026-11-20「建议后续把这些能力加到铁匠扩展」）
- **状态**：待设计，**不排期**
- **归扩展不归内核**：判据是 SPEC §1.6「多个非全部世界才要的能力进扩展」，与 family 同构 ——
  内核拥有装备的**事实**（定义 / 实例 / 词条求值 / 战斗快照），扩展拥有**养成**
  （磨损、强化、镶嵌、附魔的记账与解释）。jjk 19 件咒具一条都用不上（ADR-020 已冻结），
  没有第二个用户就进内核，等于每加一项都要模板维护镜像与回写。

### 六项各自落在哪（先分清「记账」与「改数」）

| 能力 | 记账（扩展切片） | 改数（要进 `effectiveAttributesOfActor` / `equipmentCombatOf`） |
|---|---|---|
| 负重 | 物品**没有 `weight` 字段** ⇒ 用扩展配置 `weights: {itemId: n}` 映射，零协议 | 超重惩罚 = 挂一条隐藏修正（`agility`/`evade` 负数），走既有状态链路 |
| 耐久 | `EquipmentInstance.durability` 字段已在（内核不读），扩展读写 | 「坏了不能用」是**判定**不是数值 ⇒ 先做成 `broken` 状态 + 模板条件 |
| 叠层 | `EquipmentInstance.stacks` 字段已在 | 每层数值 = 隐藏状态 × 层数（状态自己就能叠层） |
| 增幅 +N | 扩展切片记 `level` | 每级数值 = 隐藏状态（重授予同 id 幂等，改值只能换 id） |
| 镶嵌 | 扩展切片记孔位 → 宝石 id，一孔一颗由扩展校验 | 宝石词条 = 隐藏状态 |
| 附魔 | 扩展切片记附魔 id | 附魔本质就是持久 buff ⇒ 隐藏状态最自然 |

### 结论：五项可以零内核改动先跑

状态已经具备 `attributeModifiers`、战斗轴、叠层、永久时长，且进 `effectiveAttributesOfActor` ——
「装备上的持久数值」用**隐藏状态当载体**就能通。内核真正缺的只有两件，都不急：

1. **署名接缝**：装备详情要逐条写「【锋利 III】+3」并按实例区分，现在只能显示成状态行。
   future 形状：`equipmentModifiersOf(instance)` 这类钩子，把扩展贡献并进 `equipmentCombatOf`。
2. **自动磨损时机**：每战掉耐久 / 用一次掉一点，需要战后（或使用后）的扩展钩子；
   先用效果 `wearItem` 由剧本与结算显式调用。

**载体自身的三个坑**（写在这里，省得开工时再撞）：

- **「持久 + 可叠」没有天然档位**：`talent` 能持久但禁叠层，`battle` 出不了战斗，
  ⇒ 叠层的附魔只能走 `modifier` + 一个很长的 `{ value, unit }`（如 36500 天）。
  非叠层的（单条附魔、镶嵌一颗）用 `talent` 更干净。
- **摘装备要能摘掉状态**：`cureStatus` 只按 `statusId` 过滤、**不看 kind**，所以能做到；
  但「增幅 +1 → +2」不能直接改，得 `cureStatus` 再 `applyStatus`（换 id 或换实例）。
- **`hidden` 只是不写名字**，条数与合计仍会变 —— 除非加 `source: equipment` 折叠。

### 开工前必须先裁决

1. **隐藏状态当载体算不算越界**：扩展效果 `apply(state, …)` 拿得到 `state.player.statuses`，
   但 `docs/EXTENSIONS.md` §1 写的是「扩展只解释事实」。两条路：承认「状态是公共机制、扩展可授予」，
   或扩展只写自己的切片、由投影合并（工作量大一档）。
2. **耐久的语义**：坏了是「不可用」（判定，模板条件能表达）还是「数值打折」（伤害 ×0.5，
   要内核接缝）。两者实现差一整档，先定这个再动手。

### 将来开工顺序

`design.md` → `extensions/blacksmith` 骨架（状态切片 + 四个效果：`temper` / `socket` / `enchant` / `repair`）
→ **先在瓦勒蒙试**（现成的装备与加点试验田）→ 再谈是否要内核接缝。扩展自带 UI 需新增一个
`personal.subview` 槽（现在扩展只能挂 `world.subview`）。

## 凭证信封的局域网降级（2026-11-20）

B-01 的信封（RSA-OAEP + AES-GCM）依赖 `crypto.subtle`，而它只在**安全上下文**存在
（https / localhost）。局域网用 `http://192.168.x.x` 打开时整条「填自定义 LLM」的路不可用，
自签证书在手机上又要逐台接受警告。

决定：加一档 `v: 0` 明文信封，**两端的门都锁在私有地址上** ——
前端只在 loopback / 私网 / `.local` 页面降级（公网 HTTP 直接拒绝），
服务端只在 `request.ip` 或 `Host` 是私有地址时接受 `v: 0`。

不做成环境变量开关：那种开关迟早会在云端被打开，然后变成一个静默的降级口。
界面必须明说（保存后的 warning：「本机没有 HTTPS：凭证以明文提交，只应在你信任的局域网里使用」）——
静默降级会让「已经加密了」这句话变成假话。
